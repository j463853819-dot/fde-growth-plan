# 国内 FDE 岗位和海外有什么不同

国内很多岗位开始叫 FDE，但实际工作内容差异很大。

有的更像售前解决方案，有的更像交付工程师，有的更像 AI 应用顾问，有的真的在做现场工程。名字一样，不代表岗位一样。

> **国内 FDE 最大的风险，是名字变高级了，工作却仍然停在低毛利交付。**

## 一句话定义

海外 FDE 更强调工程能力前移、客户现场验证和产品反哺；国内 FDE 往往叠加了售前、交付、私有化部署、客户培训、项目管理和定制开发等职责。

所以判断一个岗位是不是 FDE，不能只看 title。

要看它是否真正承担了现场发现、工程验证、生产责任和产品反哺。

## 岗位差异

| 维度 | 海外典型 FDE | 国内常见 FDE |
| --- | --- | --- |
| 商业基础 | 高客单价、重结果 | 项目制、预算敏感 |
| 工作边界 | 现场工程 + 产品反哺 | 售前、交付、定制混合 |
| 技术重点 | 平台能力、数据建模、生产系统 | 私有化、集成、AI 应用搭建 |
| 组织地位 | 靠近核心产品和战略客户 | 容易被放在交付或解决方案团队 |
| 成功标准 | 业务结果和可复用产品能力 | 项目验收和客户满意 |

国内 FDE 更容易被拉进“什么都做”的状态。

这不一定是团队不专业，而是市场结构会自然把它推向这个位置。

## 国内 FDE 更需要边界感

国内客户常常希望一个团队同时解决：

- 售前方案。
- 原型演示。
- 私有化部署。
- 数据接入。
- 定制开发。
- 培训运维。
- 后续修改。

如果没有边界，FDE 会很快变成高级外包。

边界感不是拒绝客户。

是把探索、试点、生产、运维和产品化分成不同阶段，给每个阶段定义清楚交付物和责任。

## 实战拆解：一个“AI 解决方案工程师”到底是不是 FDE

假设一个岗位 JD 写着：

“负责客户需求调研、AI 方案设计、Demo 搭建、私有化部署、客户培训和项目验收。”

这可能是 FDE，也可能不是。

要继续看四个问题：

| 判断问题 | 是 FDE 的信号 | 不是 FDE 的信号 |
| --- | --- | --- |
| 是否重新定义问题 | 会进入现场找真实瓶颈 | 只按客户需求做演示 |
| 是否工程验证 | 能接数据、搭系统、做评测 | 只写方案和 PPT |
| 是否生产化 | 关注权限、回滚、SLO、接管 | 只做到项目验收 |
| 是否产品反哺 | 把共性能力带回产品 | 做完项目就结束 |

FDE 不是因为“见客户 + 写代码”成立。

而是因为它负责把不确定现场推进到可运行系统。

## 国内 FDE 的机会

国内市场也有优势：

- 行业场景足够丰富。
- 传统行业 AI 改造需求真实。
- 工程人才供给强。
- AI 工具链迭代快。
- 客户愿意试点，但需要更强价值证明。

机会在于用标准化方法把项目制经验沉淀下来。

如果国内 FDE 能把每次项目里的事实表、切片画布、ADR、评测集、接管清单沉淀下来，它就不会只是项目交付。

它会逐步变成组织能力。

## 岗位判断表

| 问题 | 如果答案是“是” | 更接近 |
| --- | --- | --- |
| 是否重新定义现场问题 | 是 | FDE |
| 是否动手构建和验证系统 | 是 | FDE |
| 是否参与生产化和接管 | 是 | FDE |
| 是否把经验反哺产品 | 是 | FDE |
| 是否只是做演示和验收 | 是 | 售前/交付 |

## 可以带走的判断

国内 FDE 要成立，必须从岗位名回到工作对象：真实现场、工程验证、生产责任和产品反哺。

title 不重要。

交付对象才重要。
