# 合规、私有化和数据本地化如何改变 FDE

很多 AI 项目在 Demo 阶段都很顺。

上传一份合同，模型能抽条款；接一个知识库，客服助手能回答问题；导入几张报表，系统能生成经营分析。会议上大家都觉得方向成立。

然后客户补了一句：“这些数据不能出内网。”

这句话会把项目从 AI 应用，瞬间变成合规工程、部署工程和客户接管工程。

在中国做 FDE，合规、私有化和数据本地化不是项目后期的部署细节，而是从第一天就会改变问题定义、方案设计、工具选型、交付成本和运行责任。

> **一句可以带走的判断：在中国，FDE 不懂合规和私有化，就很难真正进入生产。**

## 理论框架

合规、私有化和数据本地化，是对 AI/FDE 项目中数据流动、模型部署、系统集成、审计留痕和运行责任的约束集合。

它们决定了技术能力能以什么方式进入组织。

| 约束 | 改变 |
| --- | --- |
| 数据不出域 | 影响模型调用、RAG 架构和部署方式 |
| 私有化部署 | 增加环境适配、运维和升级成本 |
| 信创要求 | 影响数据库、中间件、操作系统和工具链 |
| 等保审计 | 要求日志、权限、访问控制和安全测评 |
| 行业监管 | 限制自动决策和数据使用范围 |

这些约束越晚发现，返工越大。

## 核心方法

FDE 在 Context 阶段就要把合规问题问清楚，而不是等上线前交给安全团队。

| 检查项 | 要问清楚什么 |
| --- | --- |
| 数据出域边界 | 哪些数据不能离开客户环境 |
| 模型部署方式 | 云端、专有云、私有化、本地模型 |
| 权限审批流程 | 谁批准访问，如何记录 |
| 日志和审计要求 | 记录什么，保存多久 |
| 信创适配要求 | 操作系统、数据库、中间件限制 |
| 安全测评要求 | 是否需要等保、渗透、安全评审 |
| 客户接管责任 | 谁负责运行、升级和问题处理 |

这些问题会直接影响方案：能不能用外部模型，能不能做 Agent 写入，能不能把日志发到外部观测平台，能不能远程运维。

## 实战拆解：合同审查 AI 为什么变成私有化工程

客户想做合同审查 AI。

如果数据可以使用云端模型，Demo 很快：上传合同，模型抽取条款，生成风险提示。

但客户补充一句：“合同不能出内网。”

FDE 需要重新设计：

| 变化 | 对方案的影响 |
| --- | --- |
| 合同不能出域 | 需要本地模型或私有推理服务 |
| 条款库在内网 | RAG 要本地向量库 |
| 法务权限不同 | 不同角色看到不同字段 |
| 审计要求高 | 每次检索和输出要留痕 |
| 模型升级受控 | 版本、评测、回滚都要记录 |

这时，第一个切片也要调整。它不再是“做一个合同审查 Agent”，而是“在内网环境中，为采购合同初审生成带引用来源的风险摘要，由法务确认后使用”。

这个定义更慢，但更接近生产。

## 最后判断

合规和私有化会让 FDE 变慢，但也会让真正有能力的团队脱颖而出。

因为只有能处理数据边界、权限审计、私有部署和客户接管的 FDE，才能把 AI 真正带进金融、政务、医疗、制造这些高价值行业。
