# 标准化交付和岗位职能的差异

很多公司谈 FDE，容易先谈岗位：招什么人、叫什么 title、放在哪个部门、汇报给谁。

这些问题重要，但不应该是第一优先级。

因为在中国市场，如果交付方法不标准，岗位再高级，也会被项目现场拖成救火队。一个强 FDE 可以把一个项目做成，但公司想复制十个项目时，很快会发现：新人不知道访谈问什么，Demo 做完不知道怎么判断继续，上线前没有统一门禁，客户接管靠个人经验。

这时候真正缺的不是一个更漂亮的岗位名，而是一套可复制的交付方法。

> **一句可以带走的判断：FDE 的组织化，不是多招几个厉害的人，而是让厉害的人做出的判断可以被复用。**

## 理论框架

岗位职能回答“这个人做什么”。

标准化交付回答“这类项目怎么被稳定完成”。

FDE 要成立，不能只靠岗位描述，还要靠流程、模板、门禁、证据和接管机制。

| 只看岗位 | 加上交付标准 |
| --- | --- |
| 依赖个人经验 | 经验可训练 |
| 项目质量不稳定 | 质量可复查 |
| 做完就散 | 经验可沉淀 |
| 客户持续依赖个人 | 客户能接管 |

岗位是人，标准是系统。

## 核心方法

标准化交付要补齐六类材料。

| 标准 | 解决什么 |
| --- | --- |
| CDEF 流程 | 项目如何推进 |
| 事实约束表 | 现场如何被记录 |
| 需求切片画布 | 需求如何被验证 |
| ADR | 决策如何被复查 |
| 生产门禁 | 上线如何被判断 |
| 接管清单 | 客户如何持续运行 |

标准化交付不是替代 FDE，而是放大 FDE。

它应该标准化方法、证据、门禁、责任和复盘；但不应该标准化行业判断、客户语境、价值切口和方案取舍。

真正成熟的 FDE 标准，是让底座稳定，让判断保留空间。

## 实战拆解：为什么一个好 FDE 不能复制出十个好项目

一个公司有一个非常强的 FDE。

他能访谈客户、写 Demo、接系统、处理上线问题，客户也信任他。

但公司想扩张时，问题来了：

- 新人不知道访谈问什么。
- Demo 做完不知道怎么判断继续。
- 上线前没有统一门禁。
- 失败样本没有沉淀。
- 客户接管靠个人口头交接。

结果就是：强人能做成项目，但组织学不会。

标准化交付要解决的正是这个问题。它不是把优秀 FDE 变成流水线工人，而是把优秀 FDE 的判断拆成可训练、可复查、可复用的动作。

在中国市场，这一点尤其重要。客户多、项目杂、预算敏感，如果每个项目都靠高级 FDE 深度定制，成本很难成立。

## 最后判断

FDE 的未来，不是岗位名越来越多，而是方法越来越可复制。

当一个团队能稳定把现场问题变成生产系统，并让客户接管，这才说明它真的拥有 FDE 能力。岗位职能定义的是“谁来做”，标准化交付定义的是“组织如何持续做成”。
