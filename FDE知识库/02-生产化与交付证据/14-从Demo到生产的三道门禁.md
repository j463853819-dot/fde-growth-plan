# 从 Demo 到生产的三道门禁

合同审查 AI 的 Demo 做得很顺。

上传合同，系统能识别付款条款、违约责任和自动续约风险。法务负责人看完说：“可以继续。”

但“可以继续”不等于“可以上线”。

下一步到底是继续原型、进入试点，还是开放给更多业务部门？这个判断不能靠兴奋感。

从 Demo 到生产，最容易被低估的不是开发工作量，而是判断门槛。

很多团队会把路径想得很线性：先做 Demo，再补功能，再上线。听起来顺，但真实 FDE 项目不是这样。Demo 能跑之后，项目反而进入更难的阶段：哪些假设已经验证，哪些风险还没暴露，哪些责任必须有人接住？

所以，从 Demo 到生产不是“把功能做完整”，而是连续通过三道门禁：原型退出、试点准入、生产准入。

从定义上看，门禁是一组阶段性判断标准，用来决定项目是否可以进入下一阶段。它不是流程审批表，而是风险控制机制。每道门禁都要说明：当前阶段验证了什么，还缺什么证据，谁有权放行，失败时如何回退。

> **一句可以带走的判断：FDE 项目不是一路冲到上线，而是一次次带着证据穿过门禁。**

## 一句话定义

从 Demo 到生产的三道门禁，是 Prototype Exit、Pilot Ready、Production Ready。

它们分别判断：原型是否验证关键假设，试点是否具备真实场景条件，生产是否具备运行、监控、回滚和接管能力。

## 第一关：Prototype Exit，原型退出标准

原型阶段的任务不是做一个完整产品，而是验证方向是否值得继续。

Prototype Exit 要回答的是：这个 Demo 是否已经证明了关键假设？如果没有，就不应该进入试点。

| 检查项 | 合格标准 |
| --- | --- |
| 问题定义 | 能说清具体场景、角色、损失和目标 |
| 价值假设 | 用户看完后能判断是否有用 |
| 数据假设 | 已确认关键输入是否存在、是否可授权 |
| 技术路径 | 至少证明核心链路可运行 |
| 风险暴露 | 已列出被简化、绕过或尚未验证的部分 |
| 下一步决策 | 明确继续、缩小、转向还是停止 |

Prototype Exit 最怕的是“演示很顺，所以继续做”。FDE 更应该问：这次演示到底让我们知道了什么？

## 第二关：Pilot Ready，试点准入标准

试点不是扩大版 Demo。

Demo 多半在受控环境中完成，试点则要让真实用户、真实数据和真实流程进入系统。它的任务不是证明系统完美，而是验证系统在有限真实场景下能否产生效果，并暴露生产前必须解决的问题。

Pilot Ready 要回答：

- 是否有明确试点范围？
- 是否有真实用户愿意进入流程？
- 是否有可用数据和权限授权？
- 是否有人工兜底和退出机制？
- 是否定义了试点指标？
- 是否记录失败样本和异常路径？

| 试点要验证 | 不是只看 |
| --- | --- |
| 用户是否持续使用 | 用户是否口头认可 |
| 输出是否被采用 | AI 是否回答流畅 |
| 异常是否可处理 | 正常路径是否顺利 |
| 指标是否有变化 | 演示反馈是否积极 |
| 客户团队是否能参与 | FDE 团队是否能维护 |

试点阶段的好结果，不是“没有问题”，而是问题被真实暴露，并且有能力收敛。

## 第三关：Production Ready，生产准入标准

生产准入是最容易被低估的一关。

到了这一关，系统不再只是项目团队内部能跑，而是要进入客户组织的日常运行。它必须被监控、被审计、被接管，也必须能在失败时限制影响。

Production Ready 至少要覆盖七类标准：

| 类别 | 必须确认 |
| --- | --- |
| 数据 | 来源、更新、质量、脱敏和权限过滤 |
| 权限 | 身份、角色、工具调用和写入边界 |
| 评测 | 评测集、回放、失败样本和回归测试 |
| 可观测 | 日志、指标、trace、成本和延迟 |
| 风险 | 降级、回滚、人工接管和事故复查 |
| 运营 | SLO、告警、值班、运行手册 |
| 接管 | 客户 Owner、培训、演练和后续变更流程 |

如果这些没有准备好，上线就只是把风险从 FDE 团队手里转移到客户组织里。

## 每道门禁都要有 Owner、证据和回滚边界

门禁不是一句“可以了”。

每道门禁至少要留下三样东西：

| 要素 | 说明 |
| --- | --- |
| Owner | 谁负责判断，谁承担下一阶段结果 |
| 证据 | 用什么材料证明达到标准 |
| 回滚边界 | 触发什么条件时停止、降级或退回上一阶段 |

比如 Agent 项目进入试点前，Owner 不能只有 FDE。业务方要确认试点价值，安全团队要确认权限边界，平台团队要确认日志和成本监控，客户 Owner 要确认人工接管方式。

这听起来麻烦，但它能避免一个更大的麻烦：系统出了事之后，大家才发现从来没人真正拥有它。

## 常见误判：把可演示当成可运行

最常见的误判有三种。

第一，把“技术可行”当成“业务可用”。模型能回答，不代表用户会采用。

第二，把“试点有效”当成“生产可靠”。小范围可用，不代表多角色、多权限、多异常场景下也可靠。

第三，把“FDE 能维护”当成“客户能接管”。如果系统只能靠 FDE 团队理解和运行，它还不是生产交付。

## 三道门禁矩阵

| 阶段 | 核心问题 | 放行证据 | 主要风险 |
| --- | --- | --- | --- |
| Prototype Exit | 方向是否值得继续 | 关键假设验证、价值反馈、风险清单 | 做错方向 |
| Pilot Ready | 是否能进入有限真实场景 | 试点范围、真实用户、数据授权、兜底机制 | 试点失控 |
| Production Ready | 是否能被组织长期依赖 | 评测、权限、监控、SLO、接管演练 | 生产不可控 |

FDE 的专业判断，不是把项目推得越快越好，而是知道什么时候该快，什么时候必须停下来补证据。

在 AI 时代，这种门禁意识会越来越重要。因为 Demo 越容易，越需要有人守住生产边界。
