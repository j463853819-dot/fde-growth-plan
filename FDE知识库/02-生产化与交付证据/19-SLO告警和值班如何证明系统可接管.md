# SLO、告警和值班如何证明系统可接管

系统上线第一周，客户很满意。

第二周，接口开始间歇性超时，AI 回复延迟从 3 秒变成 20 秒。一线用户在群里抱怨，但没人知道该看哪个指标，也没人知道这算不算事故。

这时才发现：系统上线了，但没有真正被接管。

系统上线不等于系统可接管。

很多 FDE 项目在上线时看起来已经完成：功能能用，用户能访问，业务方也认可。但只要问几个问题，接管风险就会暴露出来：系统慢了谁知道？AI 输出质量下降谁发现？接口失败谁处理？客户团队能不能看懂告警？出问题后能不能回滚？

如果这些问题没有答案，系统只是上线了，还没有真正被组织接住。

从定义上看，SLO，Service Level Objective，是系统对业务承诺的可量化目标；告警是当系统偏离目标或风险出现时触发的通知机制；值班是确保有人在合适时间响应、判断和处理异常的责任安排。三者合在一起，证明系统不仅能运行，而且能被持续运营。

> **一句可以带走的判断：客户接管的前提不是系统能跑，而是客户能看懂系统状态，并在出事时接得住。**

## 一句话定义

SLO 是系统对业务承诺的可量化目标。

告警是当系统偏离目标或风险出现时触发的通知机制。

值班是确保有人在合适时间响应、判断和处理异常的责任安排。

## 从业务承诺反推 SLI/SLO

SLO 不能从技术指标直接开始。

FDE 应该先问：这个系统对业务承诺了什么？

如果是客服 AI 助手，业务承诺可能是缩短响应时间、提高回答一致性、减少人工查询成本。如果是销售线索助手，业务承诺可能是更快识别高价值客户。如果是风险预警系统，业务承诺可能是更早发现异常。

然后再反推 SLI 和 SLO。

| 业务承诺 | SLI 指标 | SLO 示例 |
| --- | --- | --- |
| 客服响应更快 | 建议生成延迟 | 95% 请求在 3 秒内返回 |
| 回答更可靠 | 评测通过率 | 每周回放样本通过率不低于 90% |
| 系统可用 | 成功请求率 | 工作时间可用性 99% |
| 成本可控 | 单次任务成本 | 平均成本不超过设定阈值 |
| 风险可控 | 高风险转人工率 | 高风险场景 100% 触发人工确认 |

AI 项目的 SLO 不能只看可用性，还要看质量、成本和风险。

## 指标、日志、Trace 分别看什么

很多团队会说“我们有日志”，但日志不是全部。

| 类型 | 主要回答 |
| --- | --- |
| 指标 Metrics | 系统整体状态是否健康 |
| 日志 Logs | 某次事件具体发生了什么 |
| Trace | 一次请求经过了哪些步骤 |

对于 AI/Agent 系统，Trace 特别重要。因为一次结果可能经过用户输入、Prompt 构造、知识检索、模型调用、工具调用、权限过滤和输出生成。没有 Trace，出了错很难知道错在哪里。

最小可观测内容包括：

- 请求量、成功率、失败率。
- 延迟和成本。
- 模型调用和工具调用记录。
- 检索命中文档。
- 权限过滤结果。
- 人工接管和回滚记录。
- 用户反馈和修改率。

## 告警如何避免没人响应

告警不是发消息。

一个没人响应、没人判断、没人复盘的告警，只是噪音。FDE 项目里，告警设计要同时考虑触发条件、接收人、响应动作和升级路径。

| 告警类型 | 触发条件 | 响应动作 |
| --- | --- | --- |
| 可用性告警 | 请求失败率超过阈值 | 平台或运维排查服务 |
| 质量告警 | 回放通过率下降 | FDE/产品复查 Prompt、RAG 或模型 |
| 权限告警 | 出现越权访问尝试 | 安全团队介入 |
| 成本告警 | 调用成本异常增长 | 限流、检查循环调用 |
| 业务告警 | 高风险任务未转人工 | 业务 Owner 处理 |

每个告警都要有 Owner。否则系统会在“大家都收到了”里失去响应。

## 运行手册和回滚演练

客户接管前，不能只交一份功能说明。

至少要有运行手册，说明：

- 系统正常状态是什么样。
- 常见告警是什么意思。
- 先看哪些指标和日志。
- 什么时候需要转人工。
- 什么时候需要降级。
- 如何回滚到旧流程。
- 事故之后如何复查。

更重要的是，要做一次演练。

比如模拟“知识库更新后，客服 AI 回答准确率下降”。客户团队需要演练：谁发现，谁确认，谁暂停能力，谁回滚知识库，谁通知业务，谁复查失败样本。

没有演练的接管，常常只是名义接管。

## 一个案例：客服 AI 助手的接管指标

假设客服 AI 助手进入生产，SLO 可以这样设计：

| 维度 | 指标 |
| --- | --- |
| 可用性 | 工作时间成功请求率不低于 99% |
| 延迟 | 95% 建议在 3 秒内返回 |
| 质量 | 每周评测集通过率不低于 90% |
| 风险 | 投诉、高金额退款场景必须转人工 |
| 采用 | 一线客服建议采纳率持续高于 60% |
| 成本 | 单次建议平均成本不超过预算阈值 |

这套指标让客户知道系统是否健康，也让 FDE 团队知道什么时候应该介入。

## 客户接管前必须完成的演练

| 演练 | 目的 |
| --- | --- |
| 服务不可用 | 验证告警、降级和恢复 |
| 质量下降 | 验证评测、回放和暂停机制 |
| 权限异常 | 验证安全响应和审计 |
| 成本异常 | 验证限流和调用分析 |
| 错误写入 | 验证回滚和业务通知 |

演练不是形式主义。它能提前暴露客户团队是否真的知道怎么运行系统。

## SLO 定义卡模板

| 字段 | 内容 |
| --- | --- |
| 业务承诺 | 这个系统对业务承诺什么结果 |
| SLI | 用什么指标观测 |
| SLO | 目标阈值是什么 |
| 告警条件 | 低于什么标准触发 |
| Owner | 谁响应 |
| 处理动作 | 先看什么，怎么处理 |
| 回滚方式 | 什么时候降级或退回旧流程 |

FDE 的交付不应该停在“我能把系统跑起来”。更成熟的交付，是让客户组织能看懂、能响应、能复查、能继续运营。

AI 越深入业务流程，SLO、告警和值班就越不是运维细节，而是组织信任的一部分。
