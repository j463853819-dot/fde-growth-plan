# 评测集、回放和回归测试怎么设计

客服 AI 助手上线前，团队试了十几个问题。

回答都挺顺，语气也自然，引用看起来也对。项目群里有人说：“感觉可以上试点了。”

但 FDE 最怕的就是这句话：

“我试了几个问题，感觉还不错。”

主观体验当然有价值，但它不能作为上线标准。尤其在 FDE 项目里，AI 系统往往要进入真实工作流，影响客服回复、销售判断、风险识别、报告生成或工单处理。这个时候，“感觉不错”不够。

从定义上看，评测集是一组代表真实任务分布的样本和标准答案，用来衡量系统输出质量；回放是把历史任务或线上样本重新输入系统，用来复查变更影响；回归测试则是在 Prompt、RAG、模型、工具或规则变化后，验证旧能力没有被破坏。

这三件事合在一起，构成 AI 项目的质量控制底座。

> **一句可以带走的判断：没有评测和回放，AI 项目就只能靠感觉迭代；靠感觉迭代的系统，很难进入生产。**

## 一句话定义

评测集是一组代表真实任务分布的样本和评价标准。

回放是把历史任务或线上样本重新输入系统，复查变更影响。

回归测试是在 Prompt、RAG、模型、工具或规则变化后，验证旧能力没有被破坏。

## 为什么主观体验不能作为上线标准

AI 输出很会制造“看起来对”的感觉。

它语气自然，结构完整，有时还会给出很像专业判断的解释。但在企业场景里，真正重要的不是像不像，而是对不对、稳不稳、能不能追责。

主观体验有三个问题：

| 问题 | 后果 |
| --- | --- |
| 样本太少 | 只覆盖了顺手想到的问题 |
| 标准不清 | 不同人对“好”的理解不同 |
| 无法复现 | Prompt 或模型改了之后不知道哪里变差 |

所以 FDE 需要把体验转成可评测样本，把“看起来不错”转成“在哪些任务上达到了什么标准”。

## 评测集来自哪里

评测集不能只靠团队想象，最好来自真实工作。

常见来源包括：

| 来源 | 适合场景 |
| --- | --- |
| 历史工单 | 客服、售后、IT 支持 |
| 销售记录 | 线索判断、客户摘要、跟进建议 |
| 质检样本 | 内容审核、合规审查、风险识别 |
| 业务报表 | 自动报告、异常解释、趋势分析 |
| 用户反馈 | 失败样本、误判样本、边界问题 |
| 专家构造 | 高风险场景、极端样本、红队测试 |

一个好的评测集，应该同时包含常规样本、困难样本、失败样本和不可回答样本。

## Prompt、RAG、工具调用分别怎么评测

不同 AI 系统，评测重点不同。

| 类型 | 评测重点 |
| --- | --- |
| Prompt 生成 | 是否符合格式、事实是否正确、语气是否合适 |
| RAG 问答 | 是否检索到正确来源、是否引用可信证据、是否拒答 |
| 分类任务 | 标签是否准确、置信度是否可用、边界类是否稳定 |
| 工具调用 | 是否选对工具、参数是否正确、失败是否处理 |
| Agent 流程 | 计划是否合理、步骤是否受控、是否能终止和接管 |

FDE 不能只评测最终答案，还要评测中间过程。尤其是 RAG 和 Agent，很多错误不是发生在最后一句回答，而是发生在检索、工具选择或状态判断里。

## 评测标准怎么写

评测标准要尽量具体。

不要只写“回答准确”。可以拆成：

- 是否引用了正确文档。
- 是否遗漏关键条件。
- 是否编造不存在的信息。
- 是否遵守权限和脱敏要求。
- 是否给出可执行下一步。
- 是否在不确定时拒答或转人工。

示例：

| 样本 | 合格标准 |
| --- | --- |
| 客户询问退款政策 | 必须引用最新政策，说明适用条件，不能承诺超权限退款 |
| 销售请求客户摘要 | 必须区分事实和推测，不能暴露无权限字段 |
| 风险报告生成 | 必须列出数据来源和异常指标，不能凭空解释原因 |

评测标准越贴近业务，越能帮助 AI 项目进入生产。

## 回放如何支持变更

AI 项目会不断变。

Prompt 会改，知识库会更新，模型会升级，工具 schema 会调整，业务规则也会变化。每一次变化都可能让原来有效的能力变差。

回放的作用，就是用一批固定样本重新跑系统，观察变化影响。

| 变更类型 | 回放要看什么 |
| --- | --- |
| Prompt 调整 | 输出质量是否提升，格式是否稳定 |
| 知识库更新 | 是否检索到新知识，旧答案是否失效 |
| 模型升级 | 幻觉、拒答、语气和稳定性变化 |
| 工具变更 | 参数是否仍正确，失败路径是否正常 |
| 权限调整 | 是否仍遵守访问边界 |

没有回放，团队很容易修好一个问题，又悄悄破坏另一个能力。

## 回归测试报告应该包含什么

一份轻量回归报告可以包含：

| 模块 | 内容 |
| --- | --- |
| 变更说明 | 这次改了什么 |
| 样本范围 | 回放了哪些样本，覆盖哪些场景 |
| 通过率 | 总体通过率和关键类别通过率 |
| 失败样本 | 哪些样本失败，原因是什么 |
| 风险判断 | 是否影响上线或继续试点 |
| 后续动作 | 修复、扩大样本、回滚或放行 |

## 一个小案例

客服 AI 助手上线前，团队准备了 120 条历史咨询样本：

- 60 条常规政策问题。
- 30 条复杂订单问题。
- 20 条投诉和高风险问题。
- 10 条应该拒答或转人工的问题。

每次改 Prompt 或知识库，都回放这 120 条样本，并记录回答是否引用正确政策、是否越权承诺、是否能识别转人工场景。

这套评测不一定华丽，但它让团队可以有依据地说：这次改动是变好了，还是只是看起来更顺了。

## 最小评测体系

| 层级 | 最小要求 |
| --- | --- |
| 样本 | 至少覆盖常规、困难、失败和拒答样本 |
| 标准 | 每类样本有明确合格条件 |
| 过程 | 记录输入、检索、工具调用和输出 |
| 报告 | 每次变更后有通过率和失败分析 |
| 决策 | 根据评测决定放行、修复或回滚 |

AI 系统不是写完就稳定的系统。它会随着模型、数据、Prompt 和业务规则不断变化。

FDE 要做的，不是追求一次评测完美，而是建立一条持续验证的链路。只有这样，AI 才能从“聪明的演示”走向“可信的生产能力”。
