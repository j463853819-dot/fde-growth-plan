# FDE 项目为什么需要交付证据包？

销售线索助手 Demo 做完以后，销售负责人很满意。

系统能根据客户画像、历史互动和 CRM 记录，推荐线索优先级。演示时，销售团队甚至当场说：“这个如果能上线，肯定有用。”

但上线评审时，问题一个接一个冒出来：CRM 哪些字段可以给模型读？推荐错了会不会影响大客户跟进？结果要不要反写 CRM？模型更新后怎么重新测？销售运营能不能接管？

很多 FDE 项目卡住，不是因为 Demo 没做出来，而是因为 Demo 做出来之后，没人敢把它真正交给组织使用。

业务方觉得方向对，技术方觉得功能能跑，管理层觉得可以继续推进。但一到上线前，问题就会冒出来：数据权限谁批？异常谁处理？AI 回答错了谁负责？下一次模型更新要不要重新测？客户团队能不能接管？

这时候就需要交付证据包。

从定义上看，交付证据包是一组可复查的工程和业务材料，用来证明一个系统为什么可以进入试点或生产，当前有哪些边界，风险如何处理，后续由谁接管。它不是为了让文档更厚，而是为了让系统从“FDE 团队能跑”变成“客户组织能接住”。

> **一句可以带走的判断：Demo 证明可能性，交付证据包证明可接管性。**

## 一句话定义

交付证据包是一组可复查的工程和业务材料，用来证明一个系统为什么可以进入试点或生产，当前有哪些边界，风险如何处理，后续由谁接管。

它不是为了让文档更厚。

它是为了让系统从“FDE 团队能跑”，变成“客户组织能接住”。

## 为什么 Demo 不能证明可以上线

Demo 天然会简化很多东西。

样例数据可能是手工整理的，权限可能是临时开的，异常路径可能没有覆盖，用户可能是配合演示的少数人，成本和延迟也未必经过长期观察。

这些简化在 Demo 阶段可以接受，因为 Demo 的任务是验证方向。但如果团队把 Demo 的成功直接等同于上线准备完成，就会把很多隐性风险带进生产。

| Demo 能证明 | Demo 不能证明 |
| --- | --- |
| 方向可能有价值 | 系统能长期稳定运行 |
| 用户愿意看一次 | 用户会持续使用 |
| 模型在样例上有效 | 模型在真实分布下可靠 |
| 流程可以演示 | 流程能被组织接管 |
| 技术路径可行 | 风险、权限、成本和责任可控 |

FDE 项目的专业性，恰恰体现在它不会把演示成功当成交付完成。

## 交付证据包解决什么问题

交付证据包解决的不是“有没有资料”，而是“有没有证据”。

它至少要回答五类问题：

| 问题 | 证据包需要给出的答案 |
| --- | --- |
| 为什么要做 | 业务问题、价值假设、成功指标 |
| 为什么这样做 | 方案选择、架构决策、备选方案和取舍 |
| 为什么可以运行 | 数据、权限、评测、监控、回滚机制 |
| 出问题怎么办 | Owner、告警、人工接管、事故复查 |
| 后续如何演进 | 已知风险、开放问题、产品反哺和下一步计划 |

这也是 FDE 和普通定制开发的重要差别。普通交付经常只留下功能清单，FDE 交付必须留下判断过程。因为真正有价值的不是“做了什么”，而是“为什么这么做，以及什么情况下要重新判断”。

## 一个最小证据包包含哪些内容

最小交付证据包不需要一开始就做得很重，但要覆盖关键责任链。

| 证据项 | 作用 |
| --- | --- |
| 问题定义卡 | 说明解决的真实问题、影响角色和业务损失 |
| 需求切片说明 | 说明本次只做哪条价值闭环，哪些明确不做 |
| 事实与约束表 | 记录数据、系统、权限、合规、组织和时间约束 |
| 架构决策记录 | 说明关键方案为什么这么选，替代方案是什么 |
| 评测与回放报告 | 证明 AI 输出、工具调用或流程结果经过验证 |
| 风险与回滚清单 | 标明已知风险、触发条件和处理方式 |
| Owner 责任表 | 明确业务、技术、安全、运维和客户方负责人 |
| 接管检查表 | 验证客户团队是否能解释、操作、复查和继续演进 |

如果项目还处在试点阶段，证据包可以轻量一些；如果要进入生产，证据包就必须覆盖权限、审计、SLO、告警、值班、成本和变更流程。

## 一个简单案例

回到开头那个销售线索优先级助手。

假设 FDE 团队为客户做了这个系统。

Demo 阶段，它能根据客户画像、历史互动和 CRM 记录，给销售推荐线索优先级。演示效果很好，销售负责人也认可方向。

但上线前，交付证据包要继续回答：

- 哪些 CRM 字段可以被模型读取？
- 哪些字段涉及敏感客户信息？
- 优先级推荐错误时，会不会影响大客户跟进？
- 销售是否可以修改推荐结果？
- 推荐结果是否会反写 CRM？
- 如何评测推荐是否真的提升转化？
- 模型或规则更新后，是否要回放历史样本？
- 这个系统由销售运营接管，还是由 IT 平台团队接管？

这些问题不回答，系统不是不能演示，而是不能放心交给组织。

## 证据包和客户接管的关系

客户接管不是培训一次就结束。

真正的接管意味着客户知道系统解决什么问题，知道系统不能做什么，知道异常怎么处理，知道下一次变更要检查什么，也知道哪些风险还没有消除。

交付证据包就是接管的底座。没有证据包，客户只能接管一个“能跑的东西”；有了证据包，客户才可能接管一套“知道为什么能跑、出事怎么处理、以后怎么改”的能力。

## 上线前至少要回答的 10 个问题

| 问题 | 对应风险 |
| --- | --- |
| 这个系统解决的真实问题是什么？ | 价值不清 |
| 成功指标是什么？ | 无法证明效果 |
| 关键输入数据从哪里来？ | 数据不可持续 |
| 谁有权访问和修改？ | 权限越界 |
| AI 输出如何评测？ | 质量不可控 |
| 错误结果如何发现和纠正？ | 责任不清 |
| 发生异常时谁接手？ | 运维不可接管 |
| 哪些条件触发回滚？ | 失败影响扩大 |
| 下一次变更如何复查？ | 迭代失控 |
| 哪些经验可以产品化？ | 现场学习流失 |

FDE 项目进入生产，不应该只靠“大家觉得差不多了”。它需要证据，需要边界，也需要责任链。

从这个意义上说，交付证据包不是文档负担，而是 FDE 把现场项目变成组织能力的最后一段桥。
