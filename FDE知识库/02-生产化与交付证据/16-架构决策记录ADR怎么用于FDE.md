# 架构决策记录 ADR 怎么用于 FDE

一个 Agent 项目试点时，客户很想让系统自动写入 CRM。

销售团队觉得这样效率最高，IT 团队担心误写影响客户记录，安全团队要求所有写操作留痕，FDE 团队又知道评测样本还不够。

最后团队选择：试点阶段只生成建议，由销售确认后写入。

这个决定如果不记录，三个月后一定会有人问：“为什么当时不直接自动写？”

FDE 项目里的很多架构决策，不是在安静会议室里做出来的，而是在客户现场的压力下做出来的。

接口来不及开放，数据不能出域，客户要求两周内试点，安全团队不允许自动写入，业务方又希望尽快看到结果。这个时候，FDE 经常要做取舍。

问题是，如果这些取舍没有记录，项目后面很容易失忆。几个月后，没人记得为什么用了临时同步脚本，为什么没有直接写回核心系统，为什么某个 Agent 只能给建议不能自动执行。新同事接手时，只看到“现在这样做”，看不到“当时为什么这样做”。

这就是 ADR 的价值。

从定义上看，ADR，Architecture Decision Record，架构决策记录，是一种用简短文档记录关键技术和系统设计决策的方法。它不追求写全系统说明，而是记录一个具体决策的背景、备选方案、选择理由、影响、回滚条件和复审触发点。

> **一句可以带走的判断：ADR 不是补文档，而是保存关键取舍的上下文。**

## 一句话定义

ADR，Architecture Decision Record，是一种用简短文档记录关键技术和系统设计决策的方法。

在 FDE 项目里，它重点保存：当时面对什么约束、有哪些备选、为什么这样选、带来什么影响、什么时候需要复审。

## ADR 在现场项目里的作用

FDE 项目比普通研发更需要 ADR，原因有三个。

第一，现场约束多。很多决策不是技术最优，而是在数据、权限、时间、客户组织和合规要求之间做平衡。

第二，变化速度快。Demo、试点、生产阶段的目标不同，同一个方案在不同阶段可能要调整。

第三，责任边界复杂。客户业务、客户 IT、FDE、产品、平台、安全都可能参与判断，如果不记录，后面很难复查责任。

ADR 能让团队回答：

- 当时面对的问题是什么？
- 有哪些备选方案？
- 为什么选择这个方案？
- 牺牲了什么？
- 什么情况下要复审？
- 如果失败，怎么回滚？

## 哪些决策必须写 ADR

不是所有小决定都要写 ADR。FDE 项目里，以下几类决策建议必须记录：

| 决策类型 | 示例 |
| --- | --- |
| 数据流向 | 数据是否出域，是否复制到中间库 |
| 权限边界 | Agent 能否自动写入业务系统 |
| 模型选择 | 使用通用模型、私有模型还是规则系统 |
| 系统集成 | 直连核心系统还是通过中间层 |
| 评测方式 | 用人工评审、样本回放还是线上指标 |
| 回滚策略 | 失败时降级到人工、旧流程还是只读模式 |
| 产品化路径 | 现场定制是否沉淀为平台能力 |

判断标准很简单：如果这个决定未来出问题会让团队问“当初为什么这么做”，那就应该写 ADR。

## ADR 应该写什么

一个轻量 ADR 可以包含六个部分：

| 模块 | 内容 |
| --- | --- |
| 背景 | 当前业务场景、约束和问题 |
| 决策 | 最终选择了什么方案 |
| 备选方案 | 还考虑过哪些方案 |
| 取舍理由 | 为什么选它，牺牲了什么 |
| 影响范围 | 对数据、权限、成本、用户、运维的影响 |
| 复审和回滚 | 什么情况下重新评估，如何退回 |

不需要写成长篇论文。好的 ADR 应该让三个月后的接手者用 5 分钟理解关键背景。

## 一个例子：Agent 是否允许自动写入 CRM

背景：销售团队希望 Agent 根据客户互动记录，自动更新 CRM 的跟进状态。

备选方案：

| 方案 | 优点 | 风险 |
| --- | --- | --- |
| Agent 自动写入 | 效率最高 | 错误写入影响销售记录，责任不清 |
| Agent 生成建议，销售确认后写入 | 风险可控 | 多一步人工确认 |
| Agent 只生成摘要，不写入 | 最安全 | 对流程效率改善有限 |

决策：试点阶段采用“Agent 生成建议，销售确认后写入”。

理由：当前评测样本不足，CRM 数据影响销售管理和客户关系，不适合直接自动写入。先用人工确认收集修改率和失败样本，后续再评估是否开放部分自动写入。

复审触发：连续两周建议采纳率超过 85%，错误率低于 2%，且销售运营确认异常处理流程后，可以重新评估自动写入特定字段。

这就是一个典型 FDE ADR。它没有把问题复杂化，反而让后续团队知道：现在的保守设计不是因为技术做不到，而是因为生产责任还没准备好。

## ADR 和产品反哺

ADR 还有一个容易被忽略的价值：帮助产品团队理解现场模式。

如果多个客户都在同一类决策上遇到类似约束，比如都不允许 Agent 自动写入核心系统，都需要审批后执行，那这就不只是项目问题，而可能是平台能力机会。

产品团队可以据此抽象出：

- 工具权限分级。
- 人工审批节点。
- 可回放执行记录。
- 只读、建议、审批后写入、自动写入四档能力。

没有 ADR，这些现场经验很容易散掉；有了 ADR，FDE 才能把一次现场取舍变成产品学习。

## ADR 模板

```markdown
## 决策标题

### 背景
当前场景、问题、约束是什么？

### 决策
我们选择什么方案？

### 备选方案
还考虑过哪些方案？为什么没有选？

### 取舍理由
这个方案解决了什么，牺牲了什么？

### 影响范围
影响哪些系统、角色、数据、权限、成本或运维流程？

### 复审触发
什么条件下需要重新评估？

### 回滚方式
如果失败，如何退回或降级？
```

FDE 项目的很多关键价值，不在最后写出来的代码里，而在那些被正确记录、复查和沉淀的判断里。
