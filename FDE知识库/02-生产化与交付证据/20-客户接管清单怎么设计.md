# 客户接管清单怎么设计

FDE 项目真正交付完成，不是 FDE 团队能运行系统，而是客户组织能运行系统。

这句话听起来简单，但很多项目会在这里出问题。系统上线时大家都很兴奋，FDE 团队也还在旁边支持，所以问题不明显。一旦项目团队撤出，客户才发现：没人知道告警怎么看，没人知道失败样本在哪里，没人知道下一次改 Prompt 要不要重新测，也没人敢决定什么时候回滚。

这不是培训没做好，而是接管没有设计好。

从定义上看，客户接管清单是一套用于验证客户组织是否具备持续运行、复查、调整和演进系统能力的检查工具。它不是功能验收表，也不是培训签到表，而是责任转移前的能力确认。

> **一句可以带走的判断：交付完成不是客户会用，而是客户能接住系统的日常运行和异常责任。**

## 接管和培训不是一回事

培训解决的是“会不会操作”。

接管解决的是“能不能负责”。

两者差别很大。

| 培训关注 | 接管关注 |
| --- | --- |
| 功能怎么用 | 系统为什么这样设计 |
| 页面怎么点 | 异常怎么判断 |
| 正常流程怎么走 | 失败时怎么降级 |
| 用户怎么提交反馈 | 谁负责处理反馈 |
| 文档在哪里 | 下一次变更怎么复查 |

如果客户只学会了正常使用，却不知道系统边界、风险和运行机制，就还没有真正接管。

## 客户 Owner 需要能解释什么

每个生产系统都需要业务 Owner。

业务 Owner 不一定懂全部技术细节，但必须能解释系统为什么存在、服务哪条流程、成功标准是什么、哪些情况不能自动处理。

接管清单里，业务 Owner 至少要能回答：

- 这个系统解决的真实业务问题是什么？
- 使用对象是谁？
- 哪些场景适用，哪些场景不适用？
- 成功指标是什么？
- 出现争议结果时，谁有最终判断权？
- 哪些问题要反馈给产品或 FDE？

如果业务 Owner 只能说“这是一个 AI 工具”，那说明接管还不够。

## 平台/SRE 需要能操作什么

平台或 SRE 团队关注的是运行。

他们要能看懂系统状态，处理常见异常，并在必要时降级或回滚。

| 能力 | 检查问题 |
| --- | --- |
| 状态观察 | 能否看到请求量、失败率、延迟、成本 |
| 日志排查 | 能否定位某次异常请求 |
| Trace 回放 | 能否看到模型、检索、工具调用链路 |
| 告警响应 | 是否知道每类告警怎么处理 |
| 降级回滚 | 是否能切回人工流程或旧版本 |
| 变更管理 | Prompt、知识库、模型变更是否有流程 |

AI 系统的运维不只看服务是否在线，还要看质量是否稳定、成本是否异常、权限是否安全。

## 安全/合规需要能复查什么

如果系统涉及数据、权限、模型输出或工具调用，安全和合规不能只在上线前看一次。

接管时要确认：

- 数据来源和用途是否记录清楚。
- 权限模型是否可复查。
- 敏感信息是否脱敏或过滤。
- Agent 工具调用是否有审计。
- 高风险场景是否保留人工确认。
- 日志保存周期是否符合要求。
- 事故复查材料是否可导出。

尤其在企业 AI 项目中，合规不是最后盖章，而是持续运行的一部分。

## 业务用户需要能反馈什么

一线用户是系统质量的早期传感器。

他们未必能解释架构，但他们最早知道输出是否有用、哪里不符合工作习惯、哪些答案看似正确但不能用。

接管清单要设计反馈入口：

- 错误输出如何标记。
- 好用样本如何沉淀。
- 需要转人工的场景如何记录。
- 用户修改内容是否能回流评测集。
- 高频反馈由谁定期复盘。

没有用户反馈，AI 系统很难持续变好。

## 接管演练怎么做

接管不能只靠会议确认。

最好做一次或多次演练。演练不需要很复杂，但要覆盖真实风险。

| 演练场景 | 要验证 |
| --- | --- |
| 服务不可用 | 告警是否触发，谁响应，如何降级 |
| AI 回答质量下降 | 是否能回放样本，暂停能力，修复后复测 |
| 权限异常 | 是否能追踪访问记录，安全团队是否介入 |
| Agent 错误写入 | 是否能回滚，是否通知业务 Owner |
| 用户集中反馈不好用 | 是否有收集、分类和优先级机制 |

演练结束后，要留下记录：发生了什么、谁处理、耗时多久、哪里卡住、下一步补什么。

## 客户接管清单模板

| 模块 | 检查项 | 是否完成 |
| --- | --- | --- |
| 业务理解 | 业务 Owner 能说明问题、目标、边界 |  |
| 使用范围 | 适用场景和不适用场景已明确 |  |
| 数据权限 | 数据来源、权限、脱敏和审计已确认 |  |
| 质量评测 | 评测集、回放机制和失败样本已交付 |  |
| 可观测性 | 指标、日志、Trace 和成本可查看 |  |
| 告警响应 | 每类告警有 Owner 和处理动作 |  |
| 降级回滚 | 有降级方案和回滚演练记录 |  |
| 用户反馈 | 有反馈入口和定期复盘机制 |  |
| 变更流程 | Prompt、模型、知识库、工具变更有复查要求 |  |
| 后续演进 | 开放风险和产品反哺事项已记录 |  |

## 开放风险和后续行动项

接管不是要求所有风险都消失。

更现实的做法是，把开放风险写清楚：

| 风险 | 当前处理 | 后续动作 |
| --- | --- | --- |
| 某类复杂问题仍需人工判断 | 强制转人工 | 收集样本后再评估自动化 |
| 知识库更新依赖业务团队 | 每周同步 | 建立知识责任人机制 |
| Agent 暂不允许自动写入 | 人工确认后执行 | 观察采纳率和错误率 |

成熟的交付不是没有风险，而是风险被看见、被分级、被分配给具体 Owner。

## 最后的判断

客户接管清单的本质，是把 FDE 项目的责任从个人能力转成组织能力。

如果系统只有 FDE 能解释、能修、能判断，那它还停留在项目状态；如果客户业务、平台、安全和一线用户都知道自己该做什么，它才开始变成可持续能力。

AI 时代会让很多系统看起来更聪明，但真正决定它能不能长期存在的，仍然是组织能不能接住它。
