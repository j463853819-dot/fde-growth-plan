# 12-工程底座与工具生态

这个扩展专题用来补上 FDE 教材里最容易被忽略的一层：系统为什么能稳定运行，工具为什么能支撑交付，数据为什么能被业务真正使用。

FDE 不是只会做 Demo 的角色。越接近生产，越需要理解工程底座：数据集成、语义层、运行环境、CI/CD、可观测性、安全合规、SLO、事件响应和平台工程。

> **一句可以带走的判断：工具链解决“怎么做得快”，工程底座解决“做完以后能不能被组织长期依赖”。**

## 一句话定义

工程底座，是让 FDE 项目从原型、试点走向生产、接管和复用的一组基础能力。

它包括数据、运行环境、发布回滚、可观测性、安全合规、SLO、事件响应和平台化工具。

FDE 不一定要亲自建设所有底座，但必须能判断：这些能力是否存在，缺口在哪里，谁负责补齐，缺口不补会带来什么生产风险。

## 一、为什么要单独补工程底座

现有知识库已经覆盖工具链、Agent、评测、SLO 和接管，但这些内容分散在不同章节里。作为教材使用时，需要有一个更完整的工程底座入口，帮助读者把这些能力串起来。

工程底座不是让每个 FDE 都变成平台工程师，而是让 FDE 在现场判断：

- 这个系统依赖哪些数据源？
- 数据有没有统一语义和业务口径？
- 原型能不能进入客户真实环境？
- 谁能发布、回滚、观测和响应故障？
- 权限、日志、审计和合规边界在哪里？
- 客户接管后，系统是否还能持续运行？

## 三、怎么使用这一章

这一章更像工程底座地图，不适合当工具清单死记。

建议在三个时刻使用：

| 时刻 | 要问的问题 |
| --- | --- |
| Demo 后进入试点前 | 数据、权限、评测和回滚是否已经具备 |
| 试点进入生产前 | 发布、观测、告警、SLO 和安全责任是否清楚 |
| 客户接管前 | 客户是否知道系统如何运行、如何变更、如何应急 |

如果这些问题答不上来，说明项目还没有真正具备生产底座。

## 四、Ontology 与数据工程

Ontology 不是把数据库画成知识图谱，而是把客户业务中的对象、关系和动作统一起来，让系统既能理解业务，也能改变业务状态。

可以用三步法理解：

| 步骤 | 要做什么 | FDE 关注点 |
| --- | --- | --- |
| 定义实体 | 找出业务对象，如客户、订单、设备、工单、风险事件 | 对象是否是客户真实工作语言 |
| 编织关联 | 建立对象之间的关系，如订单属于客户、设备产生告警 | 关系是否能解释业务动作 |
| 赋予行动 | 让系统不只展示数据，还能触发审批、派单、提醒、回写 | 动作权限、审计和回滚是否清楚 |

### Write-back 机制

很多数据系统只负责“看数据”，但 FDE 项目经常需要“改业务”。Write-back 指系统把判断、建议、状态或动作写回业务系统。

这会带来更高价值，也带来更高责任：

- 谁允许系统写回？
- 写回前是否需要人工确认？
- 写错后如何撤回？
- 写回记录如何审计？
- 写回结果如何进入后续评测？

### 语义层与数据产品

语义层解决的是“大家是不是在说同一种业务语言”。比如“有效客户”“逾期风险”“设备异常”“高价值工单”，如果业务、数据、工程口径不同，AI 系统只会放大混乱。

FDE 可以把语义层沉淀成数据产品：

- 指标口径。
- 实体定义。
- 关系模型。
- 权限边界。
- 查询和行动接口。
- 业务词汇表。

### 领域语言包

领域语言包是客户和工程团队之间的翻译表。它不只是术语表，还应该包括：

- 业务对象。
- 常见状态。
- 关键动作。
- 例外情况。
- 指标解释。
- 禁用词和高风险表达。

它能减少 FDE、客户、一线用户、工程师和 AI 系统之间的误解。

## 五、工程底座知识地图

```text
工程底座
├── 数据层
│   ├── 数据集成：API、数据库、文件、消息队列
│   ├── 语义层：指标口径、实体关系、业务词汇表
│   └── Write-back：系统不只读数据，还能改变业务状态
├── 应用层
│   ├── RAG、Agent、工作流、权限控制
│   ├── Prompt、工具调用、状态管理
│   └── 人机协同边界
├── 交付层
│   ├── CI/CD、灰度发布、回滚机制
│   ├── 环境隔离、配置管理、版本管理
│   └── 验收门禁和接管清单
├── 运行层
│   ├── Logs、Metrics、Traces
│   ├── SLO、告警、值班、事件响应
│   └── 成本、延迟、稳定性和容量
└── 治理层
    ├── 权限、审计、数据主权
    ├── 安全合规、供应链风险
    └── 资产清单和责任边界
```

## 六、工程底座五件事

| 模块 | 关键能力 | 典型工具或方法 |
| --- | --- | --- |
| 云原生运行环境 | 容器、Kubernetes、GitOps、环境隔离 | Docker、Kubernetes、Argo CD |
| CI/CD 与自动化测试 | 持续集成、持续交付、回归测试 | GitHub Actions、GitLab CI、测试流水线 |
| 可观测性 | Logs、Metrics、Traces、成本和延迟 | OpenTelemetry、Prometheus、Grafana |
| 安全与合规 | 零信任、数据主权、供应链安全、审计 | IAM、密钥管理、权限矩阵 |
| SLO 与事件响应 | 服务目标、告警、值班、事故复盘 | SLO 卡、告警规则、事件响应手册 |

FDE 不一定要亲自建设完整平台，但必须知道这些能力是否存在、由谁负责、上线前缺哪一块。

## 七、工程底座检查卡

| 检查项 | 要确认什么 | 如果缺失 |
| --- | --- | --- |
| 数据来源 | 数据从哪里来，口径是否一致，谁维护 | AI 会放大错误口径 |
| 权限边界 | 谁能读、谁能写、谁能审批 | 上线后容易出现合规风险 |
| 运行环境 | 开发、试点、生产是否隔离 | Demo 配置可能误进生产 |
| 发布回滚 | 如何发布、灰度、回退 | 出问题只能临时救火 |
| 可观测性 | 日志、指标、trace、成本是否可看 | 故障无法定位 |
| SLO 和告警 | 什么时候算坏了，谁响应 | 系统变差但没人处理 |
| AI 资产 | Prompt、知识库、模型、工具是否有版本 | 输出变化无法追踪 |
| 接管机制 | 客户是否能操作、复查和应急 | FDE 长期被锁死 |

这张卡可以和生产准入门禁矩阵、AI 资产清单、SLO 定义卡、客户接管清单一起使用。

## 八、工具与生态地图

| 类别 | 代表工具 | FDE 要判断什么 |
| --- | --- | --- |
| 数据集成 | Airbyte、Dagster、dbt | 数据是否稳定、可追溯、口径一致 |
| Agent 框架 | LangGraph、LlamaIndex、Temporal | 状态、工具调用、重试和人工接管能否管理 |
| 评测与监控 | MLflow、OpenTelemetry、Evidently | 质量、漂移、失败样本和运行成本能否观测 |
| 平台工程 | Backstage、Internal Developer Platform | 一次性交付能否变成组织可复用能力 |

工具只是入口，真正要沉淀的是标准化交付路径。

FDE 不需要把自己变成平台工程师。
