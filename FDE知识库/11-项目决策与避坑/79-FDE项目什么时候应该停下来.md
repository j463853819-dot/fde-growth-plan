# FDE 项目什么时候应该停下来

FDE 不是永远往前推。

一个成熟的 FDE，要知道什么时候继续、什么时候缩小范围、什么时候转向、什么时候停止。项目停下来并不总是失败，有时候是避免更大浪费。

> **FDE 的专业性，不只在推进项目，也在及时识别项目不该继续。**

## 一句话定义

FDE 项目应该停下来，是指当前项目继续推进无法增加有效证据，只会扩大成本、范围、风险或误判。

停下来不是放弃。

它是重新对齐事实、约束和价值。

## 应该停下来的信号

| 信号 | 为什么危险 |
| --- | --- |
| 没有业务 Owner | 系统没人接管 |
| 成功标准说不清 | 无法验收和续费 |
| 数据长期不可获得 | Demo 无法进入真实流程 |
| 权限风险不可接受 | 上线会制造合规问题 |
| 客户只要免费探索 | 商业闭环不存在 |
| 需求不断变大 | 项目会变成无边界定制 |
| Demo 不能改变决策 | 演示只是热闹 |

## 停下来不等于放弃

停下来有三种方式：

| 方式 | 适用情况 |
| --- | --- |
| 暂停 | 缺数据、缺 Owner、缺授权 |
| 缩小 | 场景太大，但有小切口 |
| 转向 | 原需求不成立，但发现了更真实问题 |

还可以有第四种：停止。停止适用于价值、数据、Owner 和风险条件都不成立的情况。

FDE 不是为了证明自己能做，而是为了让团队做值得做的事。

## 继续、缩小、转向、停止

项目不一定只有“做”和“不做”两种选择。FDE 更应该把决策分成四类。

| 决策 | 适用情况 | 下一步 |
| --- | --- | --- |
| 继续 | 关键假设成立，证据在增加 | 扩大试点或进入生产门禁 |
| 缩小 | 大方向成立，但范围过大 | 只保留一个高频小闭环 |
| 转向 | 原需求不成立，但发现更真实问题 | 重写问题定义和成功指标 |
| 停止 | 价值、数据、Owner 或风险条件都不成立 | 留下复盘和重启条件 |

成熟的 FDE 不会把停止说成失败，而会把它说成一次基于证据的决策。

## 停止前要留下什么

即使项目暂停，也要留下：

- 已确认事实。
- 关键约束。
- 被推翻的假设。
- 不能继续的原因。
- 未来重启条件。

这能避免下一次团队从头踩同一个坑。

## 停止决策卡

| 字段 | 要写清楚什么 |
| --- | --- |
| 原始目标 | 项目最初想证明什么 |
| 已验证事实 | 哪些事实已经确认 |
| 被推翻假设 | 哪些假设不成立 |
| 主要阻塞 | 数据、Owner、权限、价值还是风险 |
| 当前决策 | 继续、缩小、转向、暂停或停止 |
| 重启条件 | 未来满足什么条件可以重启 |
| 复盘沉淀 | 哪些经验进入模板或避坑清单 |

项目停下来，也要留下可复查证据。

## 停止说明怎么写

一个好的停止说明，不应该只写“客户暂缓”。它至少要写清楚：

| 内容 | 示例 |
| --- | --- |
| 原假设 | 合同审查可以通过 AI 降低法务初审时间 |
| 当前事实 | 客户无法提供真实合同样本，风险标签无人确认 |
| 主要阻塞 | 数据授权和法务 Owner 缺失 |
| 不继续原因 | 继续优化 Prompt 不会增加生产证据 |
| 重启条件 | 提供脱敏合同样本、确认法务 Owner、定义风险分类 |

这样停下来，团队不会觉得“前功尽弃”，而是知道下一次从哪里重新开始。

## 实战拆解：合同审查 AI 什么时候该停

合同审查 AI 做完 Demo 后，客户迟迟无法提供真实合同样本。

法务 Owner 也没有明确谁来确认风险标签。

这时继续优化 Prompt 没有意义。

项目应该暂停，直到满足三个重启条件：

- 有授权合同样本。
- 有法务 Owner。
- 有明确的风险分类标准。

否则团队会一直在假数据上优化假问题。

## 可以带走的判断

如果项目继续推进只会增加功能，但不会增加证据，那就应该停下来。

FDE 的推进不是靠惯性，而是靠证据。
