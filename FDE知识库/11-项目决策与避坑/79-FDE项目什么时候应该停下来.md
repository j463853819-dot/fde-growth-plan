# FDE 项目什么时候应该停下来

FDE 不是永远往前推。

一个成熟的 FDE，要知道什么时候继续、什么时候缩小范围、什么时候转向、什么时候停止。项目停下来并不总是失败，有时候是避免更大浪费。

> **一句可以带走的判断：FDE 的专业性，不只在推进项目，也在及时识别项目不该继续。**

## 应该停下来的信号

| 信号 | 为什么危险 |
| --- | --- |
| 没有业务 Owner | 系统没人接管 |
| 成功标准说不清 | 无法验收和续费 |
| 数据长期不可获得 | Demo 无法进入真实流程 |
| 权限风险不可接受 | 上线会制造合规问题 |
| 客户只要免费探索 | 商业闭环不存在 |
| 需求不断变大 | 项目会变成无边界定制 |
| Demo 不能改变决策 | 演示只是热闹 |

## 停下来不等于放弃

停下来有三种方式：

| 方式 | 适用情况 |
| --- | --- |
| 暂停 | 缺数据、缺 Owner、缺授权 |
| 缩小 | 场景太大，但有小切口 |
| 转向 | 原需求不成立，但发现了更真实问题 |

FDE 不是为了证明自己能做，而是为了让团队做值得做的事。

## 停止前要留下什么

即使项目暂停，也要留下：

- 已确认事实。
- 关键约束。
- 被推翻的假设。
- 不能继续的原因。
- 未来重启条件。

这能避免下一次团队从头踩同一个坑。

## 一个判断句

如果项目继续推进只会增加功能，但不会增加证据，那就应该停下来。

FDE 的推进不是靠惯性，而是靠证据。
