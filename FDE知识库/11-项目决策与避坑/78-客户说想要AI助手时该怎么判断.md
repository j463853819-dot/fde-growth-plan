# 客户说想要 AI 助手时该怎么判断

“我们想做一个 AI 助手”是企业 AI 项目里最常见、也最危险的一句话。

它听起来像需求，其实往往只是一个解决方案想象。客户真正要解决的，可能是知识找不到、流程太慢、口径不一致、数据不可信、管理层想看到 AI 成果。

> **客户说想要 AI 助手时，FDE 先不要做助手，要先找它要进入哪条工作流。**

## 一句话定义

AI 助手不是需求定义，而是一种可能的产品形态。

FDE 要先判断它服务哪个岗位、进入哪条流程、读取什么输入、输出给谁确认，以及出错后有什么后果。

## 先问五个问题

1. 这个助手服务哪个岗位？
2. 它进入哪条具体流程？
3. 它读取什么输入？
4. 它输出给谁，谁确认？
5. 它出错时有什么后果？

回答不了这五个问题，就还不是一个可做需求。

## AI 助手判断卡

| 字段 | 要写清楚什么 |
| --- | --- |
| 客户原话 | 客户为什么说想要助手 |
| 真实工作流 | 助手要进入哪条流程 |
| 当前做法 | 现在谁在用什么方式处理 |
| 输入 | 需要读取哪些数据、文档或系统 |
| 输出 | 是建议、摘要、草稿、判断还是执行动作 |
| 人工确认 | 谁确认，什么场景必须转人工 |
| 风险后果 | 输出错了会造成什么影响 |
| 指标 | 如何判断助手真的有价值 |

这张卡填完后，通常会发现客户要的不是“助手”，而是某条流程里的辅助判断能力。

## 四种真实问题

| 客户说 AI 助手 | 可能真实问题 |
| --- | --- |
| 员工问不到资料 | 知识库分散、无人维护 |
| 客服回复慢 | 订单、政策、历史案例切换成本高 |
| 销售跟进差 | 线索优先级和下一步动作不清 |
| 管理层要日报 | 指标口径不统一，异常解释困难 |

AI 助手只是外壳，工作流才是核心。

## 判断是否值得做

| 判断项 | 好信号 |
| --- | --- |
| 频率 | 每天或每周高频发生 |
| 输入 | 数据、文档或记录可以获得 |
| 输出 | 能影响真实业务动作 |
| 风险 | 错误可发现、可人工兜底 |
| 指标 | 能衡量时间、质量或成本变化 |

## 把“助手”拆成六个设计问题

真正进入设计时，不要先画聊天框，而要拆六件事：

| 问题 | 要确认什么 |
| --- | --- |
| 角色 | 谁用它，是一线、主管还是客户 |
| 入口 | 它嵌在哪个系统或流程里 |
| 输入 | 它能读哪些数据、文档和历史记录 |
| 输出 | 它给建议、草稿、结论还是动作 |
| 确认 | 谁审核，什么场景必须人工确认 |
| 反馈 | 失败样本如何回流到评测和知识库 |

如果这六件事没有想清楚，聊天框越漂亮，后面越容易变成摆设。

## 三种常见落地形态

“AI 助手”不一定都长成同一种产品。

| 形态 | 适合场景 |
| --- | --- |
| 侧边栏助手 | 用户已经在业务系统里工作，需要解释和建议 |
| 流程节点助手 | 审批、工单、客服等流程中需要辅助判断 |
| 后台运营助手 | 管理者需要看异常、趋势和待处理事项 |

FDE 要帮客户选形态，而不是默认做一个独立聊天入口。很多企业 AI 助手失败，就是因为它被放在工作流之外，用户还要专门打开它。

## 好的改写方式

不要写：

“做一个 AI 助手。”

改成：

> 当客服处理退款咨询时，系统读取订单状态、退款政策和历史案例，生成建议回复和引用来源，由客服确认后发送，目标是把平均响应时间从 8 分钟降到 4 分钟以内。

这个版本才是 FDE 能推进的需求。

再进一步，它还可以变成试点定义：

| 项目要素 | 定义 |
| --- | --- |
| 用户 | 退款客服小组 20 人 |
| 范围 | 只处理标准退款咨询 |
| 输入 | 订单状态、退款政策、历史案例 |
| 输出 | 建议回复、引用来源、风险提示 |
| 兜底 | 高金额和投诉风险转人工主管 |
| 指标 | 平均响应时间、采纳率、误答率 |

## 可以带走的判断

客户说“AI 助手”，FDE 听到的应该不是助手。

而是一个尚未被定义清楚的工作流。
