# 企业 AI 项目为什么客户不续费

很多企业 AI 项目不是没有上线，而是上线后客户不续费。

原因通常不是模型完全没用，而是客户没有持续感受到价值：用户不常用，指标没变化，维护成本上升，问题没人接，系统慢慢变成一个“曾经很酷”的试点。

> **客户续费不是因为 AI 很先进，而是因为它持续改善了某个业务结果。**

## 一句话定义

客户不续费，是因为系统没有从一次性交付变成持续运营能力。

上线只是开始。

续费看的是持续采用、持续改善和持续证明价值。

## 不续费的常见原因

| 原因 | 表现 |
| --- | --- |
| 价值指标不清 | 不知道到底省了什么、赚了什么 |
| 用户采用不足 | 少数人试过，没人长期用 |
| 维护成本过高 | 知识库、Prompt、评测没人维护 |
| 质量不稳定 | 好几次答错后用户不信任 |
| 没有业务 Owner | 系统没人持续推动 |
| 没有扩场景 | 只解决一个小问题，预算难延续 |

## FDE 应该提前做什么

续费不是上线后才考虑。

在项目早期就要定义：

- 基线指标。
- 价值指标。
- 采用指标。
- 运营 Owner。
- 失败样本闭环。
- 扩场景路径。

## 续费证据包

| 证据 | 要证明什么 |
| --- | --- |
| 基线指标 | 原来有多慢、多贵、多不稳定 |
| 试点指标 | 系统是否真的改善了结果 |
| 使用数据 | 真实用户是否持续采用 |
| 失败样本闭环 | 系统是否持续变好 |
| 接管记录 | 客户是否能独立运行和复查 |
| 扩场景清单 | 后续是否还有增长空间 |
| ROI 说明 | 客户为什么值得继续付费 |

续费不是合同快到期时补一页总结，而是整个项目周期里持续积累证据。

## 续费其实从第一周开始

很多团队把续费当成商务问题，但在 FDE 项目里，续费首先是证据问题。

| 阶段 | 要为续费留下什么 |
| --- | --- |
| 项目启动 | 基线指标和价值假设 |
| Demo | 已验证假设和未验证风险 |
| 试点 | 真实用户采用数据 |
| 上线 | 运维、评测、回滚和接管证据 |
| 复盘 | ROI、扩场景路径和产品反哺 |

如果前四个阶段没有持续留下证据，合同快到期时再准备续费材料，就会非常被动。

## 续费价值证明

| 证明项 | 示例 |
| --- | --- |
| 效率改善 | 平均处理时长下降 35% |
| 质量改善 | 错误率下降 20% |
| 采用情况 | 70% 一线用户每周使用 |
| 风险控制 | 高风险场景 100% 转人工 |
| 持续优化 | 每周回放失败样本 |
| 扩张空间 | 可复制到售后、投诉、会员场景 |

客户续费需要证据，不需要更多愿景。

## 不续费前的预警信号

客户不续费通常不是突然发生的，早期会有信号：

- 业务 Owner 不再参加复盘。
- 一线用户使用频率下降。
- 失败样本没人处理。
- 知识库更新停滞。
- 客户只问“还能加什么功能”，不讨论指标。
- 采购方和使用方对价值理解不一致。

这些信号出现时，FDE 要回到价值证明，而不是继续加功能。

## 实战拆解：为什么客服 AI 第一年热闹，第二年不续

第一年上线时，客服 AI 很受关注。

但后续没人维护知识库，Prompt 改动没有回放，客服发现几次错误后开始绕开系统。

到了续费时，客户问：

“它到底带来了多少价值？”

团队拿不出持续指标。

这时再补 ROI 已经晚了。

续费要从项目第一天设计，而不是合同到期前补材料。

## 可以带走的判断

AI 项目要续费，必须从“交付项目”变成“运营能力”。

FDE 如果只负责上线，不负责价值证明和运营闭环，项目很容易热闹开场，安静结束。
