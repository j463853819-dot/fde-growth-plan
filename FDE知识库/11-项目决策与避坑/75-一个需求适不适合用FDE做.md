# 一个需求适不适合用 FDE 做

不是所有客户需求都适合用 FDE 做。

有些需求只是标准配置，有些是普通实施，有些是产品功能，有些是一次性定制。FDE 应该进入的是高不确定、高价值、需要现场验证和工程闭环的问题。

> **一句可以带走的判断：FDE 适合处理“还没被定义清楚、但一旦解决就很有价值”的问题。**

## 适合 FDE 的信号

| 信号 | 说明 |
| --- | --- |
| 问题真实但表达模糊 | 客户说不清需求，但现场痛感强 |
| 涉及多系统和多角色 | 不是单点功能能解决 |
| 需要业务和工程一起判断 | 纯产品或纯实施都接不住 |
| Demo 能验证关键假设 | 可以小步证明方向 |
| 成功后有复用可能 | 不只是一次性客户分支 |
| 结果可以衡量 | 时间、成本、质量、风险或收入能变化 |

## 不适合 FDE 的信号

| 信号 | 更适合谁做 |
| --- | --- |
| 需求已经非常清楚 | 交付/实施团队 |
| 只是界面小改动 | 产品或研发排期 |
| 完全一次性定制 | 外包或项目团队 |
| 客户没有业务 Owner | 先暂停 |
| 成功标准无法定义 | 先做问题澄清 |
| 数据和权限完全不可获得 | 先做前置治理 |

## 判断五问

1. 这个问题是否发生在真实工作流里？
2. 是否有明确受影响角色？
3. 是否需要跨业务、数据、系统和组织边界？
4. 是否能切出一个小闭环验证？
5. 成功后是否能沉淀为产品、模板或方法？

如果五个问题里只有一两个是“是”，就不要急着把它包装成 FDE 项目。

## 一个例子

客户说：“帮我们加一个导出按钮。”

这通常不是 FDE 问题。但如果继续问，发现客户真正痛点是“每周经营分析要从 5 个系统人工导出、合并、解释异常，再发给管理层”，那它就可能变成 FDE 问题。

FDE 不是去做按钮，而是重新定义“经营分析工作流”。
