# 一个需求适不适合用 FDE 做

不是所有客户需求都适合用 FDE 做。

有些需求只是标准配置，有些是普通实施，有些是产品功能，有些是一次性定制。FDE 应该进入的是高不确定、高价值、需要现场验证和工程闭环的问题。

> **FDE 适合处理“还没被定义清楚、但一旦解决就很有价值”的问题。**

## 一句话定义

适合 FDE 的需求，通常不是一个清楚功能，而是一个真实工作流里的复杂问题：现场痛感强、边界不清、涉及多角色多系统，需要通过工程验证逐步收敛。

## 适合 FDE 的信号

| 信号 | 说明 |
| --- | --- |
| 问题真实但表达模糊 | 客户说不清需求，但现场痛感强 |
| 涉及多系统和多角色 | 不是单点功能能解决 |
| 需要业务和工程一起判断 | 纯产品或纯实施都接不住 |
| Demo 能验证关键假设 | 可以小步证明方向 |
| 成功后有复用可能 | 不只是一次性客户分支 |
| 结果可以衡量 | 时间、成本、质量、风险或收入能变化 |

## 不适合 FDE 的信号

| 信号 | 更适合谁做 |
| --- | --- |
| 需求已经非常清楚 | 交付/实施团队 |
| 只是界面小改动 | 产品或研发排期 |
| 完全一次性定制 | 外包或项目团队 |
| 客户没有业务 Owner | 先暂停 |
| 成功标准无法定义 | 先做问题澄清 |
| 数据和权限完全不可获得 | 先做前置治理 |

## 判断五问

1. 这个问题是否发生在真实工作流里？
2. 是否有明确受影响角色？
3. 是否需要跨业务、数据、系统和组织边界？
4. 是否能切出一个小闭环验证？
5. 成功后是否能沉淀为产品、模板或方法？

如果五个问题里只有一两个是“是”，就不要急着把它包装成 FDE 项目。

## FDE 需求决策卡

| 字段 | 要写清楚什么 |
| --- | --- |
| 原始需求 | 客户最初怎么说 |
| 真实问题 | 现场里真正卡住的流程是什么 |
| 目标角色 | 谁受影响，谁会使用 |
| 价值指标 | 时间、成本、质量、风险或收入怎么变化 |
| 工程不确定性 | 数据、系统、权限、模型能力哪里不确定 |
| 最小验证闭环 | 第一版只验证哪一段 |
| 复用可能 | 成功后能沉淀成什么 |
| 决策 | FDE 进入 / 产品排期 / 实施交付 / 商务定制 / 暂停 |

这张卡的价值，是防止团队只因为“听起来复杂”就让 FDE 进入。

## 三类容易误判的需求

FDE 最容易被卷进去的，不是明显的小需求，而是那些看起来“有点复杂、有点 AI、有点战略”的需求。

| 需求类型 | 为什么容易误判 | 更好的处理 |
| --- | --- | --- |
| 老板指定的 AI 项目 | 战略压力大，没人敢说不适合 | 先拆成一个可验证业务闭环 |
| 客户口头很兴奋 | 会议反馈热烈，但没有 Owner | 要求客户指定流程 Owner 和试点人群 |
| 技术上很有趣 | 工程团队想挑战，但业务价值弱 | 先定义指标，不然只做技术实验 |

判断需求适不适合 FDE，不是看它够不够复杂，而是看它是否值得用现场勘探和工程验证去降低不确定性。

## 一个简单分流表

拿到需求后，可以先做分流：

| 判断结果 | 去向 |
| --- | --- |
| 需求清楚、边界稳定 | 交付或实施 |
| 多个客户反复出现 | 产品路线图 |
| 一次性深度定制 | 商务单独报价 |
| 问题真实但方案不清 | FDE 进入 |
| 数据、权限、Owner 都缺 | 暂停，先补前置条件 |

FDE 进入前，最好能写出一句项目定义：

```text
为哪个角色，在什么流程里，解决什么瓶颈，用什么最小闭环验证，成功后沉淀为什么能力。
```

写不出这句话，说明需求还没有被定义清楚。

## 实战拆解：导出按钮是不是 FDE 需求

客户说：“帮我们加一个导出按钮。”

这通常不是 FDE 问题。

但如果继续问，发现客户真正痛点是“每周经营分析要从 5 个系统人工导出、合并、解释异常，再发给管理层”，那它就可能变成 FDE 问题。

FDE 不是去做按钮。

FDE 要重新定义“经营分析工作流”：

- 数据从哪里来。
- 谁解释异常。
- 哪些指标口径不一致。
- 报告影响哪个管理决策。
- 能否先做一个异常归因切片。

这时候，原本的“导出按钮”可以被改写成：

> 每周经营会前，系统自动汇总订单、库存、履约和退款数据，识别异常指标并生成归因草稿，由运营负责人确认后进入会议材料，目标是把经营分析准备时间从 2 天降到半天。

这个版本才值得 FDE 介入，因为它有角色、有流程、有输入、有指标，也有后续产品化可能。

## 可以带走的判断

FDE 不是用来承接所有复杂需求的万能口袋。

它应该被用在那些“值得深入现场、值得工程验证、值得沉淀复用”的问题上。
