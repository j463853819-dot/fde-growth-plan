# 老板、产品、工程和销售分别应该怎么看 FDE

同一个 FDE 项目，在公司内部经常会被四种语言同时描述。

老板说：“这个东西能不能变成增长能力？”

产品说：“这些客户需求到底要不要进路线图？”

工程说：“这个原型以后谁维护？出了事故谁兜底？”

销售说：“客户下周就要看效果，能不能先做一个？”

每个人都没有错，但如果没有共同语言，FDE 就会被拉成四份：一会儿像战略项目，一会儿像产品调研，一会儿像工程救火，一会儿像免费售前。最后项目看起来很忙，组织却没有形成真正的 AI 落地能力。

> **一句可以带走的判断：FDE 是组织协作位置，不是某个部门的万能补丁。**

## 先定义：FDE 在组织里的位置

FDE 不是“谁缺人就补到哪里”的角色，而是把客户现场、业务价值、工程系统和产品沉淀连起来的转换层。

它的工作不是替老板做战略、替产品排需求、替工程写全部代码、替销售承诺结果，而是让这些角色基于同一组事实做判断：

| 共同事实 | 要回答的问题 |
| --- | --- |
| 客户真实流程 | 这个场景到底是不是刚需 |
| 业务瓶颈 | 做成以后改变哪个指标 |
| 技术约束 | 原型能不能进入生产 |
| 交付证据 | 客户为什么愿意继续投入 |
| 复用机会 | 这个项目能不能反哺产品 |

所以，FDE 的组织价值不是“多做几个项目”，而是减少内部角色之间的信息损耗。

## 老板怎么看

老板看 FDE，重点不是看它是不是“高级工程师”，而是看它能不能把 AI 从试点推进到收入、续费和战略客户关系。

老板应该问：

- FDE 是否能提升大客户成功率？
- 是否能把 AI 试点推进到采购、扩容或续费？
- 是否能沉淀行业能力？
- 是否能让公司更快理解一个行业的真实需求？
- 是否会变成高成本外包？

老板不该只看“FDE 做了多少项目”，而要看四个结果：

| 结果 | 说明 |
| --- | --- |
| 收入推进 | 是否带来成交、扩容、续费或更高客单价 |
| 复用沉淀 | 是否把一次项目变成模板、组件或行业方案 |
| 战略洞察 | 是否发现产品路线图看不见的现场问题 |
| 成本控制 | 是否避免长期人肉交付和无限定制 |

老板最容易犯的错，是把 FDE 当成“高配外包团队”。短期看项目推进快，长期看毛利、复用和组织学习都会被拖垮。

## 产品怎么看

产品看 FDE，重点不是“客户又提了什么需求”，而是“哪些现场事实值得进入产品系统”。

产品应该问：

- 现场需求里哪些是共性？
- 哪些应该进入产品路线？
- 哪些只是配置或项目定制？
- FDE 是否带回了失败样本和真实用法？
- 用户实际怎么绕过现有产品？

产品不能把 FDE 当成需求收集员。FDE 带回来的不是“客户想要什么”，而是“现场真实流程如何工作”。

一个典型例子是客户说“我要一个 AI 助手”。产品如果直接记成“新增助手功能”，就会误判。FDE 要带回来的可能是另一组事实：

- 客户真正痛的是审批材料反复补正。
- 一线员工不会主动打开新系统。
- 主管只关心异常件和超时件。
- 现有知识库缺少版本和责任人。

这些事实最后可能不会变成“AI 助手”，而会变成“材料校验、异常分流、知识库治理、审批状态追踪”的产品能力。

## 工程怎么看

工程看 FDE，重点不是“这个东西是不是代码写得优雅”，而是“它是否正在制造未来的系统债务”。

工程应该问：

- FDE 做的东西是否符合系统边界？
- 哪些原型能进入生产？
- 哪些临时方案必须重构？
- 权限、评测、SLO 和回滚是否清楚？
- 数据、日志、审计和安全责任是否明确？

工程不能只抱怨 FDE 做得粗，也不能让所有现场问题都绕过平台。

FDE 原型允许快，但不能模糊生产边界。一个健康的工程协作方式是：

| 阶段 | 工程应关注 |
| --- | --- |
| Demo | 数据是否脱敏，是否避免危险权限 |
| 试点 | 是否有评测集、灰度范围和人工兜底 |
| 生产 | 是否接入监控、告警、审计和回滚 |
| 复用 | 是否抽象成平台能力，而不是复制粘贴 |

工程和 FDE 的关系不该是“你快我慢”，而是“你验证现场，我保证系统可持续”。

## 销售怎么看

销售看 FDE，重点不是“有没有人帮我做 Demo”，而是“能不能把客户兴趣推进成可信购买理由”。

销售应该问：

- FDE 是否帮助客户看见真实价值？
- Demo 是否能推进采购决策？
- 试点结果是否能支撑合同？
- 哪些承诺不能随便说？
- 哪些客户其实不适合继续投入？

销售不能把 FDE 当成免费售前，也不能把所有客户想法都包装成可交付承诺。

FDE 对销售最大的帮助，不是让 Demo 更炫，而是让销售更早知道三件事：

1. 这个客户有没有真实场景。
2. 这个场景有没有可衡量价值。
3. 这个项目有没有可交付边界。

如果 FDE 判断客户只是“想看看 AI 能做什么”，销售就应该降低承诺，把它当成教育型机会，而不是马上包装成大项目。

## 共同语言

最好的 FDE 协作，不是每个部门都觉得自己赢了，而是所有人都接受同一套项目事实。

| 角色 | 最该关注 | 最不该做 |
| --- | --- |
| 老板 | 收入、复用、战略客户 | 只按项目数量考核 |
| 产品 | 共性需求、路线图、模板 | 把客户原话当产品需求 |
| 工程 | 生产边界、质量、平台能力 | 把现场问题一概拒绝 |
| 销售 | 价值证明、采购推进、风险承诺 | 用 Demo 替代交付承诺 |
| FDE | 现场事实、工程验证、业务结果 | 变成无边界救火队 |

## 一套简单的协作节奏

FDE 项目进入组织后，可以用四个会议节点减少拉扯：

| 节点 | 参与角色 | 产出 |
| --- | --- | --- |
| 场景筛选 | 销售、FDE、产品 | 是否值得做、价值假设、拒绝理由 |
| 方案评审 | FDE、工程、产品 | 技术边界、数据约束、风险清单 |
| 试点复盘 | FDE、销售、客户成功 | 指标变化、客户反馈、下一步采购路径 |
| 产品反哺 | 产品、工程、FDE | 模板、组件、路线图建议 |

这套节奏的核心不是增加流程，而是避免所有人靠感觉推动项目。

## 最后判断

一个组织真的理解 FDE，不是因为它设了一个新岗位，而是因为老板、产品、工程和销售开始用同一张事实表讨论 AI 项目。

FDE 要站在这些角色之间，但不能替代任何一个角色。它最重要的能力，是把“客户想要”“业务值得”“工程能做”“产品可复用”“销售能成交”这五件事放到同一张桌子上。
