# 什么样的 AI 项目不该做 Agent

Agent 很诱人，但不是所有 AI 项目都该做 Agent。

很多场景只需要检索、分类、生成建议或工作流自动化。如果一上来就做 Agent，反而会增加权限、评测、成本和责任风险。

> **一句可以带走的判断：只有当任务需要多步决策、工具调用和状态管理时，Agent 才值得引入。**

## 不该做 Agent 的场景

| 场景 | 更合适的方案 |
| --- | --- |
| 只需要回答知识库问题 | RAG 问答 |
| 只需要生成固定格式内容 | Prompt 模板 |
| 规则非常明确 | 规则引擎或工作流 |
| 输出必须 100% 可控 | 人工审核 + 系统辅助 |
| 数据权限还不清楚 | 先做数据治理 |
| 没有评测和 trace 能力 | 先补生产控制面 |

Agent 不是越早越好。

## 适合 Agent 的场景

| 条件 | 说明 |
| --- | --- |
| 任务多步 | 需要计划、执行、观察和调整 |
| 需要调用工具 | 不是只生成文本 |
| 状态会变化 | 需要根据中间结果继续行动 |
| 可以定义权限 | Agent 能做什么边界清楚 |
| 可以回放评测 | 能追踪它每一步 |
| 有人工接管 | 高风险场景不会自动乱跑 |

## 判断问题

在做 Agent 前，先问：

- 它需要调用哪些工具？
- 每个工具是只读、建议、审批后写入还是自动写入？
- 它最多能执行多少步？
- 什么时候必须停下来问人？
- 出错后如何回滚？
- 如何评测它不是“看起来完成了”？

如果这些问题说不清，先不要做 Agent。

## 一个反例

客户想做“合同审查 Agent”。

如果当前任务只是识别合同中的高风险条款，并给出引用来源，那 RAG + Prompt + 人工确认就够了。只有当系统需要自动查历史合同、匹配供应商信息、生成修改建议、发起审批、记录法务意见时，才开始接近 Agent。

不要为了显得先进，把一个可控任务做成不可控系统。
