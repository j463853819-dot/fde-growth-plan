# 什么样的 AI 项目不该做 Agent

Agent 很诱人，但不是所有 AI 项目都该做 Agent。

很多场景只需要检索、分类、生成建议或工作流自动化。如果一上来就做 Agent，反而会增加权限、评测、成本和责任风险。

> **只有当任务需要多步决策、工具调用和状态管理时，Agent 才值得引入。**

## 一句话定义

不该做 Agent 的 AI 项目，是那些任务边界清楚、动作简单、输出可模板化，或者生产控制面尚未准备好的项目。

这类项目更适合用 RAG、Prompt、规则引擎或普通工作流解决。

## 不该做 Agent 的场景

| 场景 | 更合适的方案 |
| --- | --- |
| 只需要回答知识库问题 | RAG 问答 |
| 只需要生成固定格式内容 | Prompt 模板 |
| 规则非常明确 | 规则引擎或工作流 |
| 输出必须 100% 可控 | 人工审核 + 系统辅助 |
| 数据权限还不清楚 | 先做数据治理 |
| 没有评测和 trace 能力 | 先补生产控制面 |

Agent 不是越早越好。

Agent 是在系统已经准备好承接行动风险之后，再逐步放开的能力。

## 适合 Agent 的场景

| 条件 | 说明 |
| --- | --- |
| 任务多步 | 需要计划、执行、观察和调整 |
| 需要调用工具 | 不是只生成文本 |
| 状态会变化 | 需要根据中间结果继续行动 |
| 可以定义权限 | Agent 能做什么边界清楚 |
| 可以回放评测 | 能追踪它每一步 |
| 有人工接管 | 高风险场景不会自动乱跑 |

## 做 Agent 前的六个问题

- 它需要调用哪些工具？
- 每个工具是只读、建议、审批后写入还是自动写入？
- 它最多能执行多少步？
- 什么时候必须停下来问人？
- 出错后如何回滚？
- 如何评测它不是“看起来完成了”？

如果这些问题说不清，先不要做 Agent。

## Agent 的四级放权

很多项目失败，是因为一开始就把 Agent 当成“自动执行者”。更稳的做法，是分级放权。

| 级别 | Agent 能做什么 | 适合阶段 |
| --- | --- | --- |
| L1 只读 | 查询信息，不改变业务状态 | Demo 和早期试点 |
| L2 建议 | 生成建议或草稿，不直接执行 | 低风险生产 |
| L3 审批后写入 | 人确认后调用工具写入系统 | 稳定试点 |
| L4 自动执行 | 在低风险边界内自主执行 | 高成熟场景 |

大多数企业 AI 项目，前两级已经能产生价值。不要因为“Agent”这个词很热，就跳过权限、评测和人工确认。

## 三个硬门槛

如果一个项目要进入 Agent 形态，至少要有三类基础设施：

| 门槛 | 缺失后果 |
| --- | --- |
| 工具权限边界 | Agent 不知道什么能做、什么不能做 |
| Trace 和回放 | 出错后无法解释哪一步错了 |
| 人工接管机制 | 高风险场景无法及时刹车 |

没有这些能力，Agent 的“聪明”会变成生产风险。

## Agent 决策卡

| 字段 | 要写清楚什么 |
| --- | --- |
| 当前任务 | 是问答、生成、分类、工作流，还是多步行动 |
| 必要工具 | Agent 需要调用哪些系统或接口 |
| 权限等级 | 每个工具是 L1、L2、L3 还是 L4 |
| 停止条件 | 什么时候必须停下来问人 |
| 回放能力 | 是否能追踪每一步调用 |
| 失败后果 | 错误会影响谁，是否可回滚 |
| 替代方案 | RAG、规则、工作流是否足够 |
| 决策 | 不做 Agent / L1-L2 试点 / L3 试点 / L4 谨慎放权 |

如果这张卡填不出来，就先不要做 Agent。

## 实战拆解：合同审查一定要 Agent 吗

客户想做“合同审查 Agent”。

如果当前任务只是识别合同中的高风险条款，并给出引用来源，那 RAG + Prompt + 人工确认就够了。

只有当系统需要自动查历史合同、匹配供应商信息、生成修改建议、发起审批、记录法务意见时，才开始接近 Agent。

即使到了这一步，也可以先停在 L2 或 L3：

- AI 生成风险摘要和修改建议。
- 法务确认后生成修订稿。
- 审批通过后再写入合同系统。
- 所有工具调用都保留日志。

这样既保留 Agent 的效率，也不把责任直接交给模型。

不要为了显得先进，把一个可控任务做成不可控系统。

## 可以带走的判断

Agent 不是 AI 项目的起点。

它是权限、评测、工具层和人工接管都逐步成熟之后的下一步。
