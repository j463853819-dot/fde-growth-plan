# 第一个 FDE 项目应该选什么场景

第一个 FDE 项目不要选最宏大的场景。

很多团队一开始就想做企业级 AI 中台、全流程 Agent、管理驾驶舱或智能运营大脑。愿景很大，但失败概率也高。第一个项目更应该选小而真实、可验证、可接管的场景。

> **第一个 FDE 项目，不要证明你能做多大，要证明你能把一个真实闭环做成。**

## 一句话定义

第一个 FDE 项目应该是高频、痛感明确、输入可得、风险可控、指标清楚、客户能接管的小闭环。

它不是战略终局。

它是训练组织信任 FDE 方法的第一块样板。

## 好场景的标准

| 标准 | 说明 |
| --- | --- |
| 高频 | 不是偶发问题 |
| 痛感明确 | 用户真的受影响 |
| 输入可得 | 数据或文档能拿到 |
| 风险可控 | 出错能人工兜底 |
| 指标清楚 | 能衡量改善 |
| 接管简单 | 客户能理解和维护 |

## 适合作为第一个项目的场景

| 场景 | 为什么适合 |
| --- | --- |
| 客服建议回复 | 高频、指标清楚、可人工确认 |
| 销售线索摘要 | 输入明确、价值容易感知 |
| 会议纪要到行动项 | 风险低、反馈快 |
| 知识库问答加引用 | 容易验证检索质量 |
| 工单分类和分流 | 结果可衡量 |
| 日报异常解释 | 有业务价值，但要控制范围 |

## 不建议作为第一个项目

| 场景 | 风险 |
| --- | --- |
| 全自动审批 | 责任太重 |
| 企业级 AI 中台 | 范围太大 |
| 全流程无人 Agent | 权限和回滚复杂 |
| 高风险医疗/金融决策 | 评测和合规门槛高 |
| 多部门综合驾驶舱 | 指标口径容易失控 |

## 选择公式

```text
高频 + 可控风险 + 明确指标 + 可人工确认 + 可扩展
```

做成第一个小闭环，比讲清一个宏大蓝图更有价值。

## 第一个项目的评分表

如果团队拿不准，可以给候选场景打分。每项 1 到 5 分，低于 20 分的场景不建议作为第一个项目。

| 维度 | 评分问题 |
| --- | --- |
| 频率 | 这个问题是否高频发生 |
| 痛感 | 用户是否真的愿意改变现有做法 |
| 数据 | 输入数据是否容易获得且质量可接受 |
| 风险 | 出错后是否能人工兜底 |
| 指标 | 是否能在 2-4 周内看到变化 |
| 复用 | 成功后是否能复制到相邻场景 |

这张表不是为了精确打分，而是逼团队不要只按“听起来高级”选项目。

## 第一个项目选择卡

| 字段 | 要写清楚什么 |
| --- | --- |
| 候选场景 | 具体场景名称 |
| 目标角色 | 谁会真实使用 |
| 触发频率 | 每天、每周还是偶发 |
| 输入条件 | 数据、文档和系统是否可获得 |
| 风险边界 | 出错后能否人工兜底 |
| 2-4 周指标 | 短期能看到什么变化 |
| 接管难度 | 客户是否能理解、维护和复查 |
| 扩展路径 | 成功后能扩到哪些相邻场景 |

第一个项目选得好，后面不是只多一个案例，而是多一套组织信心。

## 三个不要碰的诱惑

第一个 FDE 项目最容易被三个诱惑带偏：

| 诱惑 | 问题 |
| --- | --- |
| 选老板最关心的大场景 | 关注度高，但组织协调成本也高 |
| 选技术最酷的 Agent | 容易忽略数据、权限和流程 |
| 选客户最会夸的 Demo | 掌声多，但未必能进入真实工作 |

第一个项目要追求的是“可验证的胜利”，不是“最完整的愿景”。

## 实战拆解：为什么客服退款咨询适合做第一单

客服退款咨询常常适合做第一个 FDE 项目，因为：

- 高频发生。
- 响应时间可量化。
- 有明确用户。
- 可以人工确认。
- 高风险场景能转人工。
- 后续能扩展到物流、售后、会员权益。

它不一定最宏大，但很容易证明 FDE 的完整路径：Context、Design、Engineer、Feedback。

## 可以带走的判断

第一个项目最重要的不是炫技。

是建立信任：FDE 方法真的能把一个现场问题做成可运行、可验证、可接管的系统。
