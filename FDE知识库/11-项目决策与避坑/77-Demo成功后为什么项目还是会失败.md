# Demo 成功后为什么项目还是会失败

很多 AI/FDE 项目不是死在 Demo 前，而是死在 Demo 后。

Demo 成功会制造一种乐观错觉：既然已经能跑，那项目应该快上线了。现实往往相反。Demo 之后，数据、权限、流程、评测、成本、责任和接管问题才真正出现。

> **Demo 成功只证明方向可能对，不证明组织已经准备好接住它。**

## 一句话定义

Demo 后失败，是指项目在演示阶段验证了可能性，但没有补齐试点和生产所需的真实数据、权限边界、评测标准、工作流入口、Owner 和接管机制。

## 常见失败原因

| 原因 | 表现 |
| --- | --- |
| 数据不可持续 | Demo 用样例数据，生产数据接不上 |
| 权限没设计 | 真实用户看不到该看的，或看到不该看的 |
| 没有评测标准 | 大家觉得不错，但不知道能不能上线 |
| 不进入工作流 | 用户还要多开一个工具 |
| 没有 Owner | 出问题后没人负责 |
| 客户无法接管 | 系统只能靠 FDE 团队维护 |
| ROI 不清楚 | 客户看完热闹，但不愿继续付费 |

## Demo 后要立刻做什么

Demo 成功后，不要急着扩功能。

先补四件事：

1. 写清楚 Demo 验证了什么。
2. 写清楚 Demo 绕过了什么。
3. 定义试点范围和成功指标。
4. 列出进入生产前必须补的证据。

## Demo 复盘卡

| 字段 | 要写清楚什么 |
| --- | --- |
| Demo 验证了什么 | 哪个关键假设成立 |
| Demo 没验证什么 | 哪些生产条件被绕过 |
| 使用的数据 | 样例数据、脱敏数据还是真实数据 |
| 用户反馈 | 谁试过，反馈是什么 |
| 失败样本 | 哪些样本表现不好 |
| 下一步范围 | 试点用户、数据、场景边界 |
| 进入试点条件 | 数据、权限、Owner、评测是否满足 |
| 停止或缩小条件 | 哪些证据不成立就不继续 |

Demo 复盘卡的重点，是把会议上的兴奋转成下一阶段门禁。

## Demo 到试点的证据清单

Demo 成功后，FDE 应该把“热情”翻译成“下一阶段证据”。

| 问题 | 需要补的证据 |
| --- | --- |
| 数据能不能持续供给 | 真实数据样本、更新频率、字段质量 |
| 谁会真实使用 | 试点用户名单、使用频率、流程入口 |
| 效果怎么判断 | 评测集、基线指标、人工复核标准 |
| 出错怎么办 | 转人工规则、回滚方案、责任人 |
| 谁接住系统 | 客户 Owner、运维手册、培训计划 |

这张表比“下周继续优化”更重要。因为它能判断项目是真的进入试点，还是只是继续做更好看的演示。

## 三个关键问题

- 用户是否愿意在真实流程里使用？
- 系统输出是否能被评测和追责？
- 客户组织是否有人愿意接管？

如果这三个问题没有答案，Demo 越成功，后面的失望越大。

## Demo 复盘要写清楚什么

一次合格的 Demo 复盘，至少要包含四句话：

1. 这次 Demo 验证了什么假设。
2. 这次 Demo 没有验证什么假设。
3. 下一步试点最小范围是什么。
4. 如果试点失败，最可能失败在哪里。

很多团队只写第一句，所以会误以为“能跑”就是“能上线”。FDE 的专业性，恰恰在于把第二句和第四句讲清楚。

## 实战拆解：为什么销售助手 Demo 后卡住

销售助手 Demo 能生成客户跟进建议，业务方看完很满意。

但试点前发现：

- CRM 字段大量为空。
- 销售不信任优先级判断。
- 推荐结果不能反写系统。
- 采纳率没人统计。
- 销售主管没有时间复盘失败样本。

这说明 Demo 只验证了“能生成建议”。

没有验证“建议能进入销售流程”。

这时下一步不应该是继续加功能，而是缩小成一个试点：

- 只选一个销售团队。
- 只处理最近 30 天有互动记录的线索。
- 只输出下一步跟进建议。
- 销售确认后再写回 CRM。
- 每周复盘采纳率和成交推进率。

如果这个闭环跑不起来，做再多“智能推荐”也没有意义。

## 可以带走的判断

Demo 不是项目完成的信号，而是项目进入下一阶段的证据。

FDE 要做的，不是让客户鼓掌，而是让客户和团队一起看清：哪些假设成立了，哪些风险还没解决，下一步该试点、缩小还是停止。
