# 金融行业 FDE 案例

金融行业是 FDE 最典型、也最难的场景之一。

它不是没有数字化基础，恰恰相反，金融系统很多、数据很多、流程也成熟。真正难的是合规、权限、审计和风险责任极重，AI 不能只是“看起来聪明”，必须可解释、可追溯、可控制。

> **金融 FDE 的第一原则不是自动化，而是可控地提升判断效率。**

## 一句话定义

金融 FDE 项目，是把 AI 或数据能力部署到风控、投研、客服、合规、信贷、运营等高约束流程中，并在合规边界内证明效率和风险收益。

这类项目最忌讳一上来追求“全自动决策”。

更稳的路径，通常是先做证据组织、风险摘要、人工复核和审计留痕。

## 实战拆解：信贷审批风险摘要助手

一家金融机构想做“信贷审批 Agent”。

业务方的说法很直接：客户材料越来越多，风控人员查资料、写审批意见很耗时，希望 AI 自动生成审批建议。

如果团队直接按这个需求做，很容易做成一个风险很高的系统：AI 自动读取资料，生成“建议通过/拒绝”的结论。

但 FDE 进入现场后，应该先把问题改写。

真实切口不是“自动审批”，而是：

> 在风控人员审批前，系统能否把客户材料、征信摘要、流水异常、合同要点和历史相似案例组织成一份带来源的风险摘要，帮助风控更快进入判断？

这个切口更小，但更安全。

## 旧流程

信贷审批辅助的旧流程可能是：

- 客户经理收集资料。
- 风控人员查征信、流水、合同和历史记录。
- 多个系统之间切换。
- 人工写审批意见。
- 合规或上级复核。

效率低，但每一步都有责任边界。

金融项目不能轻易打破这些边界。

FDE 要做的是先把证据组织好，而不是替人承担最终判断。

## 现场发现

客户口头需求是“信贷审批 Agent”。

现场发现往往是另一回事：

| 发现 | 含义 |
| --- | --- |
| 材料分散 | 风控大量时间花在查找和整理 |
| 审批意见格式不一致 | 质量依赖个人经验 |
| 风险点遗漏 | 人工阅读材料容易漏细节 |
| 高风险客户必须人工判断 | AI 不能直接给最终审批结论 |
| 审计要求严格 | 每次查询、引用和输出都要留痕 |

所以第一个价值切口不应该是全自动审批。

应该是“风险摘要和证据引用助手”。

## 数据和系统约束

| 约束 | 影响 |
| --- | --- |
| 数据不出域 | 需要私有化或内网部署 |
| 权限分级严格 | 不同角色看到不同字段 |
| 审计要求高 | 每次查询和输出要留痕 |
| 错误成本高 | 高风险场景必须人工确认 |
| 监管和模型风险 | 模型输出不能伪装成人类判断 |

金融项目里，权限和审计不是后补项，而是方案设计的一部分。

## 方案设计

更稳妥的方案：

- AI 只读取授权范围内资料。
- 生成风险摘要、证据引用和待确认问题。
- 给出风险标签，但不直接审批。
- 高风险或低置信度场景转人工。
- 所有输入、检索、输出保留 trace。
- 风控人员的修改进入失败样本库。

这个方案的价值，不是让 AI 取代风控。

而是让风控少花时间找材料，多花时间做判断。

## 生产门禁

| 阶段 | 门禁 |
| --- | --- |
| Demo | 能否正确引用政策、材料和历史样本 |
| 试点 | 风控人员是否采纳，错误是否可发现 |
| 生产 | 权限、审计、评测、回滚、SLO 完成 |
| 接管 | 风控、IT、安全能共同复查系统 |

金融场景里，试点范围要非常克制。

可以先选一个信贷产品、一类客户、一组风控人员，而不是一上来覆盖所有审批流程。

## 指标

| 指标 | 说明 |
| --- | --- |
| 材料整理时间 | 风控人员进入判断前的准备时间是否下降 |
| 风险点覆盖率 | 是否减少遗漏 |
| 审批意见一致性 | 输出结构是否更稳定 |
| 人工修改率 | 风控是否需要大量改写摘要 |
| 越权访问 | 必须为零 |

## 可复用经验

金融 FDE 最值得沉淀的，不是某个模型。

而是这些能力：

- 权限分级和字段脱敏。
- 风险摘要模板。
- 证据引用和审计 trace。
- 高风险人工复核机制。
- 模型输出的评测和回放。

## 可以带走的判断

金融 FDE 的价值，不是让 AI 替代风控。

是让风控拥有更好的证据组织、更稳定的判断辅助和更可追溯的决策过程。

如果把这个案例抽象成 FDE 方法，它的关键动作是：先把“自动审批”降级成“证据组织”，再用权限、审计、评测和人工复核守住生产边界。
