# 政务行业 FDE 案例

政务行业的 FDE，经常不是技术问题最难，而是责任链最难。

政务场景强调流程合规、政策口径、数据安全、信创适配和可追溯。一个系统能不能用，不只取决于功能，还取决于它是否符合组织规则，是否能被审计，是否能解释给多个部门。

> **政务 FDE 的关键不是做得多聪明，而是让系统在公共责任链里站得住。**

## 一句话定义

政务 FDE 项目，是把 AI 和工作流能力部署到政策匹配、材料审核、热线问答、审批辅助、基层治理等公共服务流程中，并确保口径、责任和审计可控。

政务 AI 的目标不是制造一个无所不答的机器人。

而是让公共服务里的信息流动更清楚、更稳定、更可追溯。

## 实战拆解：政策匹配助手

一个部门想做“政策问答机器人”。

表面需求很清楚：企业或居民问政策，AI 快速回答，减少窗口人员压力。

但 FDE 进入现场后，很快会发现问题没这么简单。

政策不是一份静态文档。它有版本，有适用条件，有不同部门的解释口径，也有“能不能承诺”的边界。

所以第一个切口不应该是开放式问答，而是：

> 当工作人员处理企业政策咨询时，系统基于最新政策文件和已确认口径，生成匹配建议、适用条件和来源引用，由工作人员确认后回复。

## 旧流程

以政策匹配为例：

- 企业或居民提交诉求。
- 工作人员查政策库。
- 人工判断适配条件。
- 多部门确认口径。
- 形成回复或办理建议。

痛点不是没有政策。

而是政策多、口径变、跨部门判断慢。

## 现场发现

客户可能说：“我们要一个政策问答机器人。”

FDE 进一步拆解后可能发现：

| 发现 | 影响 |
| --- | --- |
| 政策文件版本多 | 必须做版本管理 |
| 不同部门口径不完全一致 | 输出前要有确认机制 |
| 适用条件复杂 | 不能只做语义问答 |
| 错误回复有公共服务风险 | 高风险问题必须转人工 |
| 信创和内网要求 | 工具链和部署方式受限制 |

政务项目里，答案“像对”不够。

它必须能解释来源、适用条件和责任边界。

## 约束

| 约束 | 影响 |
| --- | --- |
| 信创环境 | 部署和工具链要适配国产化 |
| 数据分级 | 不同部门权限不同 |
| 口径一致 | 输出必须引用来源 |
| 审计留痕 | 每次推荐和修改要记录 |
| 多部门协同 | Owner 不能只落在技术部门 |

## 方案设计

稳妥方案：

- 建立政策知识库和版本管理。
- AI 输出必须附政策来源和适用条件。
- 复杂或争议问题转人工。
- 建立口径更新流程。
- 记录每次问答和人工修改。
- 对高频问题沉淀标准回复模板。

这不是一个单纯的问答系统。

它更像一个政策口径工作台。

## 生产路径

| 阶段 | 重点 |
| --- | --- |
| Demo | 验证政策检索和引用 |
| 试点 | 在一个窗口或一个政策领域使用 |
| 生产 | 完成权限、审计、版本和告警 |
| 接管 | 业务处室负责口径，信息化团队负责运行 |

试点要尽量选边界清楚的政策领域。

不要一开始覆盖所有政策咨询。

## 指标

| 指标 | 说明 |
| --- | --- |
| 政策匹配时间 | 工作人员查找政策的时间是否下降 |
| 引用准确率 | 是否引用正确版本 |
| 人工修改率 | 输出是否被认可 |
| 争议转人工率 | 高风险问题是否被拦住 |
| 口径更新时效 | 新政策是否及时进入系统 |

## 可复用经验

政务 FDE 最值得沉淀的是：

- 政策知识版本管理。
- 口径确认流程。
- 多部门 Owner 机制。
- 信创和私有化部署清单。
- 高风险问题转人工规则。

## 可以带走的判断

政务 FDE 不是把 AI 做得更会回答。

是让每一次回答都能追溯来源、解释边界、找到责任人。

公共服务场景里，可信比聪明更重要。

这个案例的可迁移经验是：凡是涉及公共责任链的 AI 项目，都要先设计版本、口径、审计和转人工，而不是先追求开放式问答能力。
