# 政务行业 FDE 案例

政务行业的 FDE，经常不是技术问题最难，而是责任链最难。

政务场景强调流程合规、政策口径、数据安全、信创适配和可追溯。一个系统能不能用，不只取决于功能，还取决于它是否符合组织规则，是否能被审计，是否能解释给多个部门。

从定义上看，政务 FDE 项目是把 AI 和工作流能力部署到政策匹配、材料审核、热线问答、审批辅助、基层治理等公共服务流程中，并确保口径、责任和审计可控。

> **一句可以带走的判断：政务 FDE 的关键不是做得多聪明，而是让系统在公共责任链里站得住。**

## 旧流程

以政策匹配为例：

- 企业或居民提交诉求。
- 工作人员查政策库。
- 人工判断适配条件。
- 多部门确认口径。
- 形成回复或办理建议。

痛点不是没有政策，而是政策多、口径变、跨部门判断慢。

## 现场发现

客户可能说：“我们要一个政策问答机器人。”

FDE 进一步拆解后可能发现：

- 政策文件版本多。
- 不同部门解释口径不完全一致。
- 政策适用条件复杂。
- 错误回复会带来公共服务风险。

第一个切口不应是开放式问答，而是“政策匹配建议 + 来源引用 + 人工确认”。

## 约束

| 约束 | 影响 |
| --- | --- |
| 信创环境 | 部署和工具链要适配国产化 |
| 数据分级 | 不同部门权限不同 |
| 口径一致 | 输出必须引用来源 |
| 审计留痕 | 每次推荐和修改要记录 |

## 方案设计

稳妥方案：

- 建立政策知识库和版本管理。
- AI 输出必须附政策来源和适用条件。
- 复杂或争议问题转人工。
- 建立口径更新流程。
- 记录每次问答和人工修改。

## 生产路径

| 阶段 | 重点 |
| --- | --- |
| Demo | 验证政策检索和引用 |
| 试点 | 在一个窗口或一个政策领域使用 |
| 生产 | 完成权限、审计、版本和告警 |
| 接管 | 业务处室负责口径，信息化团队负责运行 |

## 可复用经验

政务 FDE 最值得沉淀的是：

- 政策知识版本管理。
- 口径确认流程。
- 多部门 Owner 机制。
- 信创和私有化部署清单。
- 高风险问题转人工规则。

政务 AI 的目标不是制造一个无所不答的机器人，而是让公共服务里的信息流动更清楚、更稳定、更可追溯。
