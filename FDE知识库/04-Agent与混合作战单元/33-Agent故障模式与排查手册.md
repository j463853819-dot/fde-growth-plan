# Agent 故障模式与排查手册

Agent 出问题时，表面现象常常很迷惑。

用户看到的是“它答错了”“它没执行”“它乱调用工具”。但真正原因可能在目标理解、Prompt、检索、工具 schema、权限、状态机、模型版本、成本限流或业务规则变更。

从定义上看，Agent 故障排查是对 Agent 的输入、计划、工具调用、状态转移、输出和业务结果进行分层诊断的过程。它不是只看最后一句回答，而是回放整条执行链。

> **一句可以带走的判断：排查 Agent 故障，不能只看答案，要看它为什么走到这个答案。**

## 常见故障模式

| 故障 | 表现 | 常见原因 |
| --- | --- | --- |
| 目标误解 | 做了不该做的任务 | 任务描述不清、上下文缺失 |
| 工具误选 | 调错接口 | 工具描述相似、选择规则不清 |
| 参数错误 | 接口调用失败 | schema 不完整、字段映射错误 |
| 权限越界 | 读取或写入不该访问的数据 | 身份继承和权限过滤缺失 |
| 循环执行 | 不断重试 | 终止条件不清 |
| 静默失败 | 看似完成但结果不可用 | 缺少业务校验 |
| 成本暴涨 | 调用次数异常 | 多 Agent 循环或大上下文滥用 |

## 排查顺序

不要一上来就改 Prompt。

建议按这个顺序排查：

1. 任务输入是否清楚。
2. Agent 计划是否合理。
3. 是否选对工具。
4. 工具参数是否正确。
5. 权限和数据是否符合预期。
6. 中间结果是否被正确观察。
7. 是否触发重试、降级或人工接管。
8. 最终输出是否通过业务标准。

很多问题不是模型“笨”，而是工具、状态或约束没有设计好。

## 必须保留 Trace

没有 trace，Agent 故障很难排查。

最小 trace 应该包括：

- 用户输入。
- 系统上下文。
- 计划步骤。
- 工具选择理由。
- 工具调用参数。
- 工具返回结果。
- 重试和降级记录。
- 最终输出。
- 用户反馈。

Trace 不是为了事后甩锅，而是为了让系统能学习。

## 故障分级

| 等级 | 示例 | 处理 |
| --- | --- | --- |
| P0 | 越权写入、错误执行高风险动作 | 立即停用、回滚、事故复查 |
| P1 | 大量任务失败或质量明显下降 | 降级、修复、回放评测 |
| P2 | 局部场景效果差 | 收集样本、优化 Prompt 或工具 |
| P3 | 体验问题 | 排期优化 |

Agent 进入生产后，故障分级要提前定义。

## 快速排查表

| 问题 | 先看什么 |
| --- | --- |
| 答案不准 | 检索结果、引用来源、业务规则 |
| 调错工具 | 工具描述、工具选择日志 |
| 参数错误 | schema、字段映射、样例 |
| 重复执行 | 状态机、最大步数、终止条件 |
| 成本异常 | 调用次数、上下文长度、循环链路 |
| 用户不采纳 | 修改记录、反馈标签、场景适配 |

Agent 故障排查的目标，不是把某一次错误修掉，而是把错误变成评测样本、规则改进或产品能力。
