# 单人加多 Agent 协作模式

一个合同审查助手项目，往往同时有几条工作线在跑：

一边要整理客户访谈和合同样本，一边要生成方案备选，一边要做 RAG 原型，一边还要构建评测集、写 ADR、准备试点说明。

这时候如果还是一个 Agent 全干，很快就会乱。

当一个 FDE 面对的任务变复杂，单 Agent 很快不够用。

一个 Agent 同时做调研、写代码、评测、文档和复盘，容易上下文混乱，也很难追踪责任。更好的方式，是把不同任务拆给不同 Agent，让它们各自承担明确角色。

从定义上看，单人加多 Agent 模式是指一个 FDE 作为总负责人，协调多个专职 Agent 完成现场分析、方案设计、开发、测试、评测、文档和运营等任务。它的本质不是“多开几个机器人”，而是建立一套小型人机协作组织。

> **一句可以带走的判断：多 Agent 协作的关键不是数量，而是分工、边界和复核链。**

## 一句话定义

单人加多 Agent 模式，是指一个 FDE 作为总负责人，协调多个专职 Agent 完成现场分析、方案设计、开发、测试、评测、文档和运营等任务。

它的本质不是“多开几个机器人”，而是建立一套小型人机协作组织。

## 常见 Agent 分工

| Agent | 主要职责 |
| --- | --- |
| Context Agent | 整理访谈、流程、角色和约束 |
| Design Agent | 生成方案备选、风险清单和切片草案 |
| Dev Agent | 生成代码、脚本和集成样例 |
| Eval Agent | 构造评测样本、回放失败案例 |
| Doc Agent | 生成 ADR、运行手册、接管材料 |
| Ops Agent | 汇总日志、指标、告警和用户反馈 |

FDE 不是把工作甩给它们，而是负责目标、优先级和最终判断。

## 多 Agent 为什么会出问题

多 Agent 协作的风险也更高。

| 风险 | 表现 |
| --- | --- |
| 上下文不一致 | 每个 Agent 对目标理解不同 |
| 重复劳动 | 多个 Agent 生成相似内容 |
| 错误传播 | 一个 Agent 的错误被另一个继续放大 |
| 责任不清 | 出错后不知道哪个环节出了问题 |
| 成本失控 | 多 Agent 循环调用和重复推理 |

所以多 Agent 系统必须有状态、日志和任务边界。

## FDE 如何当指挥官

FDE 在多 Agent 模式里要做四件事：

1. 定义任务拆分：哪些任务并行，哪些任务必须串行。
2. 维护事实源：所有 Agent 使用同一份事实约束表和项目上下文。
3. 设计复核点：关键输出必须由人或评测 Agent 检查。
4. 控制权限：只有特定 Agent 能读写特定系统。

多 Agent 不是为了让 FDE 少负责，而是让 FDE 从执行者变成指挥者。

## 一个工作流例子

客户要做“合同审查助手”。

| 步骤 | Agent 参与 |
| --- | --- |
| 整理客户访谈和合同样本 | Context Agent |
| 生成三种方案路径 | Design Agent |
| 构建 RAG 原型 | Dev Agent |
| 生成合同风险评测集 | Eval Agent |
| 写 ADR 和试点说明 | Doc Agent |
| 上线后汇总失败样本 | Ops Agent |

FDE 负责判断：先做哪类合同，哪些条款必须人工确认，什么标准才算进入试点。

## 实战拆解：合同审查助手为什么需要多 Agent

回到开头那个合同审查助手项目。

如果只有一个 Agent，它很容易出现这些问题：

- 上下文太长，角色混乱。
- 既要做方案，又要写代码，还要评测，输出风格不稳定。
- 一个错误判断被后续步骤不断放大。

而拆成多 Agent 之后，链路会清楚很多：

- `Context Agent` 只管整理访谈和合同样本。
- `Design Agent` 只管生成方案备选和风险清单。
- `Dev Agent` 只管原型和集成样例。
- `Eval Agent` 只管评测集和失败样本回放。

FDE 自己不再亲自做完所有执行，而是更像一个小型交付单元的指挥官。

## 最后判断

多 Agent 协作的价值，不在于“机器人更多”，而在于分工更清楚。

如果没有共享事实源、任务边界、复核链和权限控制，多 Agent 只会把混乱放大。FDE 在这里的角色不是放手不管，而是做小型交付组织的设计者：谁负责 Context，谁负责 Design，谁负责 Dev，谁负责 Eval，谁的输出必须被人确认。
