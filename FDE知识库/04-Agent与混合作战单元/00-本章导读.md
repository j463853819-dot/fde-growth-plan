# 04-Agent 与混合作战单元

这个专题解释 AI Agent 如何改变 FDE 的工作方式，以及人和 Agent 如何形成混合作战单元。

这里不只讲趋势，也不把 Agent 写成万能自动化。真正重要的是：Agent 进入生产之后，权限、评测、trace、成本、人工接管和回滚如何设计。

> **一句可以带走的判断：Agent 不是让 FDE 消失，而是把 FDE 的工作从亲自执行，推向设计人机协同系统。**

## AI 原生 FDE

AI 原生 FDE 不是“会用大模型工具”的 FDE，而是能把 LLM 能力嵌入真实业务流程，并让它通过评测、观测、权限和接管进入生产。

可以按四层理解：

| 层级 | 核心问题 | FDE 要留下什么 |
| --- | --- | --- |
| Prompt | 如何把任务、上下文、约束和输出格式说清楚 | Prompt 模板、版本记录、失败样本 |
| RAG | 如何让模型引用可信知识和业务数据 | 知识源清单、召回评测、引用证据 |
| Agent | 如何让系统调用工具、执行动作、保留状态 | 工具权限、状态机、审计日志、人工接管 |
| Workflow | 如何让 AI 嵌入业务流程，而不是停在聊天框 | 触发条件、责任边界、回滚方式 |

## Evals 优先

AI 项目不能等上线后才问“效果怎么样”。FDE 要在设计和工程阶段就建立评测。

- 先定义高频场景和高风险场景。
- 再收集真实样本、失败样本和边界样本。
- 然后设计离线评测、人工复核和线上监控。
- 最后把评测结果变成上线门禁，而不是演示材料。

Evals 优先的意思是：先知道系统怎么被判断，再决定系统怎么被构建。

## LLMOps

LLMOps 的重点不是多一个运维名词，而是让 AI 系统的关键变量可追踪、可回滚、可复盘。

| 版本对象 | 为什么要管 |
| --- | --- |
| 模型版本 | 模型升级可能改变输出质量、成本和延迟 |
| Prompt 版本 | 提示词变化会影响稳定性和责任边界 |
| 数据版本 | 知识库、样本集和业务数据变化会影响结果 |
| 工具版本 | Agent 工具能力变化会影响权限和行动风险 |
| 评测版本 | 评测集变化会影响上线判断 |

## 人机协同边界

AI 原生 FDE 最重要的判断，不是“哪些事情 AI 能做”，而是“哪些事情应该交给 AI，哪些必须留给人”。

| 适合交给 AI | 应该留给人 |
| --- | --- |
| 检索、归纳、草稿、分类、低风险建议 | 高风险审批、价值判断、责任确认、异常兜底 |
| 重复性强、规则相对稳定的任务 | 规则不清、责任不明、后果严重的任务 |
| 可评测、可回放、可撤销的动作 | 不可逆、强合规、强伦理风险的动作 |

## 实战使用方式

读这一章时，不要只问“Agent 能不能帮我做更多事”，而要同步回答四个问题：

| 问题 | 对应产物 |
| --- | --- |
| Agent 负责哪类任务 | 任务边界和分工表 |
| Agent 能调用哪些工具 | 工具权限分级表 |
| Agent 出错怎么发现 | Trace、评测集、告警 |
| Agent 什么时候必须交给人 | 人工确认点和接管条件 |

Agent 越强，越需要边界。FDE 的价值不在于盲目放权，而在于把人、模型、工具和责任组织成一个可运行的系统。
