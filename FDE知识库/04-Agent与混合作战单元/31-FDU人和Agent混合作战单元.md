# FDU：人和 Agent 混合作战单元

FDU 可以理解为 FDE 在 Agent 时代的一种升级形态。

过去，一个 FDE 主要依靠个人能力进入现场、拆问题、写代码、推试点。现在，FDE 可以带着一组 Agent 工作：有人负责判断，有 Agent 负责执行，有系统负责记录和回放，有客户团队负责接管。

从定义上看，FDU，Forward Deployed Unit，是由 FDE、人类业务/工程伙伴和多个 Agent 组成的混合作战单元。它不是单个人，也不是纯自动化系统，而是一种面向真实现场的协同交付形态。

> **一句可以带走的判断：FDU 的本质，是把 FDE 的个人能力组织化，把 Agent 的执行能力纳入责任边界。**

## FDU 由什么组成

一个最小 FDU 可以包括：

| 角色 | 责任 |
| --- | --- |
| FDE Lead | 现场判断、方案取舍、交付责任 |
| 业务 Owner | 定义目标、确认价值、接管流程 |
| 工程/平台伙伴 | 系统集成、权限、运行支持 |
| Context Agent | 资料整理和现场分析 |
| Dev Agent | 原型和工程辅助 |
| Eval Agent | 样本、评测和回放 |
| Ops Agent | 指标、告警、反馈和复盘 |

FDU 的重点不是角色越多越好，而是每个角色都有清晰责任。

## FDU 适合什么项目

FDU 适合高不确定、高反馈、高交付压力的项目。

| 项目特征 | 是否适合 FDU |
| --- | --- |
| 数据和系统复杂 | 适合 |
| 需要快速原型 | 适合 |
| 涉及 AI/Agent 生产化 | 适合 |
| 只有一次性配置任务 | 不一定适合 |
| 需求非常稳定 | 不一定需要 |

FDU 的价值，在于处理边界模糊和任务密集的现场。

## FDU 的工作方式

FDU 不应该变成“人类开会，Agent 写材料”。

更好的工作方式是：

- 现场材料进入统一事实库。
- Agent 对材料做结构化处理。
- FDE 进行问题定义和方案取舍。
- 工程 Agent 和人类工程师共同做原型。
- Eval Agent 持续构造评测和回放。
- Ops Agent 汇总运行数据和失败样本。
- 客户 Owner 逐步接管责任。

这是一条从现场到生产的协同链。

## FDU 的风险

FDU 如果设计不好，也会制造混乱。

| 风险 | 防护 |
| --- | --- |
| Agent 输出无人负责 | FDE 保留最终判断权 |
| 工具权限过宽 | 权限分级和审批 |
| 信息源混乱 | 建立统一项目事实库 |
| 成本不可控 | 限流、预算和调用日志 |
| 客户无法接管 | 早期引入客户 Owner |

FDU 越强，越需要清楚的治理。

## FDU 成熟度

| 阶段 | 表现 |
| --- | --- |
| 初级 | FDE 用 Agent 做个人效率增强 |
| 中级 | 多 Agent 分工处理项目任务 |
| 高级 | Agent 进入评测、运营和接管流程 |
| 成熟 | FDU 形成可复制交付单元 |

FDU 的终点不是炫耀自动化，而是让 FDE 项目的交付能力可以规模化。

未来真正稀缺的，不是“会用很多 Agent 的人”，而是能把人、Agent、客户组织和生产责任编排成一个可运行单元的人。
