# 当机器学会写代码，FDE 还剩下什么

一个客户说想做“自动生成经营日报”的系统。

现在的 AI Coding 工具，确实能很快写出页面、接口、Prompt 和导出功能。单看编码速度，很多过去要几天的活，现在几个小时就能做个七七八八。

但项目继续往前推时，真正卡住的还是老问题：哪些数据可信，哪些指标口径会变，哪些结论不能自动写进管理层日报，谁来对异常解释负责。

AI Coding 越强，FDE 越容易被问一个问题：如果机器会写代码，FDE 还重要吗？

这个问题看似在问职业替代，其实在问软件交付的本质。代码只是 FDE 工作的一部分，不是全部。FDE 真正稀缺的能力，是把真实问题定义清楚，把系统放进组织流程，把结果变成可运行、可接管、可复用的能力。

从定义上看，AI Coding 主要替代的是代码生成、修改、测试和局部工程实现。FDE 面对的是更大的系统：业务现场、客户组织、权限数据、生产责任和产品反哺。

> **一句可以带走的判断：机器会写代码以后，FDE 的价值从“写出系统”转向“判断什么系统值得写，以及如何让它进入组织”。**

## 一句话定义

AI Coding 主要替代的是代码生成、修改、测试和局部工程实现。

FDE 面对的是更大的系统：业务现场、客户组织、权限数据、生产责任和产品反哺。

## 哪些能力会被压缩

AI 会让一些执行型能力变便宜。

| 能力 | 变化 |
| --- | --- |
| 脚手架代码 | 更快生成 |
| 简单接口 | 更快实现 |
| 文档初稿 | 更快整理 |
| 测试样例 | 更快补齐 |
| 数据处理脚本 | 更快构建 |

这不意味着这些能力不重要，而是它们不再足以构成 FDE 的核心壁垒。

## 哪些能力会更贵

AI 越强，下面这些能力越贵：

| 能力 | 为什么更重要 |
| --- | --- |
| 问题定义 | AI 很容易把错误问题做得很快 |
| 现场判断 | 组织里的隐性规则不在代码里 |
| 方案取舍 | 速度、风险、成本和价值要平衡 |
| 生产治理 | AI 系统需要评测、权限、trace 和回滚 |
| 客户接管 | 系统最终要被组织持续运行 |

未来 FDE 的分水岭，不是“会不会写代码”，而是“能不能把 AI 写出来的东西变成可靠业务能力”。

## 一个例子

客户说：“帮我们做一个自动生成报告的系统。”

AI Coding 可以很快写出：

- 数据读取脚本。
- 报告生成页面。
- Prompt 模板。
- 导出功能。

但 FDE 仍然要判断：

- 报告真正服务哪个决策？
- 数据口径是否可信？
- 谁确认异常原因？
- 哪些内容不能自动生成？
- 输出错误会造成什么后果？
- 上线后谁维护指标和 Prompt？

这些问题不是代码生成问题，而是现场工程问题。

## FDE 的新分工

AI 时代，FDE 更像一个混合系统设计者。

它要决定：

- 哪些任务交给人。
- 哪些任务交给 Agent。
- 哪些任务必须人机协同。
- 哪些动作必须审批。
- 哪些结果必须回放评测。

FDE 不会因为 AI 会写代码而消失。相反，当写代码变快，定义问题、组织协作和生产责任会变得更关键。

## 最后的判断

如果一个 FDE 的价值只在“我比客户会写代码”，那确实会被 AI 挤压。

但如果他的价值在“我能进入现场、定义问题、设计系统边界、组织人机协同、让客户接管能力”，AI 反而会放大他的作用。

机器学会写代码之后，FDE 剩下的不是更少，而是更接近本质。

---

## 实战拆解：日报系统为什么不是“代码写完”就结束

回到开头那个经营日报系统。

AI 可以很快写出：

- 数据读取脚本。
- 报告生成页面。
- Prompt 模板。
- 导出和邮件发送。

但 FDE 仍然要回答另一组问题：

- 这份日报真正服务哪个决策动作？
- 哪些数字来自正式系统，哪些来自临时表格？
- 风险描述需要谁先确认？
- 模型写出来的异常解释，如果错了谁兜底？
- 上线后谁维护 Prompt、样本和指标？

代码生成越快，这些问题反而越早暴露。

所以 AI 时代真正被放大的，不是“写代码能力”，而是“定义问题和承担责任的能力”。

## 最后判断

机器越会写代码，FDE 越不能只把自己定义成写代码的人。

代码会变快，但问题定义、现场判断、生产责任、客户接管和产品反哺不会自动发生。AI Coding 会压缩实现成本，却会放大错误问题被快速实现的风险。FDE 剩下的，不是更慢地写代码，而是更准确地判断什么值得被写成系统。
