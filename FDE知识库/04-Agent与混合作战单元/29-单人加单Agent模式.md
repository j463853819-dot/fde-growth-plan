# 单人加单 Agent 模式

一个 FDE 刚进客户现场时，最常见的感受不是“问题太难”，而是“信息太多”。

十几份访谈纪要，几百条历史工单，一堆群聊截图，还有一堆别人说“你先看看”的材料。这个阶段如果全靠自己手工整理，很容易在真正开始判断之前就被体力活耗掉。

单人加单 Agent，是 FDE 最容易起步的人机协同模式。

它不是搭一个庞大的 Agent 团队，而是让一个 FDE 配一个稳定助手，帮助自己处理资料整理、代码生成、测试、文档、复盘等高频任务。

从定义上看，单人加单 Agent 模式是指一个 FDE 负责目标、判断和交付责任，一个 Agent 负责在明确边界内执行可验证任务。它适合项目早期、个人效率放大和低风险自动化。

> **一句可以带走的判断：单 Agent 的价值不是替你做决定，而是让你更快看到事实、方案和风险。**

## 一句话定义

单人加单 Agent 模式，是指一个 FDE 负责目标、判断和交付责任，一个 Agent 负责在明确边界内执行可验证任务。

它适合项目早期、个人效率放大和低风险自动化。

## 适合哪些任务

| 任务 | Agent 适配度 |
| --- | --- |
| 整理访谈纪要 | 高 |
| 提取流程和角色 | 高 |
| 生成 Demo 草稿代码 | 中高 |
| 编写测试用例 | 中高 |
| 生成 ADR 初稿 | 中 |
| 自动修改生产数据 | 低 |

单 Agent 最适合做“可检查的辅助工作”，不适合直接承担高风险业务动作。

## FDE 应该怎么使用

一个有效的单 Agent 工作法包括四步：

1. 明确任务：不要让 Agent “帮我想想”，而是让它处理具体对象。
2. 给出边界：说明哪些资料可以用，哪些结论不能下。
3. 要求结构化输出：表格、清单、差异分析比散文更好。
4. 人工复核：FDE 必须对最终判断负责。

## 一个典型场景

FDE 拿到 10 份客户访谈纪要。

Agent 可以先做：

- 提取所有角色。
- 标记每个角色的痛点。
- 汇总重复出现的问题。
- 把事实和解释分开。
- 生成待验证问题清单。

FDE 再基于这些结果判断：哪个问题最值得切片，哪些说法需要找日志验证，哪些需求其实是管理层想象。

## 单 Agent 的边界

单 Agent 容易出三个问题：

| 问题 | 应对 |
| --- | --- |
| 看似合理但事实不准 | 要求引用来源 |
| 输出太泛 | 要求按模板输出 |
| 越界建议 | 明确“不做决策，只列选项” |

Agent 不应该替 FDE 决定“客户真正需要什么”。它可以帮你整理材料、扩大视野、生成备选，但最终判断必须由人承担。

## 最小任务卡

| 字段 | 内容 |
| --- | --- |
| 任务目标 | Agent 要完成什么 |
| 输入材料 | 可以使用哪些资料 |
| 输出格式 | 表格、清单、模板或代码 |
| 禁止事项 | 不得推测、不得写入、不得外发 |
| 检查标准 | FDE 如何判断输出可用 |

单人加单 Agent 是 FDE 进入人机协作最稳的起点。它不追求宏大自动化，而是先把个人工作流里最重复、最耗时、最可检查的部分交出去。

## 实战拆解：访谈材料应该怎么交给单 Agent

一个典型场景是，FDE 拿到 10 份客户访谈纪要。

这时最不划算的做法，是让 Agent “总结一下这些内容”。输出通常会很泛。

更有效的做法，是把任务切得非常具体：

- 提取所有角色。
- 按角色列痛点。
- 区分事实、解释和愿望。
- 标记重复出现的问题。
- 生成待验证问题清单。

这样 Agent 做的是“材料结构化”，不是“替你判断客户真正的问题”。

人机协作一旦这么分工，单 Agent 的价值就会很稳定。

## 最后判断

单人加单 Agent 的关键，不是让 Agent 替 FDE 思考，而是让它接住那些可定义、可检查、可重复的任务。

FDE 仍然要负责问题定义、事实判断和方案取舍。Agent 做材料结构化、草稿生成和样本整理，人做最终判断和责任确认。这个模式小，但它是 FDE 进入人机协作最稳的第一步。
