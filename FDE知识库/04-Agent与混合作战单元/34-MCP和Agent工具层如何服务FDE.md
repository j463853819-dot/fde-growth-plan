# MCP 和 Agent 工具层如何服务 FDE

Agent 真正进入企业，不是靠会聊天，而是靠能安全地使用工具。

它要读文档、查数据库、调用 CRM、创建工单、发通知、触发审批。每一种能力都需要一个工具层来承接。工具层设计不好，Agent 不是变弱，就是变危险。

从定义上看，MCP 可以理解为一种让模型或 Agent 以标准方式连接外部工具和数据源的协议思路。对 FDE 来说，关键不在名词本身，而在于工具层如何把企业系统能力以可控、可审计、可复用的方式暴露给 Agent。

> **一句可以带走的判断：Agent 的上限取决于模型，Agent 的生产边界取决于工具层。**

## 工具层解决什么问题

| 问题 | 工具层的作用 |
| --- | --- |
| 系统分散 | 把不同系统封装成统一工具 |
| 权限复杂 | 按身份、角色和场景控制访问 |
| 操作风险 | 区分只读、建议、审批后写入、自动写入 |
| 审计困难 | 记录每次调用、参数和结果 |
| 复用困难 | 把一次项目工具沉淀成可复用能力 |

FDE 做 Agent 项目时，不能只写 Prompt，还要设计工具。

## 工具分级

| 等级 | 工具能力 | 示例 |
| --- | --- | --- |
| L1 只读 | 查询信息 | 查订单、查政策 |
| L2 建议 | 生成草稿 | 生成回复、生成工单草稿 |
| L3 审批后写入 | 人确认后执行 | 创建工单、更新 CRM |
| L4 自动写入 | 低风险自动执行 | 自动标签、低风险通知 |

生产项目通常从 L1/L2 开始，不要急着开放 L4。

## FDE 如何设计工具

一个好的 Agent 工具应该具备：

- 清晰名称。
- 明确输入参数。
- 明确输出结构。
- 权限说明。
- 错误返回。
- 调用日志。
- 速率限制。
- 可测试样例。

工具描述越模糊，Agent 越容易误用。

## Legacy 系统怎么办

企业里很多系统没有好用 API。

FDE 可以考虑几种路径：

| 路径 | 适用情况 |
| --- | --- |
| 只读报表导出 | 系统封闭但能导出数据 |
| 中间表同步 | 需要稳定查询但不直接写核心系统 |
| RPA 封装 | 没 API 但流程稳定 |
| 人工审批桥接 | 写入风险高，先让人确认 |
| 推动系统接口化 | 场景长期存在，值得产品化 |

不要为了让 Agent 显得自动化，就强行绕过系统边界。

## 工具层和产品化

FDE 项目里写的工具，如果只服务一个客户，很容易变成定制代码。

但如果多个客户都需要类似工具，比如查订单、查合同、查政策、创建工单、更新 CRM，那就应该沉淀为平台能力。

工具层是 FDE 经验产品化的重要入口。

## 最小工具卡

| 字段 | 内容 |
| --- | --- |
| 工具名称 | Agent 如何识别 |
| 业务用途 | 解决哪个场景 |
| 输入参数 | 字段、类型、必填项 |
| 输出结构 | 成功和失败返回 |
| 权限等级 | 只读、建议、审批后写入、自动写入 |
| 审计要求 | 记录什么 |
| 失败处理 | 超时、权限不足、数据为空怎么办 |

Agent 工具层看起来是技术细节，实际上是企业 AI 能不能进入生产的关键边界。
