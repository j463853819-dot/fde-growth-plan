# PDD 问题定义文档怎么写

一个项目最危险的时刻，不一定是上线前。

更早一点，在第一次方案会里，风险就已经埋下了。老板以为项目是降本增效，业务以为是减少一线查资料，技术以为只是接一个知识库，销售以为下周能演示一个完整 AI 助手。

大家都点头说“方向一致”，但他们其实在说四个不同的项目。

到了工程阶段，这种分歧才会爆出来：为什么 Demo 不解决老板关心的指标？为什么业务说不好用？为什么技术说不能上线？为什么销售觉得交付范围缩水？

PDD 的价值就在这里：在方案设计前，先把“我们到底在解决什么问题”写下来。

> **一句可以带走的判断：没有 PDD 的方案，很容易把不一致的理解包装成一致的计划。**

## 理论框架

PDD，Problem Definition Document，问题定义文档，是 FDE 在 Context 阶段输出的核心文档。

它不写完整方案，而是写清楚：问题是什么、发生在哪里、影响谁、为什么重要、有哪些约束、下一步验证什么。

PDD 适合三类场景：

| 场景 | 为什么需要 PDD |
| --- | --- |
| 客户需求模糊 | 避免把方案名当问题定义 |
| 涉及多角色协作 | 对齐老板、业务、技术和销售的理解 |
| 准备进入工程投入 | 防止 Demo 或试点做错方向 |

PDD 的核心产物不是文档本身，而是一句可验证的问题定义。

## 核心方法

写 PDD 时，先不要急着描述方案，而要按四步收敛问题。

第一步，写清楚发生场景。问题必须落在某条真实流程里，而不是停在“客户想要 AI”这种抽象表达上。

第二步，写清楚受影响角色。谁每天受影响，谁最终拍板，谁负责技术接入，谁以后要接管系统，都要放进文档。

第三步，写清楚事实证据。访谈、工单、日志、报表、截图都可以，但不能只写“客户觉得很慢”。

第四步，写清楚下一步验证。PDD 不是结案报告，它要指向 Demo、试点或停止。

一份好 PDD，最后应该能回答这句话：

```text
我们为什么相信这是一个真实问题，以及下一步用什么最小动作验证它。
```

## 核心模板

```markdown
# PDD：问题名称

## 1. 背景
客户现场是什么业务场景？为什么现在要处理这个问题？

## 2. 问题定义
谁在什么流程里遇到什么瓶颈，造成什么影响？

## 3. 受影响角色
主要用户、决策者、技术 Owner、其他相关方。

## 4. 当前流程
旧流程如何运行？关键步骤是什么？

## 5. 事实与证据
有哪些数据、访谈、日志、工单、截图能证明问题存在？

## 6. 业务影响
影响时间、成本、质量、风险、收入还是体验？

## 7. 约束条件
数据、权限、系统、合规、组织、时间和预算限制是什么？

## 8. 价值假设
如果问题被解决，哪个指标会变化？

## 9. 不做事项
本阶段明确不解决什么。

## 10. 下一步验证
要做什么 Demo、试点或实验来验证关键假设？
```

## 常见误区

| 坏写法 | 问题 | 好写法 |
| --- | --- | --- |
| 做一个 AI 客服助手 | 是方案，不是问题 | 客服处理退款咨询时，因政策和订单信息分散导致响应慢 |
| 提升效率 | 指标不清 | 平均响应时间从 8 分钟降到 5 分钟以内 |
| 接入订单系统 | 没说明原因 | 为生成建议时引用订单状态 |
| 支持所有客服场景 | 范围过大 | 先做退款咨询，不做投诉和赔付 |

PDD 写得越清楚，后面的方案越不容易漂。

## 实战拆解：合同审查 Agent

客户说要做“法务合同审查 Agent”。

如果 PDD 直接写“建设合同审查 Agent”，它没有定义问题，只是记录了一个方案名。工程团队不知道先做哪类合同，法务不知道什么叫审查成功，客户 IT 也不知道系统要读哪些数据。

FDE 经过访谈后，把问题定义改成：

> 法务初审采购合同时，需要人工检查付款、违约、数据处理和责任条款。由于历史合同和审查标准分散，新人平均初审耗时 45 分钟，且高风险条款漏标率较高。

这句话立刻改变了项目讨论。

方案不再从“Agent 要多智能”开始，而是从“采购合同、初审、四类高风险条款、45 分钟基线、漏标率”开始。下一步也不必做完整 Agent，可以先做 RAG + 风险提示 + 法务确认。

PDD 还会明确不做事项：不自动修改合同，不自动发起审批，不替代法务最终判断。

这样一来，Demo 就有了边界：验证 AI 是否能在采购合同初审中稳定标出高风险条款，并给出引用依据。

## 最后判断

PDD 不是为了多写一份文档，而是为了让项目在进入 Design 前，先确认所有人正在解决同一个问题。

好的 PDD 不会让问题变复杂，它会让复杂现场第一次变得可讨论、可验证、可取舍。FDE 如果不能写清 PDD，后面的方案越漂亮，偏离真实问题的风险越大。
