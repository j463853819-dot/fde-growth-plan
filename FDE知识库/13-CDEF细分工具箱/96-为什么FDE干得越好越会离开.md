# 为什么 FDE 干得越好越会离开

项目上线后，客户每天都来找 FDE。

今天问 Prompt 能不能改一下，明天问失败样本怎么处理，后天又让 FDE 帮忙看告警。客户很满意，销售也觉得关系很稳，团队甚至会觉得：你看，FDE 真的不可替代。

但这可能不是好信号。

如果一个系统永远离不开 FDE，说明客户没有接管，产品没有沉淀，组织没有形成能力。FDE 越忙，越可能说明项目还没有真正完成。

真正好的 FDE 项目，会经历一个微妙的变化：一开始客户什么都找你，后来客户开始自己看指标、自己维护知识库、自己复盘失败样本。你参与得越来越少，项目反而越来越稳。

> **一句可以带走的判断：FDE 的目标不是让客户离不开你，而是让客户和产品都能接住你留下的能力。**

## 理论框架

“干得越好，越会离开”指的是：FDE 在项目中完成问题定义、工程验证、生产交付、价值证明和客户接管后，应该逐步退出日常执行，把能力交给客户、产品或平台团队。

| 如果不离开 | 后果 |
| --- | --- |
| FDE 长期代运维 | 客户没有真正接管 |
| FDE 持续做小需求 | 项目变成外包 |
| FDE 一直解释业务 | 组织知识没有沉淀 |
| FDE 一直修 Prompt | AI 资产没有 Owner |
| FDE 无法复制经验 | 产品反哺失败 |

FDE 离开不是撤退，而是交付完成的标志。

离场条件包括：价值指标被验证、客户 Owner 能说明系统边界、客户 IT 能处理告警和回滚、业务团队能维护关键资产、产品团队吸收了可复用经验。

## 核心方法

FDE 离场可以分四步。

| 阶段 | FDE 做什么 | 交接给谁 |
| --- | --- | --- |
| 上线初期 | 主导问题处理和指标复盘 | 客户业务 Owner |
| 稳定运行 | 陪跑知识库、评测和告警处理 | 客户运营和 IT |
| 接管演练 | 模拟故障、回滚和失败样本复查 | 客户团队 |
| 反哺沉淀 | 总结模板、组件和产品需求 | 产品和平台团队 |

FDE 不是突然离开，而是逐步把责任从自己手里移出去。

## 常见误区

| 误区 | 后果 |
| --- | --- |
| 客户满意就继续代运营 | 短期关系好，长期成本高 |
| 上线当天就撤 | 客户还没形成运行能力 |
| 只做培训不做演练 | 客户会用，但不会处理异常 |
| 不做产品反哺 | 下个项目继续从零开始 |

离场的重点不是减少服务，而是完成能力转移。

## 实战拆解：客服 AI 的离场

客服 AI 上线后，客户很依赖 FDE。

每次知识库更新，FDE 帮忙确认；每次客服说 AI 答得怪，FDE 去查失败样本；每次主管要看效果，FDE 临时整理数据。表面上这是服务好，实际上风险很大。

FDE 开始设计离场路径。

第一步，把 Prompt、知识库、模型、评测集和工具权限放进 AI 资产清单，让客户知道系统到底由哪些资产构成。

第二步，让客服主管每周维护失败样本，不再由 FDE 单独判断哪些问题要修。

第三步，让客户 IT 完成一次告警和回滚演练。不是看文档，而是真的模拟“知识库更新后质量下降”。

第四步，把退款咨询模板、高风险转人工规则和评测集交给产品团队，判断哪些能沉淀为通用能力。

最后，FDE 从每天响应，变成每两周复盘一次。客户仍然能运行系统，产品也拿到了可复用资产。

这时 FDE 的价值没有变小，而是从个人在场，变成组织能力。

## 最后判断

FDE 最好的结局不是一直被需要，而是曾经混乱的现场，后来不再需要你每天在场。

如果 FDE 离不开项目，项目就还没有完成；如果 FDE 离开后系统仍然运行、客户仍然复盘、产品仍然进化，这才是真正的交付闭环。
