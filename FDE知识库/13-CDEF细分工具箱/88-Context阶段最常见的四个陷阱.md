# Context 阶段最常见的四个陷阱

Context 阶段最有欺骗性。

你每天都在开会、访谈、看文档、听客户讲业务。日程很满，信息很多，客户也觉得你很投入。可一周过去，团队还是说不清：到底先解决哪个问题？为什么是这个问题？下一步 Demo 要验证什么？

这就是 Context 最常见的失败方式：看起来收集了很多信息，实际上没有完成收敛。

更麻烦的是，大家还会觉得项目进展很好。因为会议纪要越来越多，流程图越画越细，客户材料越收越全，但真正要进入 Design 时，问题定义还是一团雾。

FDE 在这个阶段真正要做的，不是变成记录员，而是把混乱现场压缩成可验证问题。

> **一句可以带走的判断：Context 阶段的目标不是收集更多信息，而是把信息收敛成可验证问题。**

## 理论框架

Context 阶段有四个高频陷阱：过早方案、被客户带偏、信息收集过度、只听高层不看一线。

| 陷阱 | 表现 | 应对方法 | 产物 |
| --- | --- | --- | --- |
| 过早方案 | 客户刚说痛点，团队马上设计系统 | 先问场景、角色、损失和约束 | PDD |
| 被客户带偏 | 把客户原话当真实需求 | 三层访谈交叉验证 | 事实与约束表 |
| 信息收集过度 | 一直调研，不进入验证 | 设定 Context 退出条件 | 需求切片 |
| 只听高层 | 目标宏大但不落地 | 补一线流程观察 | 流程地图 |

Context 的适用场景很明确：客户需求还模糊、内部说法不一致、项目尚未进入方案设计。

它的核心产物是问题定义，而不是厚厚的调研材料。

## 核心方法

FDE 可以用四个问题判断 Context 是否该结束：

1. 是否能用一句话定义真实问题？
2. 是否有证据证明这个问题存在？
3. 是否知道当前阶段不做什么？
4. 是否能切出下一步最小验证？

如果这四个问题答不上来，说明 Context 还没有完成。

如果已经答得上来，就不要继续无限调研。进入 Design，用 Demo 或试点验证关键假设。

## 常见误区

| 误区 | 现场表现 | 后果 |
| --- | --- | --- |
| 把调研当成果 | 纪要很多，但没有问题定义 | 后续方案无法聚焦 |
| 把客户愿景当需求 | 直接围绕“智能大脑”设计 | 范围失控 |
| 把技术约束当终点 | 听到接口难就放弃 | 错过可行切片 |
| 不敢缩小范围 | 怕客户觉得方案太小 | Demo 大而空 |

Context 阶段不是越久越专业。它应该像漏斗一样，把大量信息收敛成少数关键判断。

## 实战拆解：智能运营大脑

客户说要做“智能运营大脑”。

第一个陷阱马上出现：过早方案。团队开始讨论大屏、指标、Agent、自动分析，看起来很专业。但 FDE 暂停了这个方向，先问：“管理层现在每周最痛的决策是什么？”

第二个陷阱是被客户带偏。客户一直说“大脑”，但访谈运营主管后发现，真正的问题不是缺一个大屏，而是库存异常没人能在会前解释清楚。

第三个陷阱是信息收集过度。客户愿意给很多报表和会议纪要，FDE 没有继续无限调研，而是设定退出条件：能否定义一个库存异常归因切片。

第四个陷阱是只听高层。一线仓储和履约同事补充了关键事实：很多异常不是库存系统的问题，而是订单取消和补货节奏没有及时同步。

最后，项目从“智能运营大脑”变成：

> 每周经营会前，系统识别库存周转异常，生成原因假设、证据来源和待确认责任人。

这个切片小了很多，但它终于能验证。

## 最后判断

Context 做得好，后面会少很多无效工程。

它不是让项目慢下来，而是防止团队很快地做错事。FDE 在 Context 阶段最重要的能力，是在信息最多的时候保持收敛，在声音最杂的时候坚持证据。
