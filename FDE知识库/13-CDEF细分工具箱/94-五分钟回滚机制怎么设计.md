# 五分钟回滚机制怎么设计

系统上线后的第一周，客服主管在群里发了一句：“今天 AI 回复的退款政策好像不对。”

一线客服开始截图，运营同事在找知识库更新记录，工程师在查日志，FDE 在翻 Prompt 版本。十分钟过去，大家还在判断问题到底出在哪里。更糟的是，客服还在继续使用系统。

这时真正暴露的问题，不是 AI 答错了一次，而是团队没有快速止血机制。

如果一个系统出错后，只能靠群消息喊停，说明它还没有真正进入生产状态。生产系统不是不会错，而是错了以后能被发现、能被暂停、能被回退、能被复盘。

五分钟回滚不是为了证明系统永远不会错，而是承认系统一定会错，并提前设计错误发生后怎么停下来。

> **一句可以带走的判断：不能快速停止错误影响的系统，就还没有真正准备好进入生产。**

## 理论框架

五分钟回滚机制，是指系统在出现严重错误、质量下降、权限异常或成本失控时，能够快速切回上一版本、旧流程或人工模式的应急设计。

它不一定要求所有业务状态真的在五分钟内完全恢复，但至少要在五分钟内完成影响止血。

AI/FDE 项目的回滚对象不只有代码。

| 对象 | 回滚方式 |
| --- | --- |
| Prompt | 回退到上一稳定版本 |
| 知识库 | 回退到上一版本索引 |
| 模型 | 切回旧模型或备用模型 |
| 工具权限 | 关闭写入，降级只读 |
| 工作流 | 暂停自动节点，切回人工确认 |
| 数据接口 | 停止读取异常数据源 |

核心产物是一张回滚卡：谁触发、什么条件触发、回到哪里、通知谁、留下什么记录。

## 核心方法

五分钟回滚要提前定义五件事：

| 问题 | 要提前确认 |
| --- | --- |
| 谁触发回滚 | 值班人、业务 Owner、平台 Owner |
| 什么条件触发 | P0/P1 故障、评测低于阈值、投诉上升 |
| 回到哪里 | 上一版本、人工流程、只读模式 |
| 谁被通知 | 一线用户、主管、客户 IT、客户成功 |
| 如何记录 | 事故记录、trace、变更记录、复盘 |

回滚机制还要演练。没有演练的回滚方案，在事故发生时往往没人敢按。

## 常见误区

| 误区 | 风险 |
| --- | --- |
| 只有代码回滚 | Prompt、知识库、模型仍可能错误 |
| 只有工程知道怎么回滚 | 客户无法接管 |
| 回滚后不复盘 | 同类问题会重复发生 |
| 没有人工流程兜底 | 暂停 AI 后业务也停了 |

FDE 要把回滚当成功能的一部分，而不是上线后的补丁。

## 实战拆解：退款政策错误

还是客服退款政策错误的例子。

如果没有回滚机制，团队会在群里靠人肉协调：“大家先别用”“等等我查一下”“是不是知识库的问题”。这个过程越长，错误影响越大。

如果提前设计了五分钟回滚，流程应该更清楚：

1. 告警发现评测通过率下降，或客服主管报告 P1 质量问题。
2. 值班人确认影响范围。
3. 立即切回上一版知识库索引，或暂停 AI 建议入口。
4. 通知客服团队切回人工知识库。
5. 保存失败样本、trace 和变更记录。
6. 复盘为什么这次知识库更新没有被评测拦住。

这里的重点不是“谁反应快”，而是系统已经设计好了谁有权暂停、暂停什么、回到哪里。

## 最后判断

五分钟回滚是一种承责能力。

它告诉客户：我们不是假设系统不会犯错，而是已经准备好在错误发生时保护业务。FDE 做生产系统，必须把回滚当成功能的一部分，而不是事故后的临时动作。
