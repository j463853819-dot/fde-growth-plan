# FDE 方案文档、成功指标和风险清单怎么写

很多方案文档看起来很完整，读完却不知道下一步该不该做。

前面有背景，后面有架构，中间堆满功能点和流程图。客户觉得专业，团队觉得辛苦，但真正关键的问题没有被回答：这个项目先验证什么？成功怎么算？风险在哪里？失败后怎么办？

销售拿着这份文档，不知道怎么推进客户决策。工程看完以后，不知道哪些能力必须做，哪些只是以后可能做。业务方看完以后，也不知道自己要承担什么责任。

FDE 的方案文档不能只是“我们准备怎么做”。

它更应该是一份决策材料：让客户、业务 Owner、工程团队和产品团队能判断，这个项目是否值得进入 Demo、试点或生产。

> **一句可以带走的判断：好的 FDE 方案文档，不是让人觉得方案很完整，而是让人知道下一步该不该做。**

## 理论框架

FDE 方案文档，是连接 Context 和 Engineer 的设计产物。它把问题定义、价值切片、系统方案、成功指标、风险清单和下一阶段门禁写在一起。

```markdown
# 方案名称

## 1. 背景与问题定义
客户现场、目标角色、当前瓶颈、业务影响。

## 2. 价值切片
本阶段只解决什么，不解决什么。

## 3. 目标流程
新流程如何运行，AI、人、系统分别做什么。

## 4. 系统方案
数据、模型、工具、权限、评测、日志、回滚。

## 5. 成功指标
效率、质量、风险、采用、接管如何衡量。

## 6. 风险清单
数据、权限、质量、成本、合规、组织风险。

## 7. 阶段门禁
进入 Demo、试点、生产分别需要什么证据。

## 8. Owner 与下一步
谁负责，什么时候验证，失败后怎么处理。
```

这类文档适合在进入 Demo 或试点前使用。它的核心产物不是功能列表，而是成功指标和风险清单。

## 核心方法

写方案时，先写清楚三件事。

第一，写清楚本阶段只做什么。FDE 方案不能把未来愿景都塞进当前交付。

第二，写清楚成功指标。指标要能被观察，不要只写“提升体验”“优化效率”。

第三，写清楚风险清单。风险不等于否定方案，而是说明团队知道哪些地方需要门禁。

| 指标类型 | 示例 |
| --- | --- |
| 效率 | 平均响应时间从 8 分钟降到 5 分钟以内 |
| 采用 | 建议采纳率超过 60% |
| 风险 | 高金额退款 100% 转人工 |
| 接管 | 客户主管能维护知识库并复查失败样本 |

## 常见误区

| 误区 | 后果 |
| --- | --- |
| 功能列表太长 | 看起来完整，但没有优先级 |
| 成功指标太虚 | 试点后无法判断是否继续 |
| 风险写得太晚 | 上线前才发现权限、数据和接管问题 |
| 不写不做事项 | 客户默认所有愿景都在本期 |

FDE 方案文档不是承诺一切，而是定义下一阶段最值得验证的范围。

## 实战拆解：客服退款建议回复

客服 AI 方案如果只写“建设智能客服助手”，客户很难判断是否值得继续。

FDE 重新写方案时，先把范围压小：

> 本阶段只处理退款咨询。系统读取脱敏订单状态、退款政策和历史案例，生成建议回复和引用来源，由客服确认后发送。

然后写成功指标：

| 指标类型 | 指标 |
| --- | --- |
| 效率 | 平均响应时间从 8 分钟降到 5 分钟以内 |
| 采用 | 建议采纳率超过 60% |
| 风险 | 高金额退款 100% 转人工 |
| 接管 | 客服主管能维护知识库并复查失败样本 |

再写风险清单：

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 知识库过期 | 回复错误 | 每周更新和回放评测 |
| 订单字段敏感 | 权限违规 | 脱敏和角色权限 |
| 采纳率低 | 价值不成立 | 复盘失败样本，缩小场景 |

这份方案不会让项目显得特别宏大，但它能推动决策。客户知道试点要看什么，工程知道边界在哪里，业务知道自己要接住什么。

## 最后判断

FDE 方案文档的价值，不是把所有可能性写进去，而是把当前阶段最该验证的价值和风险写清楚。

一份好方案读完后，团队应该能回答：为什么做，先做什么，怎么判断成功，失败后怎么退。
