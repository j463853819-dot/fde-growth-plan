# Bootcamp 五天极限工作法

客户说：“我们先小范围试试，但不要拖太久。”

销售希望下周就能看到 Demo，业务方还没完全确认流程，技术接口人说数据可以给一点样例，但生产接口还要审批。项目看起来有机会，但也很脆：做太大，会失控；做太小，客户看不出价值；做太久，窗口期就过去了。

这时候 FDE 最不该做的，是假装已经进入正式项目。

因为正式项目会自然膨胀：要更完整的功能、更稳定的架构、更漂亮的演示、更像生产的体验。几周过去，团队可能做了很多东西，却仍然不知道方向是否成立。

更好的方式，是用五天 Bootcamp 把方向打穿：这件事到底值不值得继续？如果继续，下一步应该试点什么？如果不继续，原因是什么？

> **一句可以带走的判断：Bootcamp 不是五天上线，而是五天内拿到继续、缩小、转向或停止的证据。**

## 理论框架

Bootcamp 五天工作法，是 FDE 在项目早期用 5 个连续工作日完成现场对齐、问题定义、最小原型、用户反馈和下一步决策的高密度验证方式。

| 天数 | 目标 | 产物 |
| --- | --- | --- |
| 第 1 天 | 对齐现场和目标 | 三层访谈、事实与约束表、PDD 初稿 |
| 第 2 天 | 定义价值切片 | 需求切片画布、成功指标、不做事项 |
| 第 3 天 | 搭最小原型 | 可演示流程、样例数据、关键路径 |
| 第 4 天 | 让真实用户试用 | 用户反馈、失败样本、风险清单 |
| 第 5 天 | 做阶段决策 | 继续、缩小、转向或停止 |

Bootcamp 适合客户有明确痛点但方案不清、可以拿到少量真实样本或脱敏数据、风险可控且需要快速判断方向的项目。

它不适合数据完全不可得、客户没有 Owner、涉及高风险自动决策，或成功标准完全说不清的项目。

## 核心方法

Bootcamp 的重点不是加速交付，而是压缩验证周期。

每天都要回答一个问题：

| 天数 | 必须回答的问题 |
| --- | --- |
| 第 1 天 | 这个问题是否真实存在 |
| 第 2 天 | 第一个价值切片是什么 |
| 第 3 天 | 最小原型能否跑通关键路径 |
| 第 4 天 | 真实用户是否认可价值 |
| 第 5 天 | 下一步是继续、缩小、转向还是停止 |

Bootcamp 结束时，至少要留下 PDD、需求切片、原型、用户反馈、风险清单和下一阶段门禁。

## 常见误区

| 误区 | 后果 |
| --- | --- |
| 五天里追求功能完整 | 忘了验证关键假设 |
| 只演示给领导 | 看不到真实用户反应 |
| 不敢给停止结论 | 把不成立的方向包装成继续优化 |
| 没有留下证据 | 五天忙完，团队仍然靠感觉决策 |

Bootcamp 最重要的成果，是让团队更早面对事实。

## 实战拆解：销售线索助手

客户想做“销售线索助手”。

第 1 天，FDE 访谈销售主管、销售代表和 CRM 管理员。发现真正的问题不是“销售不会写跟进话术”，而是新线索进来后，销售不知道客户背景、优先级和下一步动作。

第 2 天，团队把切片压到很小：只处理最近 30 天有互动记录的新线索，输出客户背景摘要和下一步跟进建议。

第 3 天，FDE 用样例数据搭出最小原型。不接生产写回，不做完整 Agent，只做建议草稿。

第 4 天，5 名销售试用。有人说摘要有用，但下一步建议太泛；有人指出 CRM 里很多关键字段为空。

第 5 天，团队没有硬推“助手项目成功”。他们做了更准确的判断：摘要能力值得继续，自动建议需要更多上下文，CRM 数据质量要作为风险进入试点。

下一阶段不是扩大功能，而是进入一个两周试点：只做线索摘要 + 人工确认的下一步动作。

## 最后判断

Bootcamp 的价值不是快，而是让团队尽早面对事实。

五天内看清一个方向不成立，比三个月后上线失败便宜太多。FDE 要追求的不是五天做完，而是五天后大家终于知道该继续、缩小、转向还是停止。
