# 从原型到生产的工程化工具链

原型阶段，一个 AI 助手只要能跑起来，就能让业务方看到希望。

但进入试点后，问题会换一批：代码谁管？配置谁改？Prompt 怎么回滚？线上失败怎么定位？客户内网怎么部署？出了事故怎么切回人工？

这就是原型和生产的差别。

原型工具解决“能不能看见”，工程化工具链解决“能不能依赖”。

> **原型证明想法，工程化证明系统能承受真实世界。**

## 一句话定义

工程化工具链，是把 AI 原型转成可部署、可测试、可观测、可回滚、可接管系统的一组工程能力。

它包括代码管理、环境管理、服务化、容器化、CI/CD、监控告警、评测回放和运行手册。

## 原型阶段：轻，但要诚实

原型阶段工具要轻。

它的目标是尽快验证场景，而不是一开始就建设完整平台。

| 能力 | 目标 | 可以临时吗 |
| --- | --- | --- |
| 快速页面 | 让业务方看到流程 | 可以 |
| 简单数据接入 | 验证输入是否可用 | 可以 |
| Prompt/RAG 原型 | 验证输出是否有价值 | 可以 |
| 手工评测 | 快速暴露错误 | 可以 |
| 风险记录 | 说明哪些被简化 | 不可以省 |

原型阶段可以粗糙，但不能假装成熟。

这句话很重要。

FDE 可以用脚本、低代码、手工导入、临时账号，但必须记录哪些能力还没有生产化。

## 试点阶段：开始补证据

试点不是扩大版 Demo。

试点意味着真实用户、真实数据、真实流程开始进入系统。

这时工具链要补证据：

| 能力 | 目标 |
| --- | --- |
| 版本管理 | 知道每次改了什么 |
| 评测回放 | 确认变更没有破坏旧能力 |
| 权限控制 | 限制真实数据和工具调用 |
| 日志和 trace | 能定位失败路径 |
| 用户反馈 | 收集线上失败样本 |
| 灰度范围 | 限制影响面 |

试点阶段的好结果不是“没有问题”。

是问题真实暴露，并且能被收敛。

## 生产阶段：补运行和接管

生产阶段要把系统放进客户组织的责任体系里。

这时工具链至少要覆盖：

| 能力 | 目标 |
| --- | --- |
| API 服务化 | 稳定接入业务系统 |
| 容器和环境管理 | 保证部署可复现 |
| CI/CD | 规范发布和回滚 |
| 密钥和配置管理 | 避免临时配置散落 |
| SLO 和告警 | 让客户看懂系统状态 |
| 运行手册 | 让客户团队能接管 |

生产工程化不等于把系统做重。

它是把风险变得可见、可控、可复查。

## 一条渐进路径

FDE 不需要一开始就上最重架构。

但必须知道什么时候补哪块能力。

| 阶段 | 工具策略 | 退出标准 |
| --- | --- | --- |
| Demo | 低代码平台、脚本、轻量知识库 | 验证关键价值假设 |
| 试点 | 增加版本、评测、日志、权限 | 真实用户和失败样本进入系统 |
| 生产初版 | 服务化、容器化、监控、回滚 | 可运行、可观测、可降级 |
| 规模化 | 多租户、模板化、自动化运营 | 可复制、可接管、可产品化 |

## 实战拆解：客服 AI 助手怎么从脚本走到生产

第一版客服 AI 助手可能只是一个脚本：

- 手工导入 100 条政策文档。
- 用简单 RAG 做问答。
- 页面里展示建议回复。
- FDE 手工看日志和失败样本。

这能做 Demo。

但试点时，必须补：

- 文档更新流程。
- Prompt 版本记录。
- 用户问题和回答日志。
- 失败样本标签。
- 高风险问题转人工。

到生产时，还要补：

- 客服工作台集成。
- 身份权限和数据脱敏。
- 评测集回放。
- 延迟、成本、错误率告警。
- 关闭 AI 建议的功能开关。
- 客户 Owner 的运行手册。

这条路看起来麻烦，但它防止了最常见的尴尬：Demo 很像产品，生产却全靠 FDE 个人兜底。

## 上生产前的工程检查

| 检查项 | 要回答的问题 |
| --- | --- |
| 代码和配置版本 | 当前线上到底跑的是哪一版 |
| 环境变量和密钥 | 是否有安全管理和轮换机制 |
| 评测集和回放 | 变更是否破坏旧场景 |
| 日志、指标和 trace | 出错后能不能定位 |
| 灰度和回滚 | 出事后能不能缩小影响 |
| 运行手册和 Owner | 客户是否能接管 |

工程化工具链的目标，不是让技术显得专业。

是让业务有理由信任系统。
