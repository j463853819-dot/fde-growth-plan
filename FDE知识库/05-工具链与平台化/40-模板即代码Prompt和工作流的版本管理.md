# 模板即代码：Prompt 和工作流的版本管理

FDE 项目里，很多真正影响系统行为的东西，不在代码里。

Prompt、RAG 配置、Agent 工具描述、工作流节点、评测标准、权限规则，这些都可能改变系统输出。

如果它们散落在平台页面、个人文档或聊天记录里，生产风险就会变高。

> **凡是会影响 AI 系统行为的模板，都应该像代码一样被管理。**

## 一句话定义

“模板即代码”是把 Prompt、工作流、工具 schema 和评测配置当成代码一样管理：有版本、有评审、有测试、有发布、有回滚。

它不是形式主义。

它承认一个现实：AI 系统的行为不只由代码决定。

## 哪些模板要管理

| 模板 | 影响 | 不管理的后果 |
| --- | --- | --- |
| Prompt 模板 | 输出内容和格式 | 行为变化无法追踪 |
| RAG 检索配置 | 知识召回和引用 | 回答来源不稳定 |
| Agent 工具描述 | 工具选择和参数 | 调错工具或参数 |
| 工作流节点 | 执行顺序和分支 | 责任边界被悄悄改变 |
| 评测标准 | 上线判断 | 质量门禁失真 |
| 权限规则 | 可访问数据和可执行动作 | 越权或误操作 |

这些内容如果不版本化，系统会变成“看起来没改代码，但行为变了”。

## 如何版本化

最小做法：

- 每个模板有唯一名称。
- 每次变更有版本号。
- 记录变更原因。
- 关联评测结果。
- 记录发布环境。
- 保留回滚版本。

| 字段 | 示例 |
| --- | --- |
| 模板名 | contract_risk_review_prompt |
| 版本 | v2.1.0 |
| 变更原因 | 增加付款条款风险识别 |
| 评测结果 | 80 条样本通过率 92% |
| 发布范围 | 试点客户 A |
| 回滚版本 | v2.0.3 |

## 工作流也要版本化

Agent 工作流常常比 Prompt 更危险。

比如一个节点从“生成建议”改成“自动写入”，这不是小改动，而是责任边界变化。它应该触发评审、评测和生产门禁。

工作流变更要特别记录：

- 新增或删除了哪些节点。
- 是否改变工具权限。
- 是否改变人工确认点。
- 是否影响数据写入。
- 是否影响告警和回滚。

Prompt 改坏，可能导致回答变差。

工作流改坏，可能导致系统做错事。

## 和交付证据包的关系

模板版本应该进入交付证据包。

客户接管时，需要知道：

- 当前生产版本是什么。
- 哪些 Prompt 和工作流在运行。
- 上一次变更改了什么。
- 评测通过情况如何。
- 出问题能回滚到哪个版本。

没有这些，客户只能接管一个黑盒。

## 实战拆解：合同审查工作流为什么要当代码管

一个合同审查 AI，早期只做付款条款风险识别。

工作流很简单：

1. 解析合同。
2. 检索条款库。
3. 生成风险提示。
4. 法务人工确认。

后来团队想提高效率，把“法务人工确认”改成“低风险合同自动通过，高风险合同转人工”。

这个改动看起来像工作流优化。

实际上它改变了责任边界。

这时必须留下：

| 记录 | 原因 |
| --- | --- |
| 工作流版本 | 知道什么时候开始自动通过 |
| 风险分类标准 | 说明什么叫低风险 |
| 评测报告 | 证明分类足够可靠 |
| 审批记录 | 谁同意扩大自动化范围 |
| 回滚方案 | 出问题如何恢复人工确认 |

没有这些记录，项目后面一旦出错，很难回答“当时为什么允许自动通过”。

## 最小发布流程

1. 提交模板变更。
2. 说明变更原因。
3. 跑评测集回放。
4. 人工复核关键失败样本。
5. 小范围灰度。
6. 记录发布版本。
7. 保留回滚方案。

模板即代码不是为了让流程复杂。

是为了让 AI 系统里真正影响行为的部分，都进入工程纪律。
