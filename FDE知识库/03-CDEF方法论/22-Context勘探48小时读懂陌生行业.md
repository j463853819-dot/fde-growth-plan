# Context 勘探：48 小时读懂陌生行业

FDE 经常要进入陌生行业。

第一天见客户，第二天看系统，第三天可能就要拿出一个初步判断。听起来像不可能任务，但 FDE 不需要在 48 小时内成为行业专家，它需要在 48 小时内建立一张足够可靠的现场地图。

从定义上看，Context 勘探是 CDEF 的第一阶段，用来快速识别业务现场中的角色、流程、数据、系统、约束和价值损失。它的目标不是写厚调研报告，而是为后续 Design 阶段提供可验证的问题模型。

> **一句可以带走的判断：Context 阶段不是听客户讲需求，而是把现场从口头叙事还原成事实结构。**

## 48 小时要看什么

48 小时勘探可以分成四条线：

| 线索 | 要看什么 |
| --- | --- |
| 人 | 谁发起、谁使用、谁审批、谁兜底、谁反对 |
| 流程 | 事情从哪里开始，到哪里结束，中间卡在哪里 |
| 数据 | 数据在哪里，谁维护，是否可信，是否可授权 |
| 系统 | 现有系统怎么连接，哪些动作仍靠人工完成 |

很多真实问题不在会议纪要里，而在一线人员绕过系统的动作里。

## 三层访谈法

Context 阶段不要只访谈一个角色。

| 层级 | 访谈对象 | 主要问题 |
| --- | --- | --- |
| 决策层 | Sponsor、业务负责人 | 为什么现在要做，成功意味着什么 |
| 管理层 | 部门负责人、流程 Owner | 当前流程如何运行，哪些指标受影响 |
| 一线层 | 实际操作者、支持人员 | 每天怎么做，哪里最痛，怎么兜底 |

三层访谈的价值，是把战略目标、流程管理和真实操作对齐。只听决策层，容易做成宏大项目；只听一线，容易陷入局部痛点。

## 现场证据优先级

FDE 要尽量从“可验证证据”出发。

| 证据 | 价值 |
| --- | --- |
| 系统日志 | 看真实频率和异常 |
| 历史工单 | 看重复问题和责任边界 |
| 表格和手工台账 | 看系统没覆盖的真实流程 |
| 群聊和邮件 | 看协作断点和临时规则 |
| 用户修改记录 | 看 AI 或系统输出哪里不被信任 |

访谈可以告诉你“大家怎么理解问题”，证据才能告诉你“问题实际怎么发生”。

## 48 小时输出什么

Context 阶段不追求完整答案，但必须输出初步结构。

| 产物 | 内容 |
| --- | --- |
| 角色地图 | 关键角色、责任、利益和阻力 |
| 现状流程图 | 输入、处理、判断、输出、反馈 |
| 事实约束表 | 已验证事实、解释、判断和约束 |
| 问题模型 | 真实问题、影响范围和价值损失 |
| 待验证假设 | 下一阶段需要用 Demo 或数据验证的点 |

## 一个小例子

客户说：“我们的日报太慢，想让 AI 自动写。”

Context 勘探后可能发现：

- 数据来自三个系统，口径不一致。
- 运营每天花最多时间不是写文字，而是解释异常。
- 管理层真正关心的是异常原因，而不是日报格式。
- 一线已经有一张手工维护的异常原因表。

这时真实问题就不是“AI 写日报”，而是“如何把异常指标、原因归因和建议动作形成稳定闭环”。

## Context 阶段的边界

Context 不负责做最终方案。

它只负责把现场看清楚，把不确定性拆出来，把值得验证的问题交给 Design 阶段。

如果 Context 阶段做得太轻，后面会不断返工；如果做得太重，项目又会停在调研里。好的 FDE 要掌握这个分寸：足够理解现场，但不假装自己已经知道全部答案。
