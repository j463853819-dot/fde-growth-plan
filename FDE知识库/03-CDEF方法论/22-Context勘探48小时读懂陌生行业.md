# Context 勘探：48 小时读懂陌生行业

客户第一次开口说的需求，往往不是问题本身。

一家制造企业的运营负责人第一次见面，就把诉求说得很清楚：

“我们想做一个 AI 助手，帮车间主管自动分析异常。”

这句话听起来很合理。车间数据多，异常多，人手不够，AI 好像正好能派上用场。

但 FDE 不能马上打开工具，也不能马上写 Prompt。

第一件事，是判断这句话背后到底有没有一个真实问题。

两天访谈后，团队才发现：车间主管真正痛苦的不是“不会分析异常”，而是设备状态、质检记录和维修工单对不上。主管每天花最多时间，不是在分析，而是在问人：

“这个异常到底算谁的？”

这时问题变了。

它不是“做一个 AI 助手”，而是“如何把设备、质检、维修三条线的事实对齐，让异常能被归因、派单和追踪”。

这就是 Context 勘探的价值。

> **Context 阶段不是听客户讲需求，而是把现场从口头叙事还原成事实结构。**

## 一句话定义

Context 是 CDEF 的第一阶段。

它的任务不是立刻提出方案，而是在有限时间内建立一张可靠的现场地图：谁在做事，流程怎么跑，数据在哪里，系统哪里断，真正的业务损失发生在哪。

用更直白的话说：

Context 要帮 FDE 分清楚三件事：

- 客户说自己想要什么。
- 现场真实发生了什么。
- 项目第一步到底应该验证什么。

## 48 小时不是成为专家

FDE 经常要进入陌生行业。

第一天见客户，第二天看系统，第三天可能就要给出初步判断。听起来像不可能任务，但 FDE 不需要在 48 小时内成为行业专家。

它需要建立一张足够可靠的现场地图。

这张地图至少包括四条线：

| 线索 | 要看什么 | 容易忽略什么 |
| --- | --- | --- |
| 人 | 谁发起、谁使用、谁审批、谁兜底、谁反对 | 真正受影响的人未必在会议室里 |
| 流程 | 事情从哪里开始，到哪里结束，中间卡在哪里 | 流程图常常比真实动作更漂亮 |
| 数据 | 数据在哪里，谁维护，是否可信，是否可授权 | 数据可见不等于数据可用 |
| 系统 | 现有系统怎么连接，哪些动作仍靠人工完成 | 人工台账往往藏着真实规则 |

很多真实问题不在会议纪要里。

它们藏在一线人员绕过系统的动作里。

## 核心方法一：三层访谈法

Context 阶段最怕只听一个角色。

只听决策者，项目会变得宏大；只听一线，项目会陷入局部痛点；只听 IT，系统限制会被误当成业务目标。

所以要做三层访谈。

| 层级 | 访谈对象 | 主要问题 |
| --- | --- | --- |
| 决策者 | Sponsor、业务负责人 | 为什么现在要做，成功意味着什么，愿意为哪个结果负责 |
| 业务骨干 | 部门负责人、流程 Owner、核心操作人员 | 当前流程如何运行，哪些指标受影响，哪些环节最常出问题 |
| 技术接口人 | IT、数据、系统管理员、安全合规 | 数据在哪里，系统能不能接，权限和合规边界是什么 |

这不是一个礼貌性的访谈顺序。

它是在把战略目标、真实流程和技术约束放到同一张桌子上。

如果三层说法彼此冲突，不要急着调和。冲突本身就是线索。

很多 FDE 项目的真问题，恰恰出现在这种缝隙里：

- 老板以为已经有流程。
- 一线其实靠人肉兜底。
- IT 说系统从来没支持过。

## 核心方法二：需求挖掘三层法

客户第一次说出来的，通常是表面诉求。

FDE 要继续往下挖。

| 层级 | 典型表达 | FDE 要追问 |
| --- | --- | --- |
| 表面诉求 | 我们想要一个 AI 助手、自动报表、智能客服 | 谁会用？在什么场景用？现在怎么做？ |
| 业务瓶颈 | 响应慢、错误多、人工兜底重、审批卡住 | 慢在哪里？错在哪里？谁在兜底？影响哪个指标？ |
| 根本问题 | 口径不统一、责任边界不清、数据不可用、流程断点 | 这是技术问题、流程问题、组织问题，还是三者叠加？ |

这三层不是为了把问题问复杂。

是为了避免把“客户想要什么功能”误当成“项目应该解决什么问题”。

比如客户说“想让 AI 自动写日报”。表面诉求是自动生成文字，业务瓶颈可能是异常解释太慢，根本问题可能是多个系统指标口径不一致。

如果不往下挖，团队会做一个漂亮的日报生成器。

但客户真正需要的，可能是一套异常归因和责任追踪机制。

## 核心方法三：用证据校验访谈

访谈很重要，但访谈会带着角色立场。

决策者会讲目标，一线会讲痛点，IT 会讲限制。每个人都说了真话，但都只说了自己位置上的真话。

所以 FDE 要尽量回到证据。

| 证据 | 价值 |
| --- | --- |
| 系统日志 | 看真实频率、异常分布和操作路径 |
| 历史工单 | 看重复问题、流转方式和责任边界 |
| 表格和手工台账 | 看系统没覆盖的真实流程 |
| 群聊和邮件 | 看协作断点和临时规则 |
| 用户修改记录 | 看 AI 或系统输出哪里不被信任 |

这件事在用户研究里有一个相近概念，叫 triangulation，也就是用多个来源或多种方法互相校验，提升判断可信度。

放到 FDE 语境里，就是一句话：

访谈告诉你大家怎么理解问题。

证据告诉你问题实际怎么发生。

## 核心方法四：PDD 问题定义文档

Context 阶段结束时，最好留下一个轻量的问题定义文档。

可以叫 PDD，Problem Definition Document。

它不需要很厚，但必须让团队对“问题是什么”形成共识。

| 模块 | 要写清楚什么 |
| --- | --- |
| 背景 | 为什么现在要解决这个问题 |
| 关键角色 | 决策者、使用者、Owner、技术接口人、反对者 |
| 已验证事实 | 有证据支撑的流程、数据、频率、损失 |
| 业务瓶颈 | 当前流程真正卡在哪里 |
| 根本问题 | 为什么这个瓶颈长期存在 |
| 约束条件 | 数据、权限、系统、合规、周期、预算 |
| 成功指标 | 什么变化说明问题被改善 |
| 待验证假设 | 下一阶段要用 Design 或 Demo 验证什么 |

PDD 的价值，不是多一份文档。

它让项目从“大家都觉得有问题”，进入“大家知道要验证哪个问题”。

## 48 小时后要交什么

Context 阶段不追求完整答案。

但它必须输出一个能进入 Design 阶段的初步结构。

| 产物 | 内容 |
| --- | --- |
| 角色地图 | 关键角色、责任、利益和阻力 |
| 现状流程图 | 输入、处理、判断、输出、反馈 |
| 事实约束表 | 已验证事实、解释、判断和约束 |
| 问题模型 | 真实问题、影响范围和价值损失 |
| 待验证假设 | 下一阶段需要用 Demo 或数据验证的点 |

一个好的 Context 输出，不会假装所有问题都搞清楚了。

它会明确告诉团队：哪些已经是事实，哪些只是判断，哪些还需要验证。

## 最容易踩的坑

Context 阶段最常见的坑，不是信息不够。

是太快相信自己已经懂了。

| 陷阱 | 表现 | 后果 |
| --- | --- | --- |
| 过早方案 | 听到需求后马上画架构、选工具、做 Demo | Demo 看起来快，但验证的是错问题 |
| 被客户带偏 | 只围绕客户指定功能讨论 | 忽略真正的流程断点和责任边界 |
| 信息收集过度 | 访谈越来越多，文档越来越厚 | 项目停在调研里，迟迟不能进入验证 |
| 只听单一角色 | 只听老板、一线或 IT | 目标、流程和系统约束互相打架 |

Context 做得太轻，后面会不断返工。

Context 做得太重，项目会停在调研里。

真正好的 FDE，会停在中间：足够理解现场，但不假装自己已经知道全部答案。

## 实战拆解：制造企业的异常分析助手

回到开头那个制造案例。

客户一开始要的是“AI 自动分析异常”。

如果团队第一天就接受这个需求，项目很可能会进入一个熟悉的轨道：

- 整理设备异常知识库。
- 接几张报表。
- 写 Prompt，让模型解释异常原因。
- 做一个异常问答 Demo。

它也许能演示。

但它很可能解决不了车间主管每天面对的混乱。

## 第一次误判：以为问题在分析能力

第一次会议里，运营负责人说了几个听起来很有说服力的理由：

“主管经验差异很大。”

“新主管看不懂异常。”

“每天都有人问为什么停线。”

如果只听这一层，结论很容易变成：需要一个专家助手，把老师傅经验沉淀下来。

这个判断不能说错。

但它太早了。

后来团队分别访谈了三类人：运营负责人、车间主管、IT 数据接口人。

三个人讲出来的是三套世界。

| 角色 | 他说的问题 | 暗含的线索 |
| --- | --- | --- |
| 运营负责人 | 异常分析慢，停线复盘不及时 | 想要管理视角下的效率和责任闭环 |
| 车间主管 | 不知道该信哪张表，经常要去群里问 | 现场事实没有对齐 |
| IT 接口人 | 设备、质检、维修系统不是同一套主数据 | 数据模型和系统边界断裂 |

这时候，项目的重心开始变了。

不是“主管不会分析”。

是“主管拿不到同一个事实版本”。

## 真正的卡点：异常没有被归因

车间主管的一天里，有一个很典型的动作。

某条产线出现异常。

设备系统显示是温度波动，质检系统显示这一批良率下降，维修工单里又有一条还没关闭的保养记录。

单看每个系统，都有信息。

但放在一起，没人能马上回答：

- 这是设备问题，还是物料问题？
- 要不要先停线？
- 谁来处理？
- 处理动作有没有关闭？
- 下次复盘应该算在哪个原因下面？

这就是现场问题。

不是缺一段 AI 总结。

是缺一个能把事实对齐、责任归因、动作追踪串起来的结构。

## Context 怎么把问题重写出来

Context 阶段最后应该把原始需求改写成这样：

> 当产线出现异常时，系统能否对齐设备状态、质检记录和维修工单，形成一个可追踪的异常事实包，帮助车间主管判断异常类别、责任归属和下一步动作？

这句话没有原来的“AI 助手”听起来性感。

但它更接近项目真正要解决的问题。

| 原始说法 | Context 改写后 |
| --- | --- |
| 做 AI 助手 | 建立异常事实包和归因链路 |
| 自动分析异常 | 对齐设备、质检、维修三类证据 |
| 帮主管提效 | 减少跨系统确认和群聊问责 |
| 输出原因解释 | 输出异常类别、责任归属、下一步动作和证据来源 |

讲到这里，AI 仍然有价值。

但它不再是起点。

AI 可以用来解释异常、生成复盘摘要、辅助推荐处理动作。可这些能力要建立在事实结构之上。

否则它只是在一堆没对齐的数据上，说一段看似流畅的话。

## PDD 应该怎么落

这个案例里的 PDD 可以很轻，但要把关键判断写死。

| PDD 模块 | 示例内容 |
| --- | --- |
| 背景 | 异常复盘慢，停线责任难确认，主管依赖人工沟通 |
| 关键角色 | 运营负责人、车间主管、维修负责人、质检负责人、IT 数据接口人 |
| 已验证事实 | 设备、质检、维修系统口径不一致；异常处理大量依赖群聊确认 |
| 业务瓶颈 | 异常发生后，事实对齐和责任归因耗时过长 |
| 根本问题 | 主数据不统一，流程责任边界不清，系统之间没有异常对象 |
| 约束条件 | 三套系统短期不能重构，接口权限需要 IT 审批 |
| 成功指标 | 异常归因时间下降，重复确认减少，异常处理闭环率提升 |
| 待验证假设 | 先选择一条产线、三类高频异常，验证事实包是否能减少人工确认 |

这份 PDD 的意义，是把项目从“做一个 AI 功能”拉回“解决一个现场问题”。

## 下一步才进入 Design

Context 结束后，还不应该马上做完整系统。

下一步进入 Design，要讨论的是：

- 先选哪一条产线？
- 先覆盖哪三类异常？
- 异常事实包包含哪些字段？
- 哪些判断由系统给建议，哪些必须由主管确认？
- 试点成功用什么指标证明？

也就是说，Context 只是把问题找对。

真正的方案取舍，要留给 Design。

这也是 CDEF 每个阶段的边界感。

Context 太急，会把调研变成方案。

Context 太慢，会把项目拖成咨询。

好的 Context，是把足够多的现场事实压缩成一个清楚的问题模型。

## 可以带走的判断

FDE 不是在给答案之前找工具。

FDE 是在给答案之前，先找对问题。

很多 AI 项目失败，不是因为模型不够强，而是因为它从一开始就在回答一个被误写的问题。

Context 的价值，就是把这个问题重写回来。
