# CDEF 和生产门禁如何结合

有些 FDE 项目不是败在做不出来，而是败在太早放大。

合同审查 AI 是一个典型例子。

Demo 阶段，模型能识别付款条款、违约责任和自动续约风险，法务看完也觉得“有帮助”。但如果这时候直接开放给所有业务部门使用，风险会立刻变大：误判怎么办？谁复核？审计日志在哪里？新合同类型进来前谁评测？

所以 FDE 不只需要一套推进方法。

还需要在关键节点停下来问一句：

“证据够不够进入下一阶段？”

> **CDEF 让项目往前走，门禁让项目知道什么时候该停下来补证据。**

## 一句话定义

CDEF 给 FDE 项目提供推进路径。

生产门禁给项目提供阶段判断。

一个解决“怎么往前走”，一个解决“什么时候能进入下一步”。如果只有 CDEF，项目可能推进得很快但证据不足；如果只有门禁，项目可能变成僵硬审批。

两者结合，FDE 才能既灵活又可控。

## CDEF 和门禁分别是什么

CDEF 是方法论闭环：

- Context：定义真实问题。
- Design：切出验证路径。
- Engineer：推进系统运行。
- Feedback：完成接管和反哺。

生产门禁是阶段性质量控制机制。

它不负责替你做项目，而是在关键节点检查：

- 证据是否充分。
- Owner 是否明确。
- 风险是否暴露。
- 回滚是否准备。
- 客户是否能接管。

FDE 项目不适合用重审批卡死，但也不能靠个人判断一路冲到底。

门禁的价值，是让项目扩大影响范围前先补齐证据。

## CDEF 对应哪些门禁

| CDEF 阶段 | 对应门禁 | 核心判断 |
| --- | --- | --- |
| Context | Problem Confirmed | 真实问题是否被定义清楚 |
| Design | Prototype Ready | 是否切出可验证价值闭环 |
| Engineer 早期 | Prototype Exit | Demo 是否验证关键假设 |
| Engineer 中期 | Pilot Ready | 是否能进入有限真实场景 |
| Engineer 后期 | Production Ready | 是否具备生产运行条件 |
| Feedback | Handover Ready | 客户是否能接管并继续演进 |

这样一来，CDEF 不只是四个阶段。

它变成一条带门禁的交付链。

## 每个门禁要看什么

| 门禁 | 必须有的证据 |
| --- | --- |
| Problem Confirmed | 事实约束表、问题模型、业务损失 |
| Prototype Ready | 需求切片画布、验收标准、风险边界 |
| Prototype Exit | Demo 结果、用户反馈、未验证风险 |
| Pilot Ready | 真实用户、数据授权、人工兜底 |
| Production Ready | 评测、权限、监控、回滚、SLO |
| Handover Ready | 接管清单、运行手册、演练记录 |

门禁不是为了阻拦项目。

它是为了避免项目带着隐性风险继续扩大。

## 门禁和 SLO、ADR、Eval 的关系

生产门禁不是一张审批表。

它应该连接工程证据。

| 工程证据 | 对应门禁价值 |
| --- | --- |
| ADR | 说明关键方案为什么这样选，替代方案是什么 |
| Eval / 回放 | 说明系统质量如何被持续验证 |
| SLO | 说明上线后服务要达到什么可靠性目标 |
| 告警和事件响应 | 说明出问题后谁知道、谁处理、怎么恢复 |
| 接管清单 | 说明客户是否具备独立运行能力 |

Google SRE 的实践强调用 SLO 连接用户期望和系统可靠性。Thoughtworks 推荐轻量 ADR 来保留架构取舍。OpenAI Evals 强调用评测样本和标准持续衡量模型行为。

这些方法放到 FDE 项目里，最终都服务于同一件事：

让生产门禁有证据，而不是靠感觉。

## 最小门禁矩阵

| 阶段 | 进入条件 | 退出标准 |
| --- | --- | --- |
| Context | 有业务 Sponsor 和初始问题 | 真实问题、约束和价值损失被记录 |
| Design | 问题模型已形成 | 价值切片、方案取舍和验收标准明确 |
| Engineer | 切片可验证 | Demo、试点、生产证据逐步补齐 |
| Feedback | 系统进入真实使用 | 指标复盘、客户接管、产品反哺完成 |

这张矩阵可以很轻。

但不能没有。

没有门禁，项目会靠热情和个人经验推进；有了门禁，项目才开始变得可复查、可教学、可复制。

## 实战拆解：合同审查 AI 怎么过门禁

回到开头那个合同审查 AI。

一家企业法务团队提出需求：

“我们想做一个合同审查 AI，帮法务提高初审效率。”

这是一个典型 FDE 场景。

业务价值清楚，但风险也很高。合同审查涉及法律责任、客户关系、合规风险和审批流程。

如果只按 CDEF 往前推，团队可能很快做出 Demo。

但如果没有门禁，Demo 很容易被误解成“可以上线”。

## Context：先确认真实问题

访谈后发现，法务最痛的不是所有合同都慢，而是采购合同里的付款条款、违约责任和自动续约条款经常漏审。

Problem Confirmed 门禁要求留下：

- 典型合同样本。
- 高频风险条款清单。
- 当前初审耗时。
- 漏审造成的业务损失。
- 法务 Owner 和业务 Sponsor。

没有这些证据，就不能进入方案设计。

这听起来像是在拖慢项目。

但在高风险场景里，不先确认问题和责任边界，后面所有工程速度都可能是在扩大风险。

## Design：切出可验证场景

Design 没有直接做“全合同审查 AI”。

它切出第一个场景：

“采购合同付款条款审查。”

Prototype Ready 门禁要求留下：

- 需求切片画布。
- 付款条款风险分类。
- 评测样本。
- 人工确认边界。
- 不自动给法律结论的风险说明。

这一步的关键，是先验证一个高频、边界清楚、风险可控的切片。

## Engineer：Demo 不能直接进生产

Demo 能识别付款条款风险后，团队没有马上扩大。

Prototype Exit 门禁先看：

- Demo 在历史合同上的召回和误报。
- 法务修改意见。
- 未覆盖条款类型。
- 模型不确定性样本。

Pilot Ready 门禁再看：

- 真实合同授权。
- 试点法务名单。
- 人工复核流程。
- 审计日志。
- 失败样本记录。

Production Ready 门禁最后看：

- 评测集达标。
- 权限和日志完整。
- 高风险条款转人工。
- 误判回滚和撤回机制。
- SLO、告警和响应 Owner。

每个门禁都让项目风险逐步外显。

## Feedback：交接不是发链接

系统上线后，Handover Ready 门禁要求客户能独立运行：

- 法务能解释模型适用边界。
- 法务 Owner 能复查失败样本。
- 知识库和条款库有人维护。
- 审计日志可追溯。
- 新合同类型进入前有评测流程。
- 风险条款模板能反哺产品。

这时 FDE 才能逐步退出日常运行。

不是因为项目结束了。

而是客户真的接住了。

## 可以带走的判断

CDEF 让合同审查 AI 从模糊需求走到生产系统。

生产门禁让它没有在错误时间扩大风险。

FDE 项目需要速度，但更需要知道什么时候停下来补证据。

> **没有门禁的 CDEF，容易变成一路狂奔；没有 CDEF 的门禁，容易变成原地审批。**

真正好的结合，是让门禁变轻，但让证据变硬。

不是为了审批而审批，而是为了让每一次扩大范围、增加权限、进入生产，都有清楚理由。
