# Feedback 反馈：从上线到产品反哺

很多项目把上线当成结束。FDE 不能这样看。

上线只是系统第一次进入真实组织。它会遇到新用户、新异常、新数据分布、新责任边界。真正的学习，往往在上线后才开始。

从定义上看，Feedback 是 CDEF 的第四阶段，用来把生产运行中的业务结果、用户行为、失败样本和客户接管经验，反哺到产品、平台、方法论和下一轮交付中。

> **一句可以带走的判断：FDE 的复利不在一次项目交付，而在每次现场学习都能留下可复用资产。**

## Feedback 看什么

Feedback 不只是收集用户意见。

它至少要看四类反馈：

| 反馈类型 | 要回答的问题 |
| --- | --- |
| 业务指标 | 是否真的改善了时间、成本、质量或风险 |
| 用户行为 | 用户是否采用，在哪些地方修改或绕开系统 |
| 系统质量 | 失败样本、延迟、成本、准确率是否稳定 |
| 接管情况 | 客户是否能解释、操作、回滚和继续演进 |

只听用户满意度是不够的。FDE 要同时看结果、行为和运行证据。

## 失败样本是最重要的资产

AI 项目里，失败样本比成功样本更有价值。

失败样本能告诉团队：

- 哪些问题模型理解错了。
- 哪些知识库内容缺失。
- 哪些权限边界设计不合理。
- 哪些场景必须人工确认。
- 哪些产品能力应该抽象出来。

如果失败样本没有被收集，系统就很难持续变好。

## 产品反哺怎么发生

不是每个现场需求都应该进入产品。

Feedback 阶段要判断：

| 现场发现 | 处理方式 |
| --- | --- |
| 单一客户特殊流程 | 保留为项目配置 |
| 多客户重复出现 | 抽象为产品能力 |
| 高风险但低频 | 做成审批或人工接管机制 |
| 高频通用问题 | 做成模板、组件或平台能力 |

FDE 的重要价值，就是把客户现场里的“个案”识别成“模式”。

## 复盘表怎么写

一个轻量复盘表可以包括：

| 模块 | 内容 |
| --- | --- |
| 原始假设 | 项目一开始相信什么 |
| 验证结果 | 哪些被证明，哪些被推翻 |
| 业务指标 | 关键指标变化 |
| 失败样本 | 主要失败类型和原因 |
| 客户接管 | 哪些已接住，哪些还依赖 FDE |
| 产品机会 | 哪些能力值得沉淀 |
| 下一步 | 修复、扩大、产品化或停止 |

复盘不是写总结，而是为下一次更快、更稳地交付创造条件。

## 一个简单案例

客服 AI 助手上线后，数据显示平均响应时间下降了，但人工修改率仍然很高。

Feedback 进一步分析发现：

- 政策类问题效果好。
- 订单异常类问题经常答偏。
- 客服修改主要集中在“补充订单状态解释”。
- 订单系统字段口径不稳定。

这时产品反哺不是“继续优化 Prompt”这么简单，而可能是：

- 建立订单状态标准解释模板。
- 增加订单字段质量检查。
- 把异常订单强制转人工。
- 把客服修改内容回流评测集。

## Feedback 的最终目标

Feedback 阶段的目标不是证明 FDE 做得对，而是让组织学到东西。

客户组织学到如何运行系统，产品团队学到哪些能力可复用，工程团队学到哪些架构和评测模式有效，FDE 团队学到下一次怎样更快进入现场。

这也是 CDEF 和普通项目流程最大的差别：它不是从需求走到上线，而是从现场走到组织学习。
