# Feedback 反馈：从上线到产品反哺

系统上线后，最容易出现一句话：

“客户反馈挺好的。”

这句话听起来像好消息，但在 FDE 项目里，它还不够。

一个客服 AI 助手上线第一周，平均响应时间下降了 28%，客服主管也说“确实快了”。如果项目到这里就收尾，团队很容易把它写进成功案例。

但继续看数据才发现：人工修改率仍然很高，复杂订单处理时间几乎没变。

这时问题来了。

上线到底证明了什么？又暴露了什么？

> **上线不是终点。上线只是系统第一次接受真实组织的考试。**

## 一句话定义

Feedback 是 CDEF 的第四阶段。

它接在 Engineer 之后，负责把系统上线后的业务结果、用户行为、失败样本和客户接管经验，反哺到产品、平台、模板和下一轮交付中。

很多项目把上线当成结束。

FDE 不能这样看。

上线只是系统第一次进入真实组织。它会遇到新用户、新异常、新数据分布、新责任边界。真正的学习，往往在上线后才开始。

## Feedback 解决什么问题

Feedback 不只是收集用户意见。

它要回答四个问题：

| 问题 | 要看的证据 |
| --- | --- |
| 业务是否真的改善 | 时间、成本、质量、风险、收入等指标变化 |
| 用户是否真的采用 | 使用频率、采纳率、修改率、绕开行为 |
| 系统是否稳定 | 失败样本、延迟、成本、准确率、告警 |
| 客户是否能接管 | Owner、运行手册、回滚演练、复盘机制 |

只听用户满意度是不够的。

FDE 要同时看结果、行为和运行证据。

## 价值验证三条线

Feedback 阶段至少要同时验证三条线：

| 线索 | 看什么 | 不能只看什么 |
| --- | --- | --- |
| 业务指标 | 时间、成本、质量、风险是否改善 | 不能只看演示反馈 |
| 用户采纳 | 用户是否真的进入流程，是否持续使用 | 不能只看口头认可 |
| 系统稳定性 | 准确率、延迟、成本、失败率、告警是否稳定 | 不能只看一次成功运行 |

这三条线缺一条，项目都不算真正跑通。

业务指标好但没人用，说明流程没有进入组织；用户愿意用但系统不稳，说明风险还没接住；系统很稳但指标没变，说明可能解决了假问题。

## 失败样本是资产

AI 项目里，失败样本比成功样本更有价值。

失败样本能告诉团队：

- 哪些问题模型理解错了。
- 哪些知识库内容缺失。
- 哪些权限边界设计不合理。
- 哪些场景必须人工确认。
- 哪些产品能力应该抽象出来。

如果失败样本没有被收集，系统就很难持续变好。

OpenAI 的 Evals 思路强调用样本和评价标准持续衡量系统行为。放到 FDE 项目里，失败样本不是事故垃圾，而是下一轮评测集、回归测试和产品改进的来源。

## 客户接管标准

Feedback 阶段要判断客户是否真的接住系统，而不是 FDE 还在背后兜底。

客户能独立运行，至少意味着：

- 能解释系统适用和不适用的场景。
- 能查看关键指标、日志或失败样本。
- 能处理常见异常，知道何时升级。
- 能执行回滚、降级或转人工流程。
- 能更新基础配置、知识库、样本或模板。
- 能判断下一轮迭代是否值得做。

如果客户离开 FDE 就无法运行，这个项目还没有完成交接。

它只是完成了上线。

## 产品反哺怎么发生

不是每个现场需求都应该进入产品。

Feedback 阶段要判断哪些是个案，哪些是模式。

| 现场发现 | 处理方式 |
| --- | --- |
| 单一客户特殊流程 | 保留为项目配置 |
| 多客户重复出现 | 抽象为产品能力 |
| 高风险但低频 | 做成审批或人工接管机制 |
| 高频通用问题 | 做成模板、组件或平台能力 |

FDE 的重要价值，就是把客户现场里的“个案”识别成“模式”。

## 复盘表怎么写

一个轻量复盘表可以包括：

| 模块 | 内容 |
| --- | --- |
| 原始假设 | 项目一开始相信什么 |
| 验证结果 | 哪些被证明，哪些被推翻 |
| 业务指标 | 关键指标变化 |
| 失败样本 | 主要失败类型和原因 |
| 客户接管 | 哪些已接住，哪些还依赖 FDE |
| 产品机会 | 哪些能力值得沉淀 |
| 下一步 | 修复、扩大、产品化或停止 |

复盘不是写总结。

复盘是为下一次更快、更稳地交付创造条件。

## 常见误区

| 误区 | 表现 | 后果 |
| --- | --- | --- |
| 上线即结束 | 系统上线后团队撤场 | 客户无法接管，问题无人处理 |
| 只看满意度 | 用户说好就算成功 | 没有业务指标和运行证据 |
| 不收失败样本 | 错误被临时修掉 | 系统无法持续改进 |
| 所有需求都产品化 | 客户特例也进入主产品 | 产品变复杂，平台能力被污染 |

Feedback 做得好，FDE 会逐渐从日常运行里退出。

这不是甩手。

这是系统、流程、证据和 Owner 已经被客户组织接住。

## 实战拆解：客服 AI 助手上线以后

回到开头那个客服 AI 助手。

上线后，第一周数据看起来不错。

平均响应时间下降了 28%。

客服主管很满意。

如果项目到这里就结束，团队很容易宣布成功。

但 Feedback 阶段继续往下看，发现了另一个问题：人工修改率仍然很高。

也就是说，AI 让客服更快拿到了草稿，但客服还是经常要改。

## 三条线一起看，结论变了

团队把数据拆成三条线：

| 线索 | 发现 |
| --- | --- |
| 业务指标 | 平均响应时间下降，但复杂订单处理时间没有明显变化 |
| 用户采纳 | 政策类问题采纳率高，订单异常类问题修改率高 |
| 系统稳定性 | 知识库回答稳定，订单状态解释经常答偏 |

这时结论就不是“Prompt 还不够好”。

真实问题是：订单系统里的状态字段口径不稳定，客服要补充解释，才能让用户听懂。

这就是 Feedback 阶段最有价值的地方。

它会把一个看起来像“模型效果问题”的现象，重新拉回业务流程、数据口径和用户采纳里看。

## 失败样本带来产品机会

团队收集了 200 条人工修改记录。

发现客服最常改的不是语气，而是订单状态解释：

- “待审核”到底是平台审核还是商家审核？
- “退款中”是否代表钱已经退回？
- “异常拦截”应该怎么解释给用户？

于是产品反哺不再是“继续优化 Prompt”。

而是三件更具体的事：

- 建立订单状态标准解释模板。
- 增加订单字段质量检查。
- 把异常订单强制转人工。

这就是 Feedback 的价值。

它把一次上线后的问题，变成了下一轮产品能力。

## 客户真正接住了什么

最后交接时，FDE 没有只交一个系统链接。

而是交了这些东西：

- 政策类问题评测集。
- 订单异常失败样本库。
- 客服修改记录分析表。
- 客户 Owner 每周复盘流程。
- 高风险订单转人工规则。
- 知识库更新和回归测试方法。

这些东西让客户能继续运行系统。

也让产品团队知道下一步该抽象什么。

## 可以带走的判断

Feedback 阶段的目标不是证明 FDE 做得对。

是让组织学到东西。

客户组织学到如何运行系统，产品团队学到哪些能力可复用，工程团队学到哪些架构和评测模式有效，FDE 团队学到下一次怎样更快进入现场。

FDE 的复利不在一次项目交付。

而在每次现场学习都能留下可复用资产。

如果上线后没有失败样本、没有复盘指标、没有客户接管、没有产品反哺，这个项目就只是跑完了一次。

真正好的 Feedback，会让下一次交付变得更快、更稳、更有判断。
