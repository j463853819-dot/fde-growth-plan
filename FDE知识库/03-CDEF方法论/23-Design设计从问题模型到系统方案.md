# Design 设计：从问题模型到系统方案

Context 阶段把问题看清楚之后，FDE 不能立刻做完整系统。

真实现场通常太复杂：角色多、系统多、数据脏、权限严、目标还会变化。如果一上来就设计大而全的方案，很容易把项目推向漫长定制。

Design 阶段的任务，是把问题模型切成一个最小但完整的价值闭环。

从定义上看，Design 是 CDEF 的第二阶段，用来把现场问题转化为可验证的系统方案。它包括需求切片、方案取舍、验收标准、风险边界和下一阶段工程计划。

> **一句可以带走的判断：Design 阶段不是画最完整的架构，而是找到最值得验证的那条路径。**

## 从问题模型到价值切片

一个问题模型通常很大，不能直接变成开发任务。

比如“客服效率低”可能包含知识库、订单权限、工单分类、质检标准、人员培训等多个问题。Design 要做的是选出第一个最值得验证的切片。

一个好切片要满足四个条件：

| 条件 | 说明 |
| --- | --- |
| 频率足够高 | 不是偶发问题 |
| 价值足够明确 | 能影响时间、成本、质量或风险 |
| 数据可以获得 | 至少能拿到必要输入 |
| 风险可控 | 出错后能人工兜底 |

## 需求切片的写法

不要写：“做一个客服 AI 助手。”

更好的写法是：

“当客服处理退款咨询时，系统读取订单状态、退款政策和历史相似案例，生成建议回复和引用来源，由客服确认后发送，目标是把平均响应时间从 8 分钟降到 4 分钟以内。”

这个切片包含：

- 角色：客服。
- 场景：退款咨询。
- 输入：订单状态、政策、历史案例。
- 处理：检索、生成、引用。
- 输出：建议回复。
- 边界：人工确认后发送。
- 指标：响应时间。

## 方案设计要写清取舍

FDE 的方案很少只有一种。

| 方案 | 优点 | 风险 |
| --- | --- | --- |
| 只做知识库问答 | 快速上线 | 不进入真实流程 |
| 做客服工作台插件 | 贴近工作流 | 集成成本更高 |
| 做自动回复 Agent | 效率最高 | 权限和责任风险大 |

Design 阶段要写清楚为什么先选某条路径。很多时候，FDE 不选最自动化的方案，而是先选最能验证价值且风险可控的方案。

## 验收标准要前置

如果没有验收标准，Demo 很容易变成“看起来不错”。

Design 阶段就要定义：

- 什么样的输出算合格？
- 哪些场景必须转人工？
- 试点指标是什么？
- 失败样本如何记录？
- 下一阶段进入条件是什么？

| 验收项 | 示例 |
| --- | --- |
| 质量 | 评测集通过率不低于 85% |
| 采用 | 一线客服建议采纳率超过 60% |
| 效率 | 平均响应时间下降 30% |
| 风险 | 高金额退款必须人工确认 |
| 接管 | 客户 Owner 能复查失败样本 |

## Design 的最小产物

| 产物 | 用途 |
| --- | --- |
| 需求切片画布 | 定义最小价值闭环 |
| 方案取舍表 | 记录为什么选当前方案 |
| 风险边界清单 | 标明暂不自动化或必须人工确认的部分 |
| 验收标准 | 定义 Demo、试点和生产的判断标准 |
| 工程计划 | 指向 Engineer 阶段的实现路径 |

Design 的好坏，决定后面的工程是验证真实价值，还是只是在堆功能。

在 AI 时代，模型能力会诱惑团队做更大的系统。FDE 需要反过来克制：先切小，先验证，先让价值闭环跑起来。
