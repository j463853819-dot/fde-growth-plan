# Design 设计：从问题模型到系统方案

Design 是 CDEF 的第二阶段。

它接在 Context 之后，负责把现场问题翻译成一个可验证、可实现、可进入试点的系统方案。

如果说 Context 的任务是看清现场，Design 的任务就是做取舍：不是把客户说过的所有需求都装进方案，而是在一堆混杂的信息里，找到第一条最值得验证的价值闭环。

> **Design 阶段不是把未来一次性画完，而是为下一步验证选择一条可信路径。**

## 一句话定义

Design 是把“客户现场的真实问题”转化为“系统方案、技术取舍、验收指标和风险边界”的过程。

它不是单纯写方案，也不是画架构图。

它更像一次工程前的判断：这件事先做哪一小段，为什么这样做，怎么证明它有效，哪些地方必须先留给人。

## 它解决什么问题

Context 阶段通常会带回很多信息：角色、流程、系统、数据、约束、目标、阻力和价值损失。

但这些信息还不能直接变成开发任务。

比如客户说“客服效率低”，背后可能同时有知识库不更新、订单权限查不到、工单分类混乱、质检标准不一致、复杂问题没人接手。

如果团队一上来就把这些都做进系统，项目很快会变成漫长定制。

Design 要先回答三个问题：

| 问题 | 要交代清楚什么 |
| --- | --- |
| 先验证什么 | 从大问题里切出第一个价值闭环 |
| 怎么验证 | 选择合适的系统形态、数据输入和人工边界 |
| 如何判断成败 | 提前定义 Demo、试点和生产门禁 |

所以 Design 不是“方案包装”。

它是项目进入工程前的判断系统。

## 核心方法一：从问题模型到价值切片

一个好的价值切片，不能只是一个功能点。

它至少要包含：

- 明确用户：谁会使用？
- 触发场景：什么时候发生？
- 输入数据：系统需要什么信息？
- 关键判断：系统要帮人做什么判断？
- 输出结果：用户拿到什么？
- 人工边界：哪些动作必须由人确认？
- 验收指标：怎样算有效？

一个切片通常要同时满足四个条件：

| 条件 | 判断方式 |
| --- | --- |
| 频率足够高 | 不是偶发问题，现场每天或每周都会遇到 |
| 价值足够明确 | 能影响时间、成本、质量、收入或风险 |
| 数据可以获得 | 至少能拿到必要输入，不依赖遥远的系统改造 |
| 风险可控制 | 出错后能人工兜底，不会直接放大业务损失 |

FDE 在 Design 阶段最重要的克制，是不把第一个切片做成完整系统。

先让一条价值链跑起来。

## 核心方法二：技术决策四维评估

同一个问题，可能有很多解法。

一个退款咨询问题，可以做知识库问答，可以做客服工作台插件，可以做自动回复 Agent，也可以先做一个后台质检工具。

Design 阶段要写清楚为什么选这条路，而不是那条路。

可以用四个维度评估：

| 维度 | 要问的问题 | 如果忽略 |
| --- | --- | --- |
| 可行性 | 数据、接口、权限、模型能力是否支撑 | 方案落不到真实环境 |
| 成本 | 开发、运行、维护、人工审核成本是多少 | Demo 便宜，生产很贵 |
| 时间 | 多久能验证关键假设，多久能试点 | 项目拖成长周期定制 |
| 可维护性 | 客户能否理解、运营、接管和继续迭代 | 系统长期依赖 FDE |

这四个维度不是为了选出理论最优方案。

它们是为了找到当前阶段最值得验证、也最能控制风险的路径。

## 核心方法三：把关键取舍写成 ADR

Design 阶段最容易丢的东西，不是方案本身，而是“为什么当时这么选”。

ADR，也就是 Architecture Decision Record，适合用来记录关键技术和架构取舍。它通常不需要很长，但要说清楚：

| 内容 | 说明 |
| --- | --- |
| 背景 | 当时面对什么问题和约束 |
| 决策 | 最终选择了什么方案 |
| 备选项 | 还考虑过哪些方案 |
| 理由 | 为什么当前阶段选择它 |
| 后果 | 会带来什么收益、代价和后续影响 |

对 FDE 来说，ADR 不只是工程文档。

它还是客户接管系统时的解释器。新人进来后，看到的不只是代码和接口，而是当时那组限制条件下的判断。

## 核心方法四：不完全信息下设计

FDE 很少在信息完整时开始设计。

现场总会缺数据、缺接口、缺权限、缺共识。

这时不要等到所有问题都清楚再动手，而要把不确定性写进设计里：

- 对不确定数据，先做样本验证和质量分级。
- 对不确定流程，先选一个低风险场景试点。
- 对不确定权限，先采用人工确认或只读模式。
- 对不确定指标，先定义可观测代理指标。
- 对不确定责任，先在 RACI 或接管清单里写清楚。

好的 Design 不是没有风险。

是知道风险在哪里，下一阶段如何暴露和处理。

## Design 的关键产物

Design 阶段结束时，至少要留下这些东西：

| 产物 | 用途 |
| --- | --- |
| 需求切片画布 | 定义最小价值闭环 |
| 方案取舍表 | 记录为什么选当前方案 |
| ADR 架构决策记录 | 记录关键技术取舍、替代方案和决策原因 |
| 风险边界清单 | 标明暂不自动化或必须人工确认的部分 |
| 验收标准 | 定义 Demo、试点和生产的判断标准 |
| 工程计划 | 指向 Engineer 阶段的实现路径 |

如果要给客户或内部团队正式评审，可以再整理成三类交付物：

| 交付物 | 内容 |
| --- | --- |
| 方案文档 | 场景、角色、输入输出、系统边界、集成方式 |
| 成功指标 | 质量、效率、采用率、风险、接管的判断标准 |
| 风险清单 | 数据、权限、合规、模型、流程、组织责任的风险 |

这些不是文档装饰。

它们决定后面的工程是在验证一个清楚假设，还是在补一个含糊需求。

## 常见误区

| 误区 | 表现 | 后果 |
| --- | --- | --- |
| 方案过大 | 一上来设计完整平台 | 项目周期变长，关键假设迟迟无法验证 |
| 自动化过猛 | 直接做自动回复或自动执行 | 权限、责任和信任风险失控 |
| 指标后置 | Demo 做完才讨论怎么验收 | 演示好看，但无法判断是否有效 |
| 只看技术可行 | 忽略客户能否接管 | 系统长期依赖 FDE |
| 只写方案不写取舍 | 文档很完整，但没人知道为什么这样选 | 后续迭代容易反复推倒 |

Design 的关键不是把方案讲得漂亮。

是让下一步工程有边界、有指标、有退路。

## 实战拆解：客户想要一个客服 AI 助手

一个典型场景是这样的。

消费品公司的客服负责人找到团队，说得很直接：

“我们想做一个 AI 助手，帮客服自动回答退款问题。”

如果只听这句话，这个需求几乎像是送到手边的 AI 项目。

退款问题高频，规则看起来清楚，知识库也有。做一个 RAG 问答，接上客服话术，再让模型生成回复，Demo 大概率很好看。

我以前也会下意识这么想：这不就是知识库问答吗？

但 Design 阶段真正要警惕的，恰恰是这种“看起来很像”的需求。

因为它太容易让团队跳过判断，直接进入实现。

## 第一次误判：以为问题在话术

一开始，团队以为客服慢，是因为客服不知道怎么回复。

于是很自然地想到三个功能：

- 把退款政策整理进知识库。
- 让客服输入用户问题后，生成建议回复。
- 给回复附上引用来源，方便客服检查。

这套方案没错。

问题是，它只解决了“怎么说”，没有解决“能不能退”。

后来访谈一位资深客服时，才发现真正耗时的动作不是写话术，而是在三个系统之间来回切：

- 订单系统里看支付、发货、签收、售后状态。
- 政策表里查不同渠道、不同品类、不同时间窗口的退款规则。
- 历史工单里找类似案例，判断这类情况以前是怎么处理的。

这就尴尬了。

如果 AI 只是帮她把一句话写得更顺，她依然要自己查系统、自己判断、自己担责。

效率不会真正起来。

## 问题重写：不是“自动回答”，而是“辅助判断”

Design 阶段要做的第一件事，就是把客户的需求重新写一遍。

原始需求是：

> 做一个 AI 助手，自动回答退款问题。

重写后的问题应该更接近：

> 当一线客服处理退款咨询时，系统能否读取订单状态、退款政策和历史相似案例，生成带依据的处理建议，由客服确认后发送，并把平均响应时间从 8 分钟降到 4 分钟以内？

这句话变长了。

但它变清楚了。

| 元素 | 设计结果 |
| --- | --- |
| 用户 | 一线客服 |
| 场景 | 退款咨询 |
| 输入 | 订单状态、退款政策、历史相似案例 |
| 关键判断 | 当前订单是否满足退款条件 |
| 输出 | 处理建议、回复草稿、引用来源 |
| 人工边界 | 客服确认后发送，高风险订单转人工主管 |
| 指标 | 响应时间、采纳率、错误率、转人工比例 |

这就是 Design 的第一层价值：把一个听起来正确的功能需求，改写成一个可验证的业务闭环。

## 方案取舍：为什么不第一天就做自动回复 Agent

讲到这里，很多人会问：

既然目标是提效，为什么不直接让 Agent 自动回复？

这正是 Design 要回答的问题。

| 方案 | 优点 | 风险 |
| --- | --- | --- |
| 知识库问答 | 最快做出 Demo，集成少 | 不进入真实流程，价值可能很浅 |
| 客服工作台插件 | 贴近客服动作，能读订单和政策 | 需要系统集成，周期更长 |
| 自动回复 Agent | 理论效率最高 | 涉及金额、客诉、责任归属，早期风险大 |
| 后台质检助手 | 对生产链路影响小 | 不能直接改善一线响应速度 |

如果只看“AI 感”，自动回复 Agent 最诱人。

但退款场景有金额、有情绪、有品牌风险。第一阶段就自动回复，相当于把一个还没被验证的判断系统直接推到客户面前。

我的体感是，FDE 项目里最危险的不是做不出来。

是做得太快，而且快在一个组织还接不住的地方。

所以这个项目更适合先做客服工作台插件：

- 系统负责读数据、找依据、生成建议。
- 客服负责确认、修改和发送。
- 主管负责复查高金额、异常订单、政策冲突样本。

这不是保守。

这是把自动化放在组织能承责的位置上。

## ADR：把“为什么这样选”留给后面的人

这个决策要写进 ADR。

否则两周后、两个月后，很容易有人重新问：

“为什么不直接自动回复？这样效率不是更高吗？”

一份轻量 ADR 可以这样写：

| ADR 项 | 内容 |
| --- | --- |
| 背景 | 退款咨询高频，但涉及订单状态、政策例外、金额风险和客诉风险 |
| 决策 | 第一阶段做客服工作台插件，不做自动回复 Agent |
| 备选项 | 知识库问答、自动回复 Agent、后台质检助手 |
| 决策理由 | 工作台插件能进入真实流程，同时保留人工确认和风险兜底 |
| 后果 | 需要接订单系统和政策库，但能更真实地验证效率、采纳率和错误率 |

ADR 的好处，不是让文档显得专业。

它是在保存当时的判断现场。

FDE 做的很多决策，都是在信息不完整、时间很紧、风险又不能完全消除的情况下做出来的。只留下结果，不留下原因，后面的人很难继续迭代。

## 验收标准：别让 Demo 停在“看起来还不错”

AI 项目最容易出现一句话：

“效果还不错。”

但这句话没有用。

不错到什么程度？谁觉得不错？能不能上线？能不能接管？出了错谁发现？

Design 阶段要把这些提前写清楚。

| 验收项 | 示例标准 |
| --- | --- |
| 质量 | 评测集通过率不低于 85%，关键政策问题不能错 |
| 采用 | 客服建议采纳率超过 60% |
| 效率 | 平均响应时间下降 30% 以上 |
| 风险 | 高金额、异常订单、政策冲突必须转人工 |
| 可观测 | 每次建议保留输入、引用来源、模型输出和客服最终动作 |
| 接管 | 客户 Owner 能复查失败样本，并更新政策知识 |

这里有一个细节很重要：指标不能只看模型回答得漂不漂亮。

FDE 更关心的是现场链路有没有变短，人的判断有没有被支持，系统错误有没有被发现，客户团队能不能继续运营。

## 最后留下什么

Design 阶段结束时，这个项目不应该只留下一份“客服 AI 助手方案”。

它至少应该留下：

- 一张退款咨询需求切片画布。
- 一份方案取舍表。
- 一份 ADR：为什么先做工作台插件，而不是自动回复 Agent。
- 一份风险边界清单：高金额、异常订单、政策冲突必须转人工。
- 一套验收标准：质量、采用、效率、风险、可观测和接管。
- 一份 Engineer 阶段计划：接订单系统、接政策库、建评测集、做人工确认流程。

到这个时候，项目才真正可以进入工程。

不是因为方案已经完美。

而是因为下一步要验证什么，已经清楚了。

## 可以带走的判断

Design 的价值，不是让方案看起来更像方案。

它真正的价值，是防止团队在错误方向上跑得太快。

模型能力会诱惑人去做更大的系统、更自动化的流程、更完整的平台。

但 FDE 要反过来克制。

先切小，先验证，先让价值闭环跑起来。

能把一个漂亮需求压缩成一个可验证闭环，这才是 Design 阶段真正的功夫。
