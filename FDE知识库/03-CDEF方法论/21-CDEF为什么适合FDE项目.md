# CDEF 为什么适合 FDE 项目

客户说“我们想做一个销售助手”的时候，项目看起来已经很清楚了。

用户是销售，目标是提高线索转化率，产品形态是 AI 助手。

如果团队顺着这个需求往下做，几天内就能做出 Demo：输入客户名称和历史沟通记录，AI 生成下一步跟进建议。

但现场访谈后，团队发现真正的问题不是销售不会写话术，而是线索优先级混乱。高价值线索和普通线索混在一起，销售每天先跟谁，主要靠经验。

这时项目就不能再叫“做销售助手”。

它应该被重新写成：如何帮助销售判断哪些线索值得优先跟进，以及为什么。

这就是 CDEF 的用处。

它不是让项目变慢，而是让团队在很快推进时，仍然知道自己到底在验证什么。

> **FDE 的能力，不是把客户说的东西更快做出来，而是把客户还没说清楚的问题推进成系统能力。**

## 一句话定义

CDEF 是一套面向 FDE 项目的工作方法。

它把一个现场型 AI / 软件项目拆成四个阶段：Context、Design、Engineer、Feedback。

- **Context**：进入现场，看清真实问题。
- **Design**：把问题切成可验证的价值闭环。
- **Engineer**：把 Demo 推进到试点、生产和接管。
- **Feedback**：用运行结果反哺产品、平台和下一轮交付。

它不是传统项目管理流程，也不是咨询方法论。

它更像 FDE 在不确定现场里的判断骨架。

## CDEF 解决什么问题

FDE 项目最难的地方，不是技术栈复杂，而是问题一开始就不稳定。

客户说的是需求，现场暴露的是约束，管理层要的是结果，工程团队面对的是系统边界。很多项目失败，不是因为没人努力，而是因为团队太早进入解决方案，太晚发现真正的问题。

CDEF 要解决的，就是这类断裂。

| 常见断点 | CDEF 的处理方式 |
| --- | --- |
| 客户表达模糊 | Context 先还原事实、流程、角色和约束 |
| 方案过早膨胀 | Design 切出最小但完整的价值闭环 |
| Demo 难进生产 | Engineer 补齐评测、权限、门禁、回滚和接管 |
| 经验无法复用 | Feedback 把现场学习反哺产品、模板和方法 |

传统项目通常假设需求相对稳定。

FDE 项目恰恰相反。

它经常从一个模糊愿望开始：“我们想用 AI 提升效率”“我们想做一个助手”“我们想自动化这个流程”。CDEF 的价值，就是把这些愿望逐步推进成可验证、可运行、可接管的系统能力。

## 四个阶段分别看什么

| 阶段 | 核心问题 | 最小产物 |
| --- | --- | --- |
| Context | 真实问题是什么 | 事实约束表、角色地图、问题陈述 |
| Design | 先验证哪条路径 | 需求切片画布、方案取舍、验收阈值 |
| Engineer | 怎么进入真实运行 | Demo、评测报告、ADR、上线门禁 |
| Feedback | 现场学习沉淀成什么 | 指标复盘、接管记录、产品反哺清单 |

这四个阶段不是瀑布流程。

真实项目里，CDEF 会循环。Engineer 阶段发现数据不可用，可能要回到 Context；Feedback 阶段发现用户没有采纳，可能要回到 Design 重新切片。

所以 CDEF 的重点不是“按顺序走完”。

是让团队知道现在处在哪个判断层。

## 为什么特别适合 AI 时代

AI 让 Demo 变得更容易，也让误判变得更容易。

一个模型接上知识库，几小时就能演示；一个 Agent 接上工具，几天就能跑流程。越是这样，越需要 CDEF 约束项目：

- Context 防止把“想做 AI”误读成真实问题。
- Design 防止把 AI 能力做成没有流程位置的工具。
- Engineer 防止把 Demo 直接推上生产。
- Feedback 防止一次项目结束后经验散掉。

AI 项目最危险的地方，是“看起来能跑”。

CDEF 关心的是：它是否真的进入了业务流程，是否能被评测，是否有权限边界，是否能回滚，是否能被客户接管。

## 常见误区

| 误区 | 表现 | 后果 |
| --- | --- | --- |
| 把 CDEF 当流程图 | 每阶段填表，但不改变判断 | 文档变多，项目没变清楚 |
| Context 太轻 | 客户说什么就做什么 | Demo 验证错问题 |
| Design 太大 | 一上来设计完整平台 | 项目周期拉长，风险后置 |
| Engineer 太快 | Demo 直接进生产 | 权限、评测、回滚和接管缺失 |
| Feedback 缺位 | 上线后就散场 | 经验无法复用，产品无法反哺 |

好的 CDEF，不是把项目管死。

是让项目每一步都有证据、有边界、有下一步。

## 实战拆解：客户说“我们想做销售助手”

回到开头那个销售助手项目。

一家 B2B 软件公司的销售负责人提出需求：

“我们想做一个销售助手，帮销售写跟进建议，提高线索转化率。”

这句话听起来很完整。

有用户：销售。

有目标：提高转化率。

有产品形态：销售助手。

如果团队直接进入实现，很快就能做出一个 Demo：输入客户名称和历史沟通记录，AI 生成下一步跟进话术。

但 FDE 不能只问“怎么做助手”。

要先问：销售转化率低，到底低在哪里？

## Context：先看线索怎么流动

Context 阶段访谈了销售主管、一线销售和 CRM 管理员。

结果发现，销售真正的问题不是不会写话术，而是线索优先级混乱。

高价值线索和普通线索混在一起，销售每天先跟谁，主要靠经验。CRM 里有字段，但很多字段没有及时更新；市场活动来的线索也没有统一评分。

这时问题就变了。

不是“销售需要一个助手”。

而是“销售需要知道哪些线索值得优先跟，以及为什么”。

## Design：切出第一个价值闭环

Design 没有直接设计完整销售助手。

它先切出一个小闭环：

“当新线索进入 CRM 后，系统基于公司规模、行业、来源渠道、历史互动和相似客户成交记录，生成线索摘要和优先级建议，由销售确认是否采纳。”

这个切片小，但完整。

| 元素 | 设计结果 |
| --- | --- |
| 用户 | 一线销售 |
| 场景 | 新线索进入 CRM |
| 输入 | 公司信息、渠道、互动记录、相似成交客户 |
| 输出 | 线索摘要、优先级、下一步建议 |
| 边界 | 销售确认，不自动分配客户 |
| 指标 | 建议采纳率、跟进时效、转化率变化 |

FDE 没有先做最炫的助手。

它先做最能验证价值的那一段。

## Engineer：让建议进入真实流程

Engineer 阶段不是把页面做漂亮。

它要解决几个工程问题：

- CRM 字段是否可信。
- 线索评分逻辑如何解释。
- 销售是否能看到引用来源。
- 建议被采纳、修改或忽略时如何记录。
- 错误建议如何进入评测集。

第一版试点只开放给 10 名销售，系统只做建议，不自动派单。

这一步看似保守，但很关键。

它让系统先进入真实工作流，同时把责任留在人手里。

## Feedback：从一个项目变成产品能力

试点两周后，团队发现一个有意思的结果：

销售并不总是采纳“下一步话术”，但很依赖“线索摘要”和“相似成交客户”。

这说明产品机会不一定是“AI 帮销售写话术”，而可能是“AI 帮销售快速理解线索质量”。

于是 Feedback 阶段沉淀出三件事：

- 一套线索摘要模板。
- 一个相似客户召回能力。
- 一份销售采纳/修改记录评测集。

这就是 CDEF 的闭环。

项目没有停在 Demo，也没有停在一次成交支持，而是把现场学习变成了可复用的产品能力。

## 可以带走的判断

CDEF 真正想解决的，不是“项目怎么管理”。

它解决的是 FDE 如何在现场、工程、客户和产品之间不迷路。

客户说“我要一个助手”。

CDEF 会让团队先看现场，再切价值，再做工程，再看反馈。

如果没有 CDEF，项目很容易停在“客户要什么，我们做什么”。

有了 CDEF，团队才会持续追问：这是真问题吗？这个切片能验证价值吗？这个 Demo 能进真实流程吗？上线后客户能不能接住？

这套追问，才是 FDE 项目真正的工作骨架。
