# CDEF 为什么适合 FDE 项目

FDE 项目最难的地方，不是技术栈复杂，而是问题一开始就不稳定。

客户说的是需求，现场暴露的是约束，管理层要的是结果，工程团队面对的是系统边界。很多项目失败，不是因为没人努力，而是因为团队太早进入解决方案，太晚发现真正的问题。

CDEF 的价值，就是给 FDE 一条从混沌走向交付的路径。

从定义上看，CDEF 是一套面向 FDE 项目的四阶段方法：Context、Design、Engineer、Feedback。它把现场勘探、方案设计、工程实现和反馈反哺连成一个闭环，避免项目停在咨询、Demo 或一次性交付。

> **一句可以带走的判断：CDEF 不是项目流程，而是 FDE 在不确定现场里保持判断力的骨架。**

## CDEF 解决什么问题

传统项目管理通常假设需求已经相对稳定。FDE 项目恰恰相反，它面对的是尚未被定义清楚的问题。

| 常见断点 | CDEF 的处理方式 |
| --- | --- |
| 客户表达模糊 | Context 先还原事实和约束 |
| 方案过早膨胀 | Design 切出最小价值闭环 |
| Demo 难进生产 | Engineer 补齐评测、权限、门禁和接管 |
| 经验无法复用 | Feedback 把现场学习反哺产品和方法 |

CDEF 的核心不是让项目变慢，而是让团队在快的时候仍然知道自己在验证什么。

## 四阶段怎么看

Context 是进入现场。它回答“真实问题是什么”。这一阶段不急着画方案，而是看流程、看数据、看人如何兜底。

Design 是切出路径。它回答“先验证哪一段”。这一阶段要把复杂问题切成一个小而完整的价值闭环。

Engineer 是工程推进。它回答“如何让系统真的能运行”。这一阶段从 Demo 走向试点和生产，要补证据、门禁、评测和回滚。

Feedback 是反哺沉淀。它回答“这次现场学习变成了什么”。这一阶段要看业务结果、客户接管和产品复用。

## 为什么适合 AI 时代

AI 让 Demo 变得更容易，也让误判变得更容易。

一个模型接上知识库，几小时就能演示；一个 Agent 接上工具，几天就能跑流程。但越是这样，越需要 CDEF 这样的结构来约束项目：

- Context 防止把“想做 AI”误读成真实问题。
- Design 防止把 AI 能力做成没有流程位置的工具。
- Engineer 防止把 Demo 直接推上生产。
- Feedback 防止一次项目结束后经验散掉。

## 一个简单例子

客户说：“我们想做销售助手。”

CDEF 不会直接开始做聊天机器人，而是这样推进：

| 阶段 | 关键动作 |
| --- | --- |
| Context | 发现销售真正痛点是线索优先级不清、跟进记录不完整 |
| Design | 切出“新线索进入后生成背景摘要和下一步建议”这个场景 |
| Engineer | 接入 CRM、定义字段权限、建立建议采纳率和错误样本评测 |
| Feedback | 根据销售修改记录反哺线索评分规则和产品模板 |

这个例子里，CDEF 让项目从“做助手”变成“改善线索跟进流程”。

## CDEF 的最小产物

| 阶段 | 最小产物 |
| --- | --- |
| Context | 事实约束表、角色地图、问题陈述 |
| Design | 需求切片画布、验收阈值、方案取舍 |
| Engineer | Demo、评测报告、ADR、上线门禁 |
| Feedback | 业务指标复盘、客户接管记录、产品反哺清单 |

CDEF 真正想解决的，不是“项目怎么管理”，而是 FDE 如何在现场、工程、客户和产品之间不迷路。
