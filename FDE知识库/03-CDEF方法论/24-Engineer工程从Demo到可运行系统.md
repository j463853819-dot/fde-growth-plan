# Engineer 工程：从 Demo 到可运行系统

Demo 能跑起来的那一刻，团队最容易高兴得太早。

一个服务团队做了一个自动创建工单 Agent。演示时，用户在群里发一句“客户登录不上”，Agent 能总结问题、识别类型、调用工单系统 API，还能把工单分配给支持团队。

看起来很像已经能用了。

但真要上线时，支持负责人只问了一个问题：

“它如果建错工单，谁来关？客户投诉升级了，谁负责？”

这一下，Demo 和生产之间的距离就露出来了。

> **Demo 证明可能性，Engineer 制造可靠性。**

## 一句话定义

Engineer 是 CDEF 的第三阶段。

它接在 Design 之后，负责把一个已经被切清楚的价值闭环，推进成可以试点、可以上线、可以被客户接管的系统能力。

很多人以为 Engineer 就是“把 Demo 做完整”。

但在 FDE 项目里，Engineer 真正要做的是把可能性变成可靠性。

## Engineer 解决什么问题

Design 阶段解决的是“要验证哪条路径”。

Engineer 阶段解决的是“这条路径能不能在真实环境里运行”。

这中间差很多东西：

| Demo 有什么 | 生产还需要什么 |
| --- | --- |
| 样例数据 | 授权数据、数据质量、更新机制 |
| 演示路径 | 真实流程、异常路径、人工接管 |
| 临时账号 | 正式身份、权限、审计 |
| 人工解释 | 日志、指标、Trace、错误样本 |
| 单次成功 | 回归测试、SLO、告警、回滚 |

Engineer 的任务，就是把这些缺口补齐。

它不是单纯编码阶段，而是从 Demo 到试点、从试点到生产的工程转化。

## Demo 要保留假设意识

Demo 可以简化。

但不能假装没有简化。

FDE 在 Engineer 阶段要记录：

- 哪些数据是样例数据？
- 哪些权限是临时权限？
- 哪些异常路径没有覆盖？
- 哪些操作还没有审计？
- 哪些指标还没有稳定观测？
- 哪些环节还依赖 FDE 手工解释？

这些记录会进入交付证据包。

它们防止 Demo 成功之后产生错觉。

## 三阶段门禁

Engineer 可以按原型、试点、生产三阶段推进。

每个阶段都要有进入条件。

| 阶段 | 放开什么 | 必须守住什么 |
| --- | --- | --- |
| 原型 | 样本数据、演示路径、少量手工配置 | 明确哪些是假设，不能冒充生产能力 |
| 试点 | 真实用户、授权数据、有限流程 | 人工确认、失败记录、指标观测 |
| 生产 | 稳定流程、正式权限、持续运行 | SLO、告警、回滚、审计、接管 Owner |

这三阶段不是流程仪式。

它们是风险逐步释放机制。

## Bootcamp 5 天工作法

有些 FDE 项目需要在很短时间内完成首次价值验证。

Bootcamp 不是 5 天上线，而是 5 天内判断一个方向值不值得进入试点。

| 天数 | 目标 | 产物 |
| --- | --- | --- |
| 第 1 天 | 对齐现场和问题 | 角色地图、PDD 初稿、成功指标 |
| 第 2 天 | 切出最小价值闭环 | 需求切片画布、风险边界 |
| 第 3 天 | 做出可演示原型 | Demo 链路、样本数据、失败样本 |
| 第 4 天 | 接入真实约束 | 权限、接口、评测、人工确认流程 |
| 第 5 天 | 决定下一步 | 继续、缩小、转向或停止的判断 |

Bootcamp 的好处，是让团队快速看到“方向是否成立”。

它不能替代生产化。

## 生产化要补哪些能力

Engineer 阶段至少要补齐六件事：

| 能力 | 说明 |
| --- | --- |
| 数据链路 | 数据来源、更新、质量和权限过滤 |
| 权限控制 | 身份、角色、工具调用和审计 |
| 评测回放 | 样本集、失败样本、回归测试 |
| 可观测性 | 日志、指标、Trace、成本和延迟 |
| 失败处理 | 降级、回滚、人工接管 |
| 交付证据 | ADR、Owner、门禁、运行手册 |

这些不是大公司才需要的复杂流程。

它们是系统进入生产的基本安全带。

Google SRE 强调用 SLO、监控和事件响应来管理服务可靠性。FDE 不一定要照搬完整 SRE 体系，但至少要把“系统出了问题如何发现、谁处理、如何恢复”设计清楚。

## 灰度发布和 5 分钟回滚

进入生产前，FDE 要和客户一起设计发布和回滚方式。

| 发布阶段 | 含义 | 适用场景 |
| --- | --- | --- |
| Canary | 极小范围验证 | 单团队、单场景、低风险用户 |
| EA | Early Access，早期用户试用 | 愿意反馈且能承受轻微不稳定的用户 |
| Broad | 扩大到主要用户群 | 关键风险已被处理，但仍需观测 |
| Full | 全量开放 | 运行、支持、接管机制已经稳定 |

5 分钟回滚不是说每个系统都必须真的 5 分钟恢复所有状态。

它要求团队在上线前回答：

如果出错，谁能在最短时间内关闭、降级、切回人工或撤回自动化动作？

至少要准备：

- 功能开关或权限开关。
- 回退到人工流程的方式。
- 失败样本和异常日志定位方式。
- 值班或响应 Owner。
- 对客户和用户的通知口径。

## Engineer 的退出标准

Engineer 结束时，不能只交代码。

至少要交：

- 可运行系统或试点版本。
- 评测集和回放结果。
- ADR 架构决策记录。
- 权限和工具调用清单。
- 监控指标和告警规则。
- 风险、回滚和人工接管方案。
- 客户接管前的开放问题。

Engineer 阶段的成熟标志，是系统不再只依赖 FDE 个人理解，而开始拥有可复查、可运行、可交接的证据。

## 实战拆解：一个自动创建工单 Agent

回到开头那个自动创建工单 Agent。

一家 B2B 服务团队想做一个 Agent。

目标很明确：用户在群里反馈问题后，Agent 自动识别问题类型，创建工单，并分配给对应支持团队。

Demo 很快就做出来了。

Agent 能读消息，能总结问题，能调用工单系统 API。

看起来已经很接近可用了。

但 Engineer 阶段真正要问的是：

它在什么边界下，才被允许真正创建工单？

## 原型阶段：先验证能力，不扩大责任

第一版原型只用历史对话。

Agent 不真正创建工单，只生成工单草稿。

这一阶段验证三件事：

- 能否正确识别问题类型。
- 能否提取必要字段。
- 能否生成可读的工单描述。

原型阶段不追求自动化。

它追求知道系统哪里会错。

这句话很关键。

很多团队做 Demo 时，只想证明系统哪里能对。Engineer 阶段反过来，要尽快知道它会在哪里错。

## 试点阶段：真实用户进入，但保留人工确认

试点时，Agent 接入一个低风险客户群。

它可以生成工单草稿，但必须由支持人员确认后创建。

同时记录：

- 分类准确率。
- 重复工单率。
- 人工修改率。
- 失败原因。
- 工具调用日志。

这一步最重要的产物，不是“Agent 创建了多少工单”。

而是失败样本。

失败样本告诉团队哪些问题不能自动化，哪些字段需要补充，哪些规则必须转人工。

## 生产阶段：只开放低风险类别

进入生产时，团队没有全量开放。

只允许 Agent 自动创建低风险、规则稳定的问题类别，比如账号开通、权限申请、常见配置咨询。

高风险问题仍然转人工：

- 涉及合同。
- 涉及退款。
- 涉及安全权限。
- 涉及客户投诉升级。

这不是技术不够强。

这是责任边界清楚。

## 最后留下什么

这个 Engineer 阶段最后留下：

- 一套工单分类评测集。
- 一份 Agent 工具权限清单。
- 一份 ADR：为什么先草稿、再人工确认、最后只开放低风险自动创建。
- 一套失败样本回放机制。
- 一份告警和回滚方案。
- 一份支持团队接管手册。

这时，系统才从“能演示”变成“能运行”。

## 可以带走的判断

Engineer 的核心，不是让系统显得更智能。

是让系统进入真实责任时，不靠运气运行。

FDE 做工程，最怕的是一种错觉：演示路径跑通了，就以为系统已经完成。

真正的工程交付，要把权限、数据、评测、日志、告警、回滚和接管都放进系统边界里。

只有这样，客户才不是“看到了一个 Demo”，而是真的拿到了一套可以运行的能力。
