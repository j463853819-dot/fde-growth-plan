# Demo 到生产系统，中间差了什么？

很多 AI 项目最危险的时刻，不是 Demo 失败，而是 Demo 成功。

Demo 成功会让团队产生一种错觉：既然已经跑通了，那离上线应该不远了。尤其现在模型能力很强，原型工具也很快，半天做出一个“看起来能用”的东西并不稀奇。

但 FDE 视角下，Demo 和生产系统解决的是两类问题。Demo 证明“这件事可能有价值”，生产系统证明“这件事可以被组织长期依赖”。

这里的“生产系统”不是指代码部署到了服务器上，而是指系统进入真实业务环境后，能够在明确权限、稳定数据、可观测运行、可追责输出和可接管运维的条件下持续工作。它需要面对真实用户、真实异常、真实安全要求和真实业务责任。

因此，从 Demo 到生产的差距，本质上是从“可能性验证”到“责任体系建设”的差距。前者看重速度和想象力，后者看重稳定性、治理能力和组织承接。

> **一句可以带走的判断：Demo 验证可能性，生产系统承担责任。**

## Demo 和生产系统不是同一种东西

Demo 环境通常是被精心整理过的。样例数据干净，流程简单，演示人知道怎么绕过异常，用户也愿意配合。

生产环境恰恰相反。数据会缺字段，权限会卡住，用户会误操作，模型会偶尔答偏，系统会遇到高峰，业务规则会变化，合规会追问每一次数据访问。

可以用这张表看差异：

| 维度 | Demo | 生产系统 |
| --- | --- | --- |
| 目标 | 验证方向 | 长期运行 |
| 数据 | 样例、脱敏、手工整理 | 真实、持续变化、有权限边界 |
| 用户 | 少量配合用户 | 多角色、真实压力、真实习惯 |
| 错误 | 可以解释或忽略 | 必须记录、兜底、回滚 |
| 责任 | 演示团队负责 | 业务、运维、安全、产品共同负责 |
| 成功标准 | 看起来可行 | 可用、可测、可审计、可接管 |

Demo 是入口，不是终点。

## 差距一：数据从样例变成流动资产

Demo 阶段可以用几份样例文档、几百条历史记录，甚至手工整理一批数据。

生产系统不行。生产系统要面对持续变化的数据源：新增记录、字段变更、权限变化、数据质量波动、历史口径不一致。

如果数据链路不稳定，AI 输出就会不稳定。很多 AI 项目的问题不是模型突然变笨，而是上游数据变了、知识库过期了、权限过滤漏了。

生产化时必须回答：

- 数据从哪里来？
- 谁有权访问？
- 如何更新？
- 如何脱敏？
- 如何记录访问？
- 数据异常时系统怎么降级？

## 差距二：权限和审计从“临时开一下”变成硬边界

Demo 里常见一句话：“先给我开个权限，我跑一下。”

生产环境不能这样。

尤其在企业 AI 项目里，权限不是小问题。模型看到什么，就可能影响它回答什么；Agent 能调用什么工具，就可能执行什么动作。权限设计不清楚，AI 系统就可能越权读取、错误写入或泄露敏感信息。

生产系统至少要有：

- 身份边界。
- 数据分级。
- 工具调用权限。
- 审计日志。
- 高风险动作人工确认。
- 访问和操作的可追溯记录。

## 差距三：评测从“感觉不错”变成质量门禁

Demo 成功往往靠主观感受：这个回答不错，这个总结挺像样，这个流程看起来能省时间。

生产系统不能靠感觉。

AI 输出具有不稳定性，提示词、检索语料、模型版本、业务规则变化都会影响结果。因此，生产化必须建立评测机制：

```mermaid
flowchart LR
    A["真实任务"] --> B["评测集"]
    B --> C["验收阈值"]
    C --> D["上线门禁"]
    D --> E["线上追踪"]
    E --> F["失败样本回流"]
    F --> B
```

评测不是一次性测试，而是一条持续反馈链。

## 差距四：异常处理从“人工解释”变成系统能力

Demo 里出错，演示人可以解释：“这个样本比较特殊”“这里还没接真实接口”“上线前会补”。

生产系统出错，用户只会问：现在怎么办？

所以生产系统必须设计异常处理：

- 模型低置信度怎么办？
- 工具调用失败怎么办？
- 数据缺失怎么办？
- 输出冲突怎么办？
- 用户不接受建议怎么办？
- 系统需要暂停或回滚时谁负责？

生产系统不是不出错，而是出错后能被发现、限制影响、恢复运行。

## 差距五：用户采用从“愿意看”变成“真的用”

Demo 里用户说“这个很好”，不代表上线后会每天使用。

生产系统要进入真实岗位动作：客服要在工作台里用，销售要在跟进流程里用，运营要在日报节奏里用，管理者要在决策会上用。

如果 AI 系统没有嵌入原来的工作入口，用户就会多一个工具、多一次切换、多一份负担。最后它可能不是提效，而是添乱。

## 生产化检查框架

从 Demo 到生产，可以用这张表做检查：

| 检查项 | 关键问题 |
| --- | --- |
| 数据 | 是否有稳定来源、更新机制、权限边界 |
| 安全 | 是否有身份、审计、敏感信息处理 |
| 评测 | 是否有评测集、阈值、回归机制 |
| 运行 | 是否有监控、告警、回滚、成本控制 |
| 用户 | 是否嵌入真实工作流，是否有人负责采用 |
| 接管 | 客户或内部团队是否能维护和迭代 |

## 结尾判断框架

判断一个 Demo 能不能进入生产，不要问“它能不能跑”，而要问：

| 问题 | 代表什么 |
| --- | --- |
| 失败时谁知道？ | 可观测性 |
| 出错时谁接管？ | 运行责任 |
| 变更后怎么验证？ | 评测和回归 |
| 数据和权限谁负责？ | 治理边界 |
| 用户为什么每天会用？ | 组织采纳 |

如果这些问题答不上来，Demo 再漂亮，也还只是 Demo。

从这个意义上说，生产化不是 Demo 的最后一步，而是一次重新设计责任的过程。AI 越有能力，这件事越不能省。
