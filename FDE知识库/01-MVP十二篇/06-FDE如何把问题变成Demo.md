# FDE 如何把问题变成 Demo？

Demo 最危险的地方，是它太容易成功。

现在用 AI 做一个看起来像样的原型并不难：接一个模型，放几条样例数据，做一个简单页面，演示时效果往往不错。问题是，很多 Demo 成功之后，团队反而更容易误判，以为项目已经离生产很近。

Demo 在 FDE 项目里很重要，但它经常被误解。很多人把 Demo 当成“小产品”，或者当成一次漂亮演示。FDE 视角下，Demo 的真正价值不是好看，而是验证关键假设：这个问题值不值得继续做？数据能不能接？用户会不会用？AI 输出是否可信？系统能不能进入下一阶段？

在 FDE 语境中，Demo 更准确的定义是“最小可验证系统”，而不是“最小可展示界面”。它需要围绕一个具体业务场景，把输入、处理、输出、反馈和关键风险串起来，用最小成本验证项目是否值得进入下一阶段。

一个 FDE Demo 至少要说明三件事：它验证了哪个业务假设，暴露了哪个生产风险，下一步决策是什么。没有这三点，Demo 再流畅，也只是演示资产，不是工程证据。

> **一句可以带走的判断：Demo 不是为了证明你很强，而是为了证明这个方向值得继续。**

## Demo 之前，先切一个价值闭环

模糊问题不能直接变 Demo，必须先切片。

一个好的 Demo 切片，不是一个功能点，而是一个最小价值闭环。它可以小，但要完整。

| 不完整切片 | 更好的 Demo 切片 |
| --- | --- |
| 接入知识库 | 客服处理退款问题时，能看到政策、历史案例和建议回复 |
| 做自动日报 | 运营主管每天 10 点前看到异常趋势、原因和建议动作 |
| 做销售助手 | 销售打开线索时看到优先级、客户背景和下一步跟进建议 |
| 做数据看板 | 管理者能定位某个指标异常来自哪个流程节点 |

Demo 的目标是让业务方看到：这不是一个抽象能力，而是一段能改变工作动作的流程。

## 一个好 Demo 验证什么？

FDE 做 Demo，通常不是验证“能不能做出来”，而是验证“最不确定的部分是否成立”。

常见假设包括：

| 假设 | Demo 需要验证 |
| --- | --- |
| 价值假设 | 用户看到结果后是否觉得有用 |
| 数据假设 | 所需输入是否稳定、完整、可授权 |
| 模型假设 | AI 输出是否达到可接受质量 |
| 流程假设 | 结果是否能接入真实工作动作 |
| 风险假设 | 错误是否可发现、可纠正、可控制 |
| 采用假设 | 用户是否愿意改变原来的工作方式 |

如果一个 Demo 只验证了“技术能跑”，没有验证业务和风险，它还不够 FDE。

## Demo 里可以简化什么？

Demo 阶段当然可以简化，但要知道哪些能简化，哪些不能假装。

可以简化的是：

- 界面不必精致。
- 自动化不必覆盖所有分支。
- 数据量可以先小。
- 部署可以先轻。
- 用户范围可以先窄。

不能假装的是：

- 数据来源。
- 权限边界。
- 关键业务规则。
- 人工确认点。
- 错误样本。
- 生产风险。

> **Demo 可以粗糙，但不能虚假。粗糙是为了快，虚假会把团队带到错误方向。**

## Demo 的标准流程

一个 FDE Demo 可以按五步推进：

```mermaid
flowchart LR
    A["现场问题"] --> B["价值切片"]
    B --> C["关键假设"]
    C --> D["最小 Demo"]
    D --> E["用户反馈"]
    E --> F["继续/缩小/停止"]
```

每一步都要留下证据。

| 阶段 | 要留下什么 |
| --- | --- |
| 现场问题 | 问题发生位置、角色、当前损失 |
| 价值切片 | 用户、触发场景、输入、输出、验收条件 |
| 关键假设 | 最不确定但最影响成败的判断 |
| 最小 Demo | 可重复演示链路、样例数据、失败样本 |
| 用户反馈 | 真实使用意见，不只是“挺好” |
| 决策 | 继续、缩小、换切片或停止 |

## Demo 最容易带来的误判

Demo 成功后，团队最容易高估项目成熟度。

演示环境里，数据是干净的，用户是配合的，异常是被提前避开的，权限是临时开的，流程是演示人熟悉的。生产环境不是这样。

所以 Demo 结束时，FDE 要特别明确三件事：

- 哪些是真能力？
- 哪些是临时绕过？
- 哪些风险还没有验证？

如果这三件事不写清楚，Demo 就会被误读为“已经差不多能上线了”。

## 结尾判断框架

判断一个 Demo 是否合格，可以问五个问题：

| 问题 | 如果答不上来 |
| --- | --- |
| 它验证的是哪个业务切片？ | 可能只是功能演示 |
| 它验证了哪个关键假设？ | 可能只是炫技 |
| 它用了哪些真实约束？ | 可能离生产很远 |
| 它暴露了哪些失败样本？ | 可能只展示了好结果 |
| Demo 后的决策是什么？ | 可能没有推动项目向前 |

Demo 的价值不是让人鼓掌，而是让团队更早知道：该继续、该缩小，还是该停下。

这句话在 AI 时代尤其重要。因为当 Demo 变得越来越便宜，真正值钱的就不是“能不能做出一个东西”，而是“能不能用它更早暴露真问题”。
