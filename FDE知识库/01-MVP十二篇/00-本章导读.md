# 01-MVP 十二篇

这一章是 FDE 的角色入口，回答 FDE 是什么、为什么 AI 时代需要它、它和产品经理、售前、咨询、交付工程师有什么不同，以及什么样的人适合进入这个角色。

> **一句可以带走的判断：FDE 不是“更懂业务的工程师”，也不是“会写代码的咨询顾问”，而是能在客户现场直接推动问题定义、系统验证和业务交付的人。**

## 角色本质

FDE 至少包含四个不可省略的关键词：

- **派驻现场**：不是远离客户接需求，而是进入客户真实工作环境。
- **深度嵌入**：理解业务流程、组织结构、决策文化和一线动作。
- **技术解决**：能用工程手段搭系统、接数据、做集成、推生产。
- **直接交付**：交付能运行、能验收、能接管的业务结果。

## 价值三角

```text
      技术深度
         /\
        /  \
       / FDE\
      /______\
业务理解    客户同理心
```

FDE 的价值来自三角平衡：

| 能力 | 作用 | 缺失后果 |
| --- | --- | --- |
| 技术深度 | 判断什么能做、怎么做、能不能进生产 | 容易停留在方案或沟通层 |
| 业务理解 | 看懂真实流程、指标和约束 | 容易做出客户不用的系统 |
| 客户同理心 | 理解组织压力、采用阻力和责任边界 | 容易把正确方案推不动 |

## 和相近角色的区别

| 角色 | 更关注什么 | 和 FDE 的区别 |
| --- | --- | --- |
| 后端工程师 | 系统稳定性、接口、服务能力 | FDE 需要更靠近客户现场和问题定义 |
| 产品经理 | 需求、路线图、用户体验 | FDE 需要直接做技术验证和系统交付 |
| 咨询顾问 | 诊断、方案、组织建议 | FDE 需要把方案变成可运行系统 |
| 售前工程师 | 方案展示、成交支持 | FDE 对试点、生产和接管结果负责 |
| 交付工程师 | 按既定方案实施 | FDE 经常要在方案未清楚时先定义问题 |

## 反选人哲学

不是所有优秀工程师都适合做 FDE。

| 不适合的人 | 缺的 FDE 本质 |
| --- | --- |
| 完美主义工匠型 | 速度优先于优雅的交付力 |
| 坐等需求执行型 | 自己定义问题的发现力 |
| 觉得现在挺好型 | 对现状的不满和洞察力 |
| 只懂技术内向型 | 双向翻译能力 |
| 受不了换行业型 | 快速学习和适应能力 |

这里的“反选”不是劝退，而是帮助读者判断：FDE 的困难不只是技术难，而是要持续面对模糊现场、陌生行业、组织阻力和不完整信息。

## Echo / Delta 倾向

可以用一个简单区分来判断自己是否适合 FDE：

- **Echo 倾向**：更擅长复述需求、执行明确任务、维持既有流程。
- **Delta 倾向**：更愿意发现偏差、定义问题、推动变化、承担不确定性。

FDE 更需要 Delta 倾向。它不是只把客户说的话变成代码，而是找出客户自己还没有表达清楚的问题。
