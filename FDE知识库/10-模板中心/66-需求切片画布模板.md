# 需求切片画布模板

需求切片画布用于把一个模糊需求切成最小可验证价值闭环。

它解决的问题是：不要把一个大而泛的需求直接做成 Demo。Demo 应该验证最关键的不确定性，而不是展示最多功能。

> **需求切片不是把需求砍小，而是把价值闭环切清楚。**

## 一句话定义

需求切片画布是一张把目标角色、触发条件、输入、处理、输出、指标和风险边界放在同一页上的设计表。

它的目标是决定第一版 Demo 或试点到底验证什么。

## 什么时候用

- 已经完成初步事实收集。
- 客户需求太大，无法直接实现。
- 团队需要确定第一个 Demo 做什么。
- 需要向客户解释为什么先做小切口。

## 模板

| 模块 | 要填写的内容 | 示例 |
| --- | --- | --- |
| 场景名称 | 这个切片叫什么 | 退款咨询建议回复 |
| 目标角色 | 谁使用或受益 | 一线客服 |
| 触发条件 | 什么时候发生 | 用户咨询退款政策 |
| 当前痛点 | 旧流程哪里慢、错、贵或有风险 | 需要切换订单系统和政策文档 |
| 输入 | 需要哪些数据、文档或用户输入 | 订单状态、退款政策、历史案例 |
| 处理 | AI、规则、人分别做什么 | AI 生成建议，客服确认 |
| 输出 | 最终交付给用户或系统的结果 | 建议回复和引用来源 |
| 验收指标 | 如何判断有效 | 响应时间下降 30%，采纳率超过 60% |
| 风险边界 | 哪些不能自动化 | 高金额退款必须转人工 |
| 不做事项 | 本轮明确不做什么 | 不自动退款，不直接发送回复 |
| 试点范围 | 先在哪些用户、数据或流程中试 | 10 名客服，退款咨询场景 |
| 下一阶段条件 | 满足什么才继续扩大 | 评测通过率 85%，投诉无上升 |

## 好切片和坏切片

| 坏切片 | 问题 | 更好的切片 |
| --- | --- | --- |
| 做一个 AI 助手 | 太泛，无法验收 | 客服处理退款咨询时生成建议回复 |
| 做自动日报 | 不知道服务哪个决策 | 运营主管每天看到异常指标和原因解释 |
| 做销售助手 | 范围太大 | 新线索进入后生成背景摘要和下一步建议 |
| 做管理驾驶舱 | 容易变成大屏 | 定位某个指标异常来自哪个流程节点 |

## 判断标准

一个需求切片合格，至少要满足：

- 有明确目标角色。
- 有明确输入和输出。
- 有可衡量验收指标。
- 有风险边界。
- 能在有限时间内验证。
- 成功或失败都能改变下一步决策。

如果一个切片失败后团队仍然不知道该继续、缩小、转向还是停止，说明切片还不够好。

换句话说，好的切片不只服务成功，也服务失败后的决策。

## 填写顺序

需求切片不要从“功能清单”开始填，建议按这个顺序：

1. 先填目标角色和触发条件。
2. 再填当前痛点和业务影响。
3. 然后填输入、处理和输出。
4. 最后才填验收指标、风险边界和下一阶段条件。

这个顺序能防止团队一上来就讨论界面、模型和工具，而忽略工作流本身。

## 合格示例

| 模块 | 内容 |
| --- | --- |
| 场景名称 | 退款咨询建议回复 |
| 目标角色 | 一线客服 |
| 触发条件 | 用户咨询退款政策或退款进度 |
| 当前痛点 | 客服需要在订单系统、政策文档和历史案例之间切换 |
| 输入 | 订单状态、退款政策、历史相似工单 |
| 处理 | AI 生成建议回复和引用来源，客服确认后发送 |
| 输出 | 可编辑建议回复、风险提示、引用来源 |
| 验收指标 | 平均响应时间下降 30%，采纳率超过 60% |
| 风险边界 | 高金额退款、投诉风险、政策例外转人工主管 |
| 不做事项 | 不自动退款，不直接发送给客户 |

## 常见误填

| 误填方式 | 后果 |
| --- | --- |
| 场景名称写成“智能助手” | 范围太大，无法验收 |
| 目标角色写成“全员” | 入口和使用频率不清 |
| 指标写成“提升效率” | 无法判断试点是否成功 |
| 不写不做事项 | Demo 后范围快速膨胀 |

## 交付产物

需求切片画布完成后，应该能产出三件事：

1. 第一版 Demo 的范围。
2. 试点验收指标。
3. 明确不做的边界。

## 可以带走的判断

FDE 切的不是功能点，而是能被验证、能被停止、也能被扩大的价值闭环。
