# 事实与约束表模板

事实与约束表用于 FDE 项目早期，把客户说法、现场事实、团队判断和不可忽略的约束拆开。

它解决的问题很简单：不要把“客户说了什么”直接当成“我们要做什么”。

> **事实与约束表的核心，是把项目从“听起来有道理”拉回“证据上站得住”。**

## 一句话定义

事实与约束表是一张用于区分事实、解释、判断、约束和待验证问题的现场勘探表。

它通常是 Context 阶段最先产出的证据。

## 什么时候用

- 客户刚提出一个模糊需求。
- 业务方、技术方、管理层说法不一致。
- 团队准备做 Demo，但还不确定真实问题。
- 项目已经开始，但频繁返工。

## 模板

| 字段 | 内容 | 示例 |
| --- | --- | --- |
| 编号 | 事实或约束编号 | F-001 |
| 来源 | 访谈、日志、工单、系统截图、会议纪要 | 客服主管访谈 |
| 类型 | 事实 / 解释 / 判断 / 约束 / 待验证 | 事实 |
| 描述 | 尽量写可验证内容 | 退款咨询平均响应 8-10 分钟 |
| 相关角色 | 谁受影响，谁处理，谁审批 | 一线客服、客服主管 |
| 业务影响 | 时间、成本、质量、风险或体验影响 | 用户等待时间长，投诉上升 |
| 证据链接 | 截图、数据、文档或记录位置 | 工单统计表 2026-06 |
| 当前假设 | 团队对原因的初步判断 | 知识库和订单系统分散 |
| 约束条件 | 数据、权限、系统、合规、组织、时间 | 订单字段仅授权客服查看 |
| 待验证问题 | 下一步要验证什么 | 是否可在工作台展示脱敏摘要 |
| Owner | 谁负责继续确认 | FDE / 客服主管 |
| 状态 | 已确认 / 待验证 / 已失效 | 待验证 |

## 填写示例

| 字段 | 内容 |
| --- | --- |
| 编号 | F-001 |
| 来源 | 历史工单统计 |
| 类型 | 事实 |
| 描述 | 过去 30 天退款咨询占客服咨询量 38%，平均响应时间 8.6 分钟 |
| 相关角色 | 一线客服、客服主管、售后运营 |
| 业务影响 | 用户等待时间长，高峰期投诉上升 |
| 证据链接 | 客服工单月报 |
| 当前假设 | 响应慢主要来自政策查询和订单状态确认 |
| 约束条件 | 订单数据包含敏感字段，不能直接暴露给所有客服 |
| 待验证问题 | 是否可以生成脱敏订单摘要 |
| Owner | FDE + 客服主管 |
| 状态 | 待验证 |

## 使用提醒

事实与约束表不追求一次填满。

它应该随着项目推进不断更新。最重要的是把“已经知道的事实”和“只是我们的解释”分开。很多 FDE 项目失败，就是因为这两件事混在一起了。

如果一条信息无法说明来源，它就不要被写成事实；如果一条判断还没有证据，它就应该进入“待验证问题”。

## 合格标准

一张事实与约束表填完后，至少要做到：

| 标准 | 判断方式 |
| --- | --- |
| 事实可验证 | 每条关键事实都有来源或证据 |
| 解释不冒充事实 | “客户觉得慢”和“平均响应 8.6 分钟”分开写 |
| 约束可行动 | 不是写“数据有问题”，而是写清哪个字段、谁授权、什么时候可用 |
| 待验证问题明确 | 下一步知道要访谈谁、查什么数据、做什么实验 |
| Owner 清楚 | 每条重要待验证项都有人继续推进 |

如果表里大量出现“可能、应该、感觉、客户希望”，说明还停留在主观判断阶段，需要继续补证据。

## 常见误填

| 误填方式 | 问题 |
| --- | --- |
| 把客户原话全写成事实 | 客户说法可能只是局部视角 |
| 只写业务痛点，不写系统约束 | 后面 Demo 很容易接不上生产 |
| 只写问题，不写证据链接 | 复盘时没人知道依据来自哪里 |
| 不更新状态 | 已失效的信息继续影响决策 |

## 交付产物

事实与约束表完成后，应该能支持三个决策：

1. 这个问题是否值得继续做需求切片。
2. 哪些约束会影响 Demo、试点或生产。
3. 下一轮勘探要验证什么。

## 可以带走的判断

FDE 早期最重要的能力，不是更快给方案，而是更快把事实、解释和假设拆开。
