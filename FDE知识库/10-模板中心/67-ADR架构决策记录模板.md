# ADR 架构决策记录模板

ADR 用来记录 FDE 项目里的关键架构和系统取舍。

它不是为了补文档，而是为了让团队未来能复查：当时为什么这么做，为什么不选别的方案，什么情况下要重新评估。

> **ADR 记录的不是“用了什么技术”，而是在当时约束下为什么这样取舍。**

## 一句话定义

ADR 是一份轻量架构决策记录，用来保存关键方案选择、备选方案、取舍理由、影响范围和复审条件。

## 什么时候必须写 ADR

- 改变数据流向。
- 改变权限边界。
- 引入新模型、新工具或新平台。
- 决定是否自动写入业务系统。
- 选择私有化、云端或混合部署。
- 决定试点和生产的回滚方式。
- 做了会影响客户接管的技术选择。

## 模板

```markdown
# ADR-编号：决策标题

## 状态
草案 / 已接受 / 已替代 / 已废弃

## 背景
当前业务场景是什么？遇到了什么问题？有哪些现场约束？

## 决策
我们最终选择什么方案？

## 备选方案
| 方案 | 优点 | 风险 | 为什么未选择 |
| --- | --- | --- | --- |
| 方案 A |  |  |  |
| 方案 B |  |  |  |

## 取舍理由
为什么当前方案最合适？它牺牲了什么？

## 影响范围
- 数据：
- 权限：
- 用户：
- 运维：
- 成本：
- 安全/合规：

## 复审触发
什么条件发生时，需要重新评估这个决策？

## 回滚方式
如果方案失败，如何退回或降级？

## Owner
谁负责维护这个决策？
```

## 示例：Agent 是否允许自动写入 CRM

| 模块 | 内容 |
| --- | --- |
| 背景 | 销售希望 Agent 自动更新 CRM 跟进状态 |
| 决策 | 试点阶段只允许“生成建议，销售确认后写入” |
| 理由 | 当前错误样本不足，自动写入风险高 |
| 复审触发 | 连续两周建议采纳率超过 85%，错误率低于 2% |
| 回滚方式 | 关闭写入入口，保留只读建议 |

## 使用提醒

ADR 不需要很长。

好的 ADR 应该让三个月后的接手者用五分钟理解：当时为什么这样做，以及什么时候该推翻这个决定。

FDE 项目里的很多“临时方案”，如果没有 ADR，很容易在没人记得原因的情况下变成长期方案。

## 合格标准

一条 ADR 写完后，要能回答四个问题：

| 问题 | 要求 |
| --- | --- |
| 当时为什么要做决策 | 背景里有业务场景和约束，不只是技术偏好 |
| 为什么选这个方案 | 有备选方案和取舍理由 |
| 这个决策影响谁 | 数据、权限、用户、运维、成本、安全都被检查 |
| 什么时候重新评估 | 有清楚的复审触发条件 |

如果 ADR 只写“我们决定使用某某方案”，没有备选和取舍，它就不是决策记录，只是结论备忘。

## FDE 项目里最该写 ADR 的场景

| 场景 | 为什么必须记录 |
| --- | --- |
| 是否允许 Agent 写入业务系统 | 影响责任、权限和回滚 |
| 是否使用客户生产数据做试点 | 影响合规和数据授权 |
| 是否切换模型或供应商 | 影响效果、成本和可用性 |
| 是否把能力做成产品功能 | 影响路线图和维护责任 |
| 是否私有化部署 | 影响成本、性能、安全和交付周期 |

## 常见误区

- 把 ADR 写成技术方案说明，缺少业务背景。
- 只写最终方案，不写为什么不选其他方案。
- 没有复审触发，导致临时方案永久化。
- 没有 Owner，后续没人维护和废弃。

## 交付产物

一条合格 ADR 至少应该包含：

1. 当前业务和系统约束。
2. 已选择方案和备选方案。
3. 取舍理由和代价。
4. 复审触发条件。
5. 回滚或替代路径。

## 可以带走的判断

FDE 项目越接近生产，越不能只留下“我们决定这么做”，必须留下“为什么当时只能这么做”。
