# ADR 架构决策记录模板

ADR 用来记录 FDE 项目里的关键架构和系统取舍。

它不是为了补文档，而是为了让团队未来能复查：当时为什么这么做，为什么不选别的方案，什么情况下要重新评估。

## 什么时候必须写 ADR

- 改变数据流向。
- 改变权限边界。
- 引入新模型、新工具或新平台。
- 决定是否自动写入业务系统。
- 选择私有化、云端或混合部署。
- 决定试点和生产的回滚方式。
- 做了会影响客户接管的技术选择。

## 模板

```markdown
# ADR-编号：决策标题

## 状态
草案 / 已接受 / 已替代 / 已废弃

## 背景
当前业务场景是什么？遇到了什么问题？有哪些现场约束？

## 决策
我们最终选择什么方案？

## 备选方案
| 方案 | 优点 | 风险 | 为什么未选择 |
| --- | --- | --- | --- |
| 方案 A |  |  |  |
| 方案 B |  |  |  |

## 取舍理由
为什么当前方案最合适？它牺牲了什么？

## 影响范围
- 数据：
- 权限：
- 用户：
- 运维：
- 成本：
- 安全/合规：

## 复审触发
什么条件发生时，需要重新评估这个决策？

## 回滚方式
如果方案失败，如何退回或降级？

## Owner
谁负责维护这个决策？
```

## 示例：Agent 是否允许自动写入 CRM

| 模块 | 内容 |
| --- | --- |
| 背景 | 销售希望 Agent 自动更新 CRM 跟进状态 |
| 决策 | 试点阶段只允许“生成建议，销售确认后写入” |
| 理由 | 当前错误样本不足，自动写入风险高 |
| 复审触发 | 连续两周建议采纳率超过 85%，错误率低于 2% |
| 回滚方式 | 关闭写入入口，保留只读建议 |

## 使用提醒

ADR 不需要很长。

好的 ADR 应该让三个月后的接手者用五分钟理解：当时为什么这样做，以及什么时候该推翻这个决定。
