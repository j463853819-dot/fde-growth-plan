# RACI 责任边界矩阵模板

FDE 项目里，很多风险不是技术风险，而是责任不清。

系统出了问题，业务说找技术，技术说找 FDE，FDE 说客户没接管，安全说之前没人报审。这种情况一旦发生，说明项目早期没有把责任边界说清楚。

RACI 矩阵用来明确每件关键事项里谁负责、谁批准、谁咨询、谁知会。

> **RACI 的价值不是分锅，而是让生产责任在上线前被看见。**

## 一句话定义

RACI 是一张责任边界矩阵，用来明确 FDE 项目中关键事项的执行人、最终负责人、咨询方和知会方。

## RACI 定义

| 缩写 | 含义 | 说明 |
| --- | --- | --- |
| R | Responsible | 具体执行和推进的人 |
| A | Accountable | 对结果最终负责的人，只能有一个 |
| C | Consulted | 需要参与讨论和给意见的人 |
| I | Informed | 需要被同步信息的人 |

## 模板

| 事项 | FDE | 业务 Owner | 客户 IT/平台 | 安全/合规 | 产品团队 | 客户成功 |
| --- | --- | --- | --- | --- | --- | --- |
| 真实问题确认 | R | A | C | I | C | I |
| 需求切片确认 | R | A | C | C | C | I |
| 数据授权 | C | A | R | C | I | I |
| 架构方案 | R | C | A | C | C | I |
| Agent 工具权限 | R | C | C | A | C | I |
| 评测集验收 | R | A | I | C | C | I |
| 生产准入 | R | A | R | C | I | I |
| SLO 和告警 | C | A | R | C | I | I |
| 客户接管 | R | A | R | C | I | C |
| 产品反哺 | R | C | I | I | A | C |

## 使用规则

- 每一行只能有一个 A。
- R 可以有多个，但要避免所有人都是 R。
- 安全、合规、客户 IT 不要只在上线前才出现。
- 客户接管的 A 通常应该在客户侧，不应该长期是 FDE。

## 常见问题

| 问题 | 风险 |
| --- | --- |
| 没有 A | 出问题没人最终负责 |
| 太多 A | 决策反而没人拍板 |
| FDE 全是 R/A | 项目会变成长期代运营 |
| 客户只做 I | 客户无法真正接管 |

RACI 的价值不是填表，而是提前暴露责任冲突。

## 什么时候必须重画 RACI

RACI 不是项目启动时填一次就结束。下面情况出现时，需要重新确认：

| 触发条件 | 为什么要重画 |
| --- | --- |
| Demo 进入真实试点 | 用户、数据和风险范围变了 |
| Agent 从建议变成写入 | 责任从辅助变成执行 |
| 客户 IT 接入生产系统 | 运维、告警和回滚责任变了 |
| 项目从单部门扩到多部门 | A 可能发生冲突 |
| FDE 准备离场 | 接管责任必须转移到客户侧 |

## 合格标准

一张 RACI 表合格，不是因为每格都填满，而是因为关键责任没有悬空：

- 生产事故谁最终负责。
- 数据授权谁批准。
- AI 输出质量谁验收。
- Prompt、知识库、评测集谁维护。
- 客户接管谁签字。

如果这些问题答不出来，项目还没有真正准备好上线。

## 一个实用提醒

FDE 可以在早期承担很多 R，但不应该长期承担 A。否则项目表面交付成功，实际仍然没有被客户组织接住。

## 可以带走的判断

如果一个项目的 RACI 表里 FDE 长期承担大多数 A，它就还不是一个可接管项目。
